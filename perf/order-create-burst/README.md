# 주문 생성 — 2,000건 집중 요청과 명시적 flush 생략 비교

## 목적과 결론

서로 다른 회원이 같은 상품에 주문을 한 건씩 집중 요청할 때,
주문·결제·재고의 정확성과 호출 지연을 확인했다.

10 → 100 → 500 → 1,000 → 2,000건으로 단계적으로 확대했다.
이후 Java 진단 기록에서 DB 연결 대기를 확인하고,
주문 저장의 saveAndFlush()를 save()로 변경하는 후보를 비교했다.

변경 전·후 각각 앱 재시작과 예열 1회 후 본 측정 3회를 수행했다.
실행별 전체 호출 P95 중앙값은 5,739.25ms에서 5,403.15ms로
5.86% 감소했다. 평균과 P99의 중앙값도 감소했다.

본 측정 6회에서 주문 12,000건과 응답 검증 84,000개가 통과했다.
HTTP 실패·중단은 0건이며, DB 검증과 취소 후 재고 복구도 통과했다.

현재 실험 범위에서 변경을 유지할 근거가 있다고 판단했다.
관측된 감소분 전체를 코드 변경의 인과 효과로 확정하지는 않는다.

## 기존 주문 생성·취소 반복 부하와의 차이

| 구분 | 기존 반복 부하 | 이번 집중 요청 |
|---|---|---|
| 흐름 | 생성·취소 후 대기하며 반복 | 회원별 생성 1회 |
| 부하 | 최대 100 VU, 60초 반복 | 최대 2,000 VU, 각 1회 |
| 상품 | 공통 상품·분산 상품 비교 | 실행별 새 공통 상품 |
| 취소 | 측정 흐름에 포함 | 측정·검증 후 별도 수행 |
| 개선 후보 | DB 연결 풀 확대 | 명시적 flush 생략 |

시나리오와 측정 지표가 다르므로 두 실험의 수치를 직접 비교하지 않는다.

## 실행 환경

- 기준 소스: 529966e8 기반 브랜치
- Java 17, JVM 힙 최소 256MB·최대 512MB
- 앱 포트 18092, 관리 포트 18093
- MySQL 포트 13316
- 전용 DB: attraction_order_create_burst_perf
- Redis 포트 16396, DB 2
- Hikari 최대 연결 수: 변경 전·후 모두 10개
- 실험에 불필요한 스케줄러 비활성화
- 실제 외부 결제 승인 요청은 수행하지 않음
- 본 비교 전 이전 주문·내 정보 조회 실험 앱 종료
- 본 비교는 잠자기 방지 사용, JFR 미사용
- k6 이미지는 실행 명령에 기록한 digest로 고정

회원 가입과 로그인은 측정 전에 수행한다.
실행마다 가격 10,000원·재고 10,000개인 새 상품을 준비한다.
회원별 주문 수량은 1개다.

## 시나리오와 지표

각 VU는 공통 목표 시각까지 대기한 뒤 주문을 한 번 요청한다.
목표 시각은 setup에서 약 15초 뒤로 지정한다.
요청 시간 제한은 30초, 시나리오 최대 시간은 90초다.

주지표 burst_request_elapsed는 요청 시작부터 HTTP 호출 반환까지의
클라이언트 경과 시간이다. JSON 해석과 응답 검사는 제외한다.
서버 내부 처리 시간만을 의미하지 않는다.

burst_http_duration은 k6의 HTTP 송신·대기·수신 시간 지표다.
전체 호출 시간과 구분해서 기록한다.

burst_launch_offset은 목표 시각 대비 클라이언트 호출 시작 지연이다.
검증 도구는 최솟값 0 이상, 최댓값 1,000ms 미만을 요구한다.
호출 분산은 시작 지연의 최댓값과 최솟값 차이다.
서버 도착 시각이나 서버 내부 동시 처리 수를 측정한 값은 아니다.

이번 주문 실험에는 응답 시간에 대한 업무 SLO를 설정하지 않았다.
검증 통과는 정확성과 부하 발생 조건의 충족을 의미한다.
사용자에게 충분히 빠르다는 판정과는 구분한다.

15초 대기가 포함된 전체 실행 시간으로 계산된 counter rate를
서버의 지속 가능한 TPS로 해석하지 않는다.

## 정확성 검증과 정리

응답마다 다음 7개 항목을 확인한다.

1. HTTP 201
2. 업무 성공
3. 유효한 주문 ID
4. 주문 PENDING 상태
5. 총금액
6. 주문 항목 ID·상품·가격·수량
7. 결제 식별자 존재

실행 후 응답 주문 ID와 DB 주문 소유자를 대조한다.
회원별 주문·항목·결제 건수, 상품·금액·수량·방문일,
주문·결제 상태와 성공 주문 수에 따른 재고 차감을 확인한다.

검증 후 각 소유자의 계정으로 주문을 별도 취소한다.
주문·결제 CANCELLED, 재고 10,000개 복구,
주문·항목·결제 이력 건수 유지를 확인한다.

정리가 끝날 때까지 active-run.json으로 다음 실행을 차단한다.
HTTP 실패나 시간 초과가 주문 미생성을 의미하지 않을 수 있으므로
같은 생성 요청을 무조건 재시도하지 않고 DB와 대조한다.
한 시점의 DB 관측만으로 진행 중인 처리가 없다고 확정하지 않는다.

## 진단 근거와 분석 수정 이력

order-create-burst-2000-diagnostic-01에서 토큰 준비 후 JFR을 시작하고,
k6 종료 직후 중지했다. DB 검증과 취소는 기록 구간에서 제외했다.

- 요청 2,000건 성공, 응답 검증 14,000개 통과
- 전체 호출 P95 8,607.05ms
- MySQL 서버 전체 잠금 대기 증가 1,998회
- MySQL 서버 전체 누적 잠금 대기 시간 증가 65,800ms
- DB 연결 대기 3,937개 이벤트, 평균 396.08ms
- DB 통신 대기 1,880개 이벤트, 평균 33.51ms
- GC 16개 이벤트, 총 소요 시간 280.75ms

DB 연결 대기에서 인증 필터와 주문 생성 서비스 경로가 확인됐다.
상품을 잠근 상태에서 수행하는 작업의 비용을 줄이는 후보를 검토했다.

이벤트 수는 요청 수가 아니며, 여러 스레드의 대기 합계는
실제 실행 시간을 넘을 수 있다. MySQL 카운터는 서버 전체 값이다.
통신 대기에는 SQL 실행·잠금·통신의 영향이 섞인다.
GC 이벤트 소요 시간 합계를 전체 정지 시간으로 해석하지 않는다.

초기 분석은 HTTP 스레드 이름에서 주소를 누락하여 일부 지표를
0개로 잘못 집계했다. 실제 이름을 반영하여 재분석했다.
판단에는 diagnostic-summary-corrected.txt를 사용한다.
초기 요약의 연결·통신 대기와 실행 표본 0개는 사용하지 않는다.

진단 기록이 있는 실행은 성능 비교에서 제외했다.

## 개선 후보와 코드 검증

OrderService.createOrder()의 저장 호출을 변경했다.

- 변경 전: orderRepository.saveAndFlush(order)
- 변경 후: orderRepository.save(order)

명시적 flush를 생략해 추가 동기화 비용을 줄일 수 있다는 가설이다.
트랜잭션, 상품 비관적 잠금, 결제의 동일 트랜잭션 처리는 유지했다.
필수 INSERT나 최종 DB 반영 자체를 제거한 변경은 아니다.

단위 테스트의 저장 메서드 설정·호출 검증을 함께 수정했다.
업무 결과의 검증은 유지했다.

다음 지정 테스트를 실행하여 통과했다.

- OrderControllerTest
- OrderServiceTest
- OrderServiceIntegrationTest
- OrderStockConcurrencyTest
- TicketProductStockConcurrencyIntegrationTest

기존 통합 테스트의 응답 항목 ID·저장된 ID 대조와
결제 생성 실패 시 주문 롤백 검증도 포함한다.
테스트 통과 후 새 JAR을 빌드하고 앱을 재시작했다.

## 판단과 한계

변경 후 세 실행의 P95가 모두 변경 전 세 실행보다 낮았고,
평균·P99 중앙값도 감소했다. 지정 테스트와 부하 후 정확성 검증을
통과하여 현재 실험 범위에서 변경을 유지할 근거가 있다고 판단했다.

- 부하 도구·앱·DB가 같은 Mac의 자원을 공유한다.
- 변경 전과 변경 후를 순서대로 측정했다.
- 실행 시각·예열·공유 자원·누적 DB 이력의 영향이 가능하다.
- 변경 전 측정에서도 실행 순서에 따른 지연 감소가 관측됐다.
- 그룹별 3회로 통계적 유의성이나 인과 효과를 입증한 것은 아니다.
- SQL 횟수나 잠금 유지 시간 감소를 직접 측정하지 않았다.
- 변경 후에도 P95는 약 5.4초로 지연 문제가 모두 해결된 것은 아니다.
- 서버 내부의 정확한 동시 처리 수는 측정하지 않았다.
- 운영 환경 전체 수용 능력·장시간 안정성·외부 결제 성능을 의미하지 않는다.

## 실행 순서

전용 DB와 권한, MySQL·Redis, Java 17, 빌드된 JAR을 먼저 준비한다.
앱 실행 후 Flyway 이력과 대상 DB를 확인한다.
실행마다 기존 이력과 다른 이름을 사용한다.

1. start-app.py로 앱 실행
2. prepare-users.py --users 2000으로 회원 준비
3. prepare-tokens.py --users 2000으로 토큰 준비
4. prepare-run.py 실행이름 --users 2000으로 실행 기준 준비
5. VUS=2000으로 order-create-burst.js를 한 번 실행
6. k6 종료 코드를 exit-code.txt에 저장
7. verify-run.py 실행이름으로 응답·DB 대조
8. 검증 통과 시 cleanup-run.py 실행이름으로 취소·정리

k6 실행 예시는 다음과 같다.
아래 실행 이름은 준비 단계에서 사용한 이름과 일치해야 한다.

    perf_burst_result="$PWD/perf/order-create-burst/results/order-create-example-01"
    caffeinate -i docker run --rm \
      --user "$(id -u):$(id -g)" \
      -v "$PWD/perf:/scripts:ro" \
      -v "$perf_burst_result:/results" \
      -e VUS=2000 \
      grafana/k6@sha256:3e4186aea62e11a45560bfc51e19eeafe82fc07ce069c78aff44b7ff893d9a5e \
      run --out json=/results/metrics.json \
      /scripts/order-create-burst/order-create-burst.js \
      < /dev/null > "$perf_burst_result/console.log" 2>&1
    perf_burst_exit=$?
    printf '%s\n' "$perf_burst_exit" > "$perf_burst_result/exit-code.txt"

준비 도구 실행에도 입력 리디렉션 < /dev/null을 사용한다.
같은 전용 DB에서 다른 부하를 동시에 실행하지 않는다.
실패 시 생성 요청을 재실행하거나 차단 파일을 임의로 삭제하지 않는다.
