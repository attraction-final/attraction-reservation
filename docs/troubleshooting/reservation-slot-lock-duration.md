# KAN-155 예약 생성의 슬롯 잠금 구간 측정과 정원 확보 SQL 감소

## 결과 요약

이미 잠근 슬롯에서 정원을 확보할 때 실행하던 bulk UPDATE와 refresh를 관리 상태 엔티티 변경으로 대체했다.
정원 확보·flush의 SQL은 일반 자리 2→1회, 마지막 자리 3→1회로 줄었다.
로컬 고정 업무 시각의 2,000건 집중 부하에서 변경 전후 각각 두 번 비교했고, 변경 후 API p95와 조회 후 완료 구간 평균이 모두 낮게 관측됐다.

| 항목 | 변경 전 2회 | 변경 후 2회 |
| --- | --- | --- |
| 성공 / 예상 외 오류 | 매회 2,000 / 0 | 매회 2,000 / 0 |
| API p95 | 21.25~22.37초 | 19.11~19.43초 |
| 슬롯 조회 평균 | 90.38~92.37ms | 81.85~82.97ms |
| 조회 후 완료 평균 | 10.61~10.75ms | 9.51~9.64ms |

이는 특정 로컬 조건에서 관측한 결과다. 운영 최대 수용량, 완전한 동시 2,000명 처리, 지연 목표 충족이나 통계적 유의성을 보장하지 않는다.
부하와 테스트는 사용자가 실행했으며, 저장된 결과와 테스트 보고서를 확인해 기록했다.

## 1. 문제와 개선 가설

[KAN-150 진단](reservation-create-load-test.md)에서 슬롯 잠금 대기와 pool pending을 확인했다.
pool 20 단일 비교에서는 지연 개선이 확인되지 않아 pool 10을 유지했다.
중복·시간 충돌 검사의 동등 SQL 실행계획은 선택 회원의 예약 1건 조건에서 인덱스를 사용했다. 이 결과만으로 검사 쿼리를 변경할 근거는 부족했다.

예약 생성은 슬롯 잠금을 얻은 뒤 어트랙션 조회·검증, 중복·시간 충돌 검사, 정원 확보와 예약 저장을 수행한다.
같은 슬롯의 요청이 기다리는 시간을 줄이기 위해, 잠금 보호를 유지하면서 이 구간의 DB 왕복을 줄이는 것을 가설로 삼았다.
정원 확보 작업 자체의 시간은 별도 Timer로 분리하지 않았고, SQL 수 감소를 통합 테스트로 확인한 뒤 전체 구간과 API 지연을 비교했다.

## 2. 측정 구간 정의

| 지표 | result | 의미 |
| --- | --- | --- |
| reservation.create.slot.lookup | success / failure | 슬롯 조회 직전부터 반환 또는 예외까지. 잠금 대기·SQL 실행·엔티티 조회 포함 |
| reservation.create.slot.postlookup | committed / rolledback / unknown | 조회 지표 기록 직후부터 트랜잭션 afterCompletion callback까지 |
| reservation.create.attraction.lookup | success / failure | 어트랙션 잠금 조회 호출 구간. postlookup 내부에 포함 |

- Timer 평균은 같은 result의 시작 전후 sum 차이 / count 차이로 계산한다. Prometheus 시간 단위는 초다.
- 조회 Timer는 finally에서 기록하므로 예외 경로도 집계한다. 조회 성공은 예약 성공과 다르다.
- postlookup은 실제 DB 잠금 보유 시간 자체가 아니다. 조회 반환과 실제 잠금 획득, callback과 DB 잠금 해제 시점에는 차이가 있다.
- 메서드 반환이나 flush를 commit 완료로 취급하지 않는다. 바깥 트랜잭션이 rollback되면 rolledback으로 기록한다.
- 어트랙션 조회 시간과 postlookup을 합산하면 중복 계산이다. 내부 Timer에는 histogram/percentile을 설정하지 않아 구간 p95/p99를 제공한다고 가정하지 않는다.
- API 전체 지연과 내부 구간 차이를 전부 슬롯 잠금 또는 pool 대기로 설명하지 않는다.

## 3. 재현 환경과 업무 시각

| 항목 | 조건 |
| --- | --- |
| 서버 | 2 CPU, 메모리 1GiB, heap 256~512MiB |
| MySQL / Redis | 1 CPU·1GiB / 0.5 CPU·256MiB |
| Hikari | max/min 10/10 |
| 측정 k6 | 2 CPU, 메모리 2GiB |
| 요청 | 서로 다른 회원 2,000명, 회원당 예약 생성 1회 |
| 집중 슬롯 | 정원 2,000, 21:50~22:00 |
| 준비 | 실행마다 앱 재생성, warm-up 없음, setup 순차 로그인 |
| 발송 | scenario 시작 +5초 목표, 실제 호출 시작 범위와 늦은 VU 별도 확인 |
| 관측 | 구간 Timer, Hikari·CPU 등, Performance Schema 잠금 표본 |
| 업무 시각 | 2026-11-10T14:00:00+09:00으로 고정 |

야간에도 예약 생성 검증을 실행할 수 있도록 java.time.Clock을 주입했다.
기본 ClockConfig는 실제 KST를 제공하고, reservation-create-perf-time profile에서만 고정 Clock을 우선 주입한다.
실행기에 PERF_FIXED_TIME을 명시한 경우에만 전용 Compose overlay를 사용하고, SQL 방문일·슬롯·티켓 날짜도 같은 날짜로 맞춘다.
설정하지 않으면 실제 시각 모드와 기존 실행 시간 제한을 유지한다.

고정 Clock은 Clock 주입을 받는 구성요소에 우선 적용된다. 전용 부하 환경에서만 사용하고 기존 스케줄러 비활성화를 유지한다.
JWT·로그·Micrometer 경과 시간·SQL Auditing 시각은 실제 시간이다. KstTime.now()를 직접 쓰는 취소 등 다른 API까지 고정한 구성은 아니다.
고정 시각은 흐르지 않으므로 마감 경과·자정 경계 검증과 구분한다. 설정 격리·정상 값·누락·잘못된 형식은 별도 테스트로 확인했다.
고정 모드 50명 확인 실행 fixed155-01은 성공 50·예상 외 0, DB 정합성과 세 지표 각각 50회 기록을 확인했다.

## 4. 개선 전후 SQL 확인과 구현

### SQL 예산 테스트

AttractionSlotCapacityQueryIntegrationTest는 실제 MySQL 8.4에서 같은 트랜잭션으로 슬롯 잠금을 먼저 얻는다.
그 뒤 정원 확보 호출과 flush의 SQL만 센다. fixture 준비, 초기 잠금 SELECT와 검증용 재조회는 제외한다.
예약 INSERT를 포함한 전체 예약 생성 SQL 수가 아니라는 점에 주의한다.

| 인원 변화 | 변경 전 | 변경 후 |
| --- | --- | --- |
| 0→1 | 조건부 UPDATE + refresh: 2회 | 1회 |
| 8→9 | 조건부 UPDATE + refresh: 2회 | 1회 |
| 9→10 | 조건부 UPDATE + refresh + 자동 마감 UPDATE: 3회 | 1회 |

개선 전 8개 테스트 중 SQL 수 assertion 3개만 실패했다. 그 전에 확인한 인원·상태는 맞았고, 예약 불가 상태·정원 초과·rollback 검증은 통과했다.
개선 후 세 SQL 수 검증을 포함한 8개가 통과했고, 트랜잭션 부재·쓰기 잠금 부재 거부까지 보강한 10개도 통과했다.

### 변경한 처리

| 대상 | 역할 |
| --- | --- |
| AttractionSlot.acquireReservationCapacity() | OPEN·잔여 정원 검사 → 인원 증가 → 자동 마감 동기화 |
| AttractionSlotService.tryReservationCapacity() | 기존 트랜잭션 필수 → 관리 상태 슬롯 조회 → 보유 잠금 검사 → 엔티티 변경 |
| ReservationService.createReservation() | 기존 회원·슬롯·어트랙션 잠금 순서와 잠금 이후 시각 검증 유지 |

서비스는 Propagation.MANDATORY를 사용한다. 이것만으로 잠금을 보장하는 것은 아니므로 보유 모드도 검사한다.
같은 영속성 컨텍스트의 잠긴 엔티티를 재사용해 dirty checking으로 반영하며 정원 확보 경로의 bulk UPDATE·refresh를 제거했다.
취소의 정원 복구 경로는 이번 개선에서 변경하지 않았다. BR-RSV-30은 비관적 잠금 방식의 정원 보호를 허용한다.

## 5. 회귀 중 발견한 잠금 모드 문제

첫 동시성 회귀에서 예약 생성·마감 경계·슬롯 변경은 통과했지만, 취소 동시성 6개는 준비 단계에서 실패했다.
그 테스트는 새 슬롯 INSERT·flush와 예약 두 건 생성을 같은 트랜잭션에서 수행했다.
임시 spy로 슬롯 조회 직후와 정원 확보 직전 상태를 확인한 결과, 두 시점 모두 다음과 같았다.

| 관측 항목 | 값 |
| --- | --- |
| 관리 상태 | true |
| JPA 모드 | PESSIMISTIC_FORCE_INCREMENT |
| Hibernate 내부 모드 | WRITE |
| Hibernate 버전 | 7.4.5.Final |

Hibernate는 같은 트랜잭션에서 INSERT·UPDATE한 엔티티를 내부 WRITE 모드로 관리한다. [공식 설명](https://docs.hibernate.org/orm/7.4/javadocs/org/hibernate/LockMode.html#WRITE)
PESSIMISTIC_WRITE와 정확히 같은 값만 허용한 검사가 이 경로를 거절했다.
검사에서 PESSIMISTIC_WRITE와 PESSIMISTIC_FORCE_INCREMENT를 허용하고, NONE·낙관적 잠금·PESSIMISTIC_READ 등은 계속 거절하도록 보완했다.
Repository가 새로 강제 버전 증가 잠금을 요청하도록 바꾼 것은 아니다. 실제 요청은 기존 PESSIMISTIC_WRITE를 유지했다.
테스트 준비 흐름과 보호 잠금은 유지했고, 진단용 spy·출력은 원인 확인 후 제거했다.

보완 후 잠금 검사 단위 테스트 13개와 취소 동시성 6개가 통과했다.
진단 제거 후 최종 회귀는 예약 생성 8개·취소 경합 6개·마감 경계 5개·슬롯 변경 경합 10개, 총 29개가 통과했다.

## 6. 집중 부하 전후 비교

모든 실행에서 성공 2,000·거절/예상 외 0, DB 예약·서로 다른 예약 회원·인원·정원 모두 2,000이었다.
시작 전 구간 지표는 없었고 종료 후 세 지표의 success 또는 committed count는 각각 2,000이었다.

| 실행 | API 평균 / p95 / p99 | 슬롯 조회 평균 | 조회 후 완료 평균 | 어트랙션 조회 평균 | 발송 범위 |
| --- | --- | --- | --- | --- | --- |
| 변경 전 fixed155-02 | 12.78 / 21.25 / 21.96초 | 90.38ms | 10.61ms | 1.03ms | 334ms |
| 변경 전 fixed155-03 | 13.85 / 22.37 / 23.06초 | 92.37ms | 10.75ms | 1.00ms | 320ms |
| 변경 후 opt155-01 | 11.51 / 19.11 / 19.64초 | 81.85ms | 9.51ms | 1.01ms | 295ms |
| 변경 후 opt155-02 | 11.54 / 19.43 / 19.99초 | 82.97ms | 9.64ms | 1.03ms | 275ms |

늦은 VU는 모두 0이었다. 변경 후 실행에서도 pool pending 최대 190과 슬롯 경합은 남아 있다.
SQL 감소와 낮은 지연이 두 번 관측됐지만, 순서가 변경 전→변경 후이고 호스트 편차·데이터 누적·warm-up 부재·표본 수의 영향을 배제한 실험은 아니다.
실제 DB 잠금 보유 시간을 직접 측정한 개선율이나 전체 서비스의 성능 향상률로 표현하지 않는다.

| JAR 구분 | SHA-256 |
| --- | --- |
| 변경 전 | eb5fda0f3e91ae150f8d66a00d2d076710f12a4661b88391fbcb55a5ce7ae85c |
| 변경 후 | 39a826287e80836a38cd6f8b94c9d8e07ad1f31c59e4a346e460dcc33a667def |

실행별 metadata에는 JAR·도구 해시, 실제 자원, 고정 시각과 작업 트리 상태를 남긴다. 변경 전후 JAR이 다르며, 운영 부하나 KAN-150 실제 시각 모드와 동일 조건으로 취급하지 않는다.

## 7. 변경 후 매진·분산 회귀

| 항목 | full155-01 매진 | spread155-01 분산 |
| --- | --- | --- |
| 요청 / 성공 / 정상 거절 / 예상 외 | 2,000 / 20 / 1,980 / 0 | 2,000 / 2,000 / 0 / 0 |
| DB 정합성 | 슬롯 예약·회원·인원·정원 모두 20 | 5개 슬롯 각각 400, 전체 예약·회원 2,000 |
| API 성공 평균 / p95 / p99 | 1.46 / 1.64 / 1.65초 | 9.72 / 16.55 / 16.98초 |
| 정상 거절 평균 / p95 / p99 | 6.86 / 11.07 / 11.33초 | 해당 없음 |
| 슬롯·어트랙션 조회 success count | 각각 2,000 | 각각 2,000 |
| postlookup committed / rolledback count | 20 / 1,980 | 2,000 / 0 |
| 발송 범위 / 늦은 VU | 268ms / 0명 | 247ms / 0명 |

슬롯 자동 마감과 정원 유지도 확인했다. 매진의 rolledback은 예상된 업무 거절이며 서버 오류 1,980건을 뜻하지 않는다.
분산의 구간 평균은 슬롯 조회 35.57ms·어트랙션 조회 4.34ms·조회 후 완료 30.44ms였다.
여러 슬롯의 트랜잭션이 병행되므로 구간 평균을 집중 조건과 같은 직렬 시간으로 해석하거나 합산하지 않는다.
두 실행은 각 1회 회귀 확인이다. 동일 고정 시각의 변경 전 매진·분산 기준값이 없어 개선율을 계산하지 않는다.
기록한 부하 실행 모두 준비·HTTP·DB·수집·정리 종료 코드가 0이었고 오류 파일은 비어 있었으며 커넥션 timeout·k6 OOM은 없었다.

## 8. 완료 범위와 후속 과제

이번 범위는 정합성 보호를 유지한 정원 확보 SQL 감소와 로컬 집중 부하 전후 관측까지다.
프로젝트 전체 테스트·CI·운영 성능 검증이 완료됐다고 주장하지 않는다. 사용자 실행으로 확인한 테스트와 부하 결과만 기록했다.
원시 로그는 results의 무시 대상 파일로 남고, 이 문서에는 핵심 수치·조건·한계만 정리한다.

| 후속 검증 | 남긴 이유 |
| --- | --- |
| 프로젝트 전체 테스트·CI | 이번에는 관련 테스트와 부하 중심으로 확인 |
| 실제 시각 모드의 개선 후 비교 | 효과 비교는 고정 업무 시각 모드에서 수행 |
| 기존 예약이 많은 회원·혼합 API | 부하 fixture는 새 회원이며 취소 등과 섞인 장시간 HTTP 부하는 미검증 |
| 장시간 지속 부하·회복 시간 | 짧은 burst와 기능 회귀는 장시간 안정성을 보장하지 않음 |
| 추가 반복·실행 순서 교차 | 현재 변경 전후 각 2회로 호스트·순서 영향을 분리하기 어려움 |
| 지연 목표 설정 | 성공·정상 거절의 허용 지연은 미설정 |

실행 방법과 지표 수집 위치는 [부하 도구 README](../../perf/reservation-create/README.md)를 따른다.
