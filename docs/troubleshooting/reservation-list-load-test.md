# 내 예약 목록 HTTP 부하 테스트와 측정 기록

> **KAN-134** · 회원 200명·예약 100,000건의 전용 환경을 구성했다. smoke 회귀를 거쳐 **10 VUs·60초의 첫 측정에서 목록 1,190건·check 5,951회가 모두 통과**했다. 성능 합격 기준은 설정하지 않았으며, 자원 수집 보강 후의 실행과 병목 분석은 남아 있다.

## 1. 목적과 현재 범위

[N+1 해결](reservation-list-n-plus-one.md)과 [회원 목록 인덱스 분석](reservation-list-index.md) 이후,
실제 HTTP 요청에서 인증·Service·Repository·DTO 직렬화가 함께 동작하는지 확인하는 단계를 마련했다.
DB 실행 계획의 개선을 HTTP 처리량 개선으로 바로 간주하지 않고, API 기준의 별도 실험을 진행하려는 목적이다.

| 현재 확인한 것 | 아직 확인하지 않은 것 |
| --- | --- |
| 실제 Spring Security를 거친 조회와 미인증 접근 차단 | 전체 API 권한 정책 |
| 회원별 예약 ID·정렬·상태 필터·페이지·건수·일부 DTO 필드 | 모든 날짜·페이지·정렬 조건 |
| smoke와 첫 10 VUs 측정의 응답 시간·오류 여부 | 더 높은 부하에서의 변화·장시간 안정성·성능 목표 충족 여부 |
| 준비부터 실행·결과 저장까지 자동화 | 운영 수용량과 최대 처리량 |

## 2. 실행 구성과 선택 이유

Python 보조 스크립트를 참고해 시작했지만 현재 PC에 Python 실행 환경이 없었다.
Node.js로 대체한 뒤, 추가 runtime 설치 없이 팀원이 재현할 수 있도록 **Docker + k6 + SQL + Git Bash 실행기**로 정리했다.
보조 언어 변경 자체를 애플리케이션 성능 개선으로 기록하지 않는다.

| 구성 | 역할 |
| --- | --- |
| 전용 Compose | 앱·MySQL·Redis·k6를 기존 개발 환경과 분리 |
| 준비용 k6 | 실제 회원가입·CSRF·로그인으로 테스트 계정 생성/재사용 확인 |
| MySQL client 컨테이너 | SQL로 합성 이력 생성 또는 기존 fixture 검증, 응답 기대 결과 추출 |
| 측정용 k6 | setup에서 실제 로그인 → VU별 목록 조회 → 집계 결과 저장. smoke는 2명, load는 10명 |
| Git Bash `run.sh` | 위 작업을 순서대로 실행하고 메타데이터·전후 메트릭·종료 코드 기록 |

Node.js·Python·host의 MySQL client는 필요하지 않다. k6의 JavaScript는 k6 자체 runtime에서 실행한다.
회원 준비용 실행은 실제 목록 smoke와 분리했다. 토큰 발급은 측정 전 setup에서 수행하며 목록 전용 Trend에는 포함하지 않는다.
실행 방법은 [테스트 README](../../perf/reservation-list/README.md)에 정리했다. 팀원의 `perf/order-list`는 변경하지 않았다.

## 3. 검증 조건

| 항목 | 조건 |
| --- | --- |
| 실행 ID·기록 시각 | `smoke-03`, 2026-11-09 13:28:02 KST (실행기 메타데이터 기록 시각) |
| 기준 HEAD | `c8d04337b7d9cfb6d5facb6d4800a9b8d75289ba`, 새 테스트 파일은 당시 미커밋 |
| 환경 | Docker, Java 17 JRE 이미지, MySQL 8.4.11, Redis, 고정 digest의 k6 이미지 |
| 스키마 | Flyway 적용, Hibernate validate. 회원·상태·ID 및 상태·ID 인덱스 존재 확인 |
| 데이터 | 회원 200명, 예약 100,000건, 슬롯 500개, 시설 10개 |
| 분포 | 회원별 500건, RESERVED·COMPLETED·CANCELLED·NO_SHOW 각 125건 |
| 요청 | `GET /api/reservations/me?page=0&size=10`, 동일 요청의 `status=RESERVED` 조건 |
| 기본 정렬 | status DESC, id DESC |
| 실행량 | 서로 다른 회원 2명, 2 VUs × 5 iterations × 2조건 = 목록 20건 |
| 대기·warm-up | iteration마다 1초 대기. 목록 전용 warm-up 구간은 없음 |
| 앱 제한 | CPU 1개, 메모리 1GiB, JVM heap 256~512MiB, Hikari 최대 10개 |
| MySQL·Redis·부하용 k6 제한 | CPU 각각 1 / 0.5 / 1개, 메모리 1GiB / 256MiB / 512MiB |

SQL로 만든 조회용 합성 이력이다. 실제 서비스의 사용자 이력 분포를 대표하지 않으며, 예약 생성·결제·환불 업무 검증용도 아니다.
기존 100,000건은 삭제하지 않고 구조·건수를 확인해 재사용했다. Generated Column에 직접 값을 넣지 않는다.
쓰기 스케줄러를 비활성화했으며, 앱·DB·k6는 같은 PC의 Docker 자원을 공유한다.

## 4. 실행 중 발견한 문제와 조치

| 항목 | 확인 사실 | 조치·검증 상태 |
| --- | --- | --- |
| `smoke-02` 준비 후 중단 | fixture 기대 결과는 만들어졌지만 metadata의 gitHead가 비었고 k6 결과·종료 코드가 없었음. 전역 `MSYS_NO_PATHCONV=1` 때문에 Git이 `/d/...` 경로를 찾지 못하는 오류를 읽기 전용 명령으로 재현 | 경로 변환 예외를 Docker 명령에만 적용하고 Git은 프로젝트 디렉터리로 이동해 실행. 이후 `smoke-03`에서 끝까지 완료 |
| summary에 토큰 저장 | `handleSummary(data)`가 받은 객체에 `setup_data`도 포함돼, 객체 전체를 JSON으로 저장하면 로그인 토큰이 함께 저장됨 | 집계 필드 4개만 저장하도록 수정. `smoke-03`의 해당 필드는 제거하고 측정값은 유지. 이후 `smoke-04`에서 통과 및 저장 파일의 setup_data·토큰 필드·JWT 패턴 미검출을 확인 |

설정·저장 문제와 애플리케이션의 성능 문제를 구분한다. 준비 중 중단된 `smoke-02`를 API 실패율에 포함하지 않는다.
기존 결과를 덮어쓰지 않고 새로운 RUN_ID로 재실행한다.

## 5. smoke 결과

사용자가 실행한 로컬 결과의 종료 코드와 summary·metadata를 직접 확인했다. 별도 테스트를 대신 실행한 것은 아니다.

| 검증 항목 | 결과 |
| --- | ---: |
| k6 종료 코드 | 0 |
| 목록 요청 | 전체 10건 + RESERVED 10건 = 20건 |
| 전체 HTTP 요청 | 25건 (목록 20 + 미인증 1 + 두 회원의 CSRF·로그인 4) |
| check | 101회 통과, 실패 0 |
| 목록 HTTP 오류율·응답 불일치율 | 각각 0% |
| 실패한 threshold | 0개 |

검증은 HTTP 200, 공통 성공 응답, 첫 페이지와 전체 건수, 회원별 예약 ID·정렬·DTO 매핑, 상태 필터를 포함한다.
DTO 비교 항목은 reservationId·reservationNumber·slotId·attractionName·ticketId·status이며 날짜 필드 전체까지 비교한 것은 아니다.
기대 결과는 API 응답을 복사하지 않고 SQL에서 별도로 추출했다. 미인증 접근은 예상대로 401이었다.

### 목록 전용 응답 시간

| 조회 조건 | 요청 수 | 평균(ms) | 중앙값(ms) | p95(ms) | p99(ms) | 최댓값(ms) |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 전체 | 10 | 26.86 | 15.91 | 69.08 | 69.11 | 69.12 |

조건별 `reservation_list_all_duration`, `reservation_list_reserved_duration` 값이며 단위는 ms다.
전체 기본 HTTP Trend에는 setup 요청이 포함되므로 목록 지표와 혼용하지 않는다.
관측한 목록 요청률은 약 3.67 req/s지만 2 VUs·1초 대기를 포함한 값이므로 최대 처리량으로 해석하지 않는다.

실행 후 Hikari active·pending·timeout_total은 모두 0이었다. 전후 snapshot만 있으므로
실행 중 대기가 한 번도 없었거나 최대 사용량이 0이었다는 뜻은 아니다.

## 6. 첫 부하 측정: load-01

같은 데이터와 jar에서 목록 warm-up을 별도 k6 프로세스로 수행한 후 측정했다.
실행기 기록은 **2026-11-09 14:42:15 KST**, warm-up 시작 기록은 **14:42:19**, 측정 시작 기록은 **14:42:42**다.
기준 HEAD는 `bbba4c632e9759d7f26ab9e13e0fa2413a933452`이며 당시 부하 프로필 변경은 미커밋이었다.

| 항목 | 조건 |
| --- | --- |
| 모델 | constant-vus의 닫힌 모델, 서로 다른 회원 10명 |
| 요청 | iteration마다 전체·RESERVED 각 1회 후 1초 대기 |
| warm-up / 측정 | 20초 / 60초, 각 구간의 진행 중 iteration에 최대 25초 완료 대기 |
| 데이터 | 총 100,000건, 요청 회원별 500건, 각 상태 125건 |
| 기능 기준 | 응답 check 전체 통과, HTTP 오류율·응답 불일치율 0 |
| 성능 기준 | 미설정. metadata의 p95Ms=unset |
| 수집 범위 | k6 집계와 앱 Prometheus 전후 snapshot. 자원 연속 수집은 이 실행에 없었음 |

### 실행 결과

| 항목 | warm-up | 실제 측정 |
| --- | ---: | ---: |
| 목록 요청 | 400건 (조건별 200건) | 1,190건 (조건별 595건) |
| check | 2,001회 통과·실패 0 | 5,951회 통과·실패 0 |
| HTTP 오류·응답 불일치 | 0건 | 0건 |
| 실패한 threshold | 0개 | 0개 |
| 종료 코드 | 0 | 0 |
| k6가 기록한 실행 시간 | 약 21.37초 | 약 61.63초 |
| 관측 목록 요청률 | 약 18.72 req/s | 약 19.31 req/s |

실행 시간과 요청률에는 k6의 setup·완료 대기 등의 영향도 있으므로 설정한 duration과 정확히 같지 않다.
warm-up의 요청 수와 시간 분포를 측정 구간에 합산하지 않았다. check에는 미인증 401 확인 1회가 포함된다.
두 결과 JSON의 최상위 필드는 집계용 4개였으며, 저장 파일에서 setup_data·토큰 필드·JWT 패턴 검출은 0건이었다.

### 조건별 응답 시간

| 구간 | 조건 | 평균(ms) | 중앙값(ms) | p95(ms) | p99(ms) | 최댓값(ms) |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| warm-up | 전체 | 10.96 | 7.61 | 15.67 | 72.79 | 101.20 |
| warm-up | RESERVED | 15.34 | 7.33 | 85.49 | 100.56 | 152.86 |
| 측정 | 전체 | 7.26 | 6.72 | 12.32 | 17.03 | 25.83 |
| 측정 | RESERVED | 8.03 | 6.53 | 10.20 | 65.15 | 77.29 |

측정에서 RESERVED의 p99가 p95보다 높았다는 관측은 남긴다. 요청별 시각·자원 사용을 연결한 자료가 없어 GC나 DB 대기를 원인으로 단정하지 않는다.

### 전후 메트릭의 해석 범위

| 항목 | 전 → 후 | 확인할 수 있는 것·한계 |
| --- | --- | --- |
| Hikari timeout_total | 0 → 0 | 두 snapshot 사이 해당 pool timeout counter 증가는 없음 |
| Hikari active / pending | 각각 0 → 0 | 시작·종료 근처 관측값. 실행 중 최대 사용량이나 대기 부재의 근거는 아님 |
| minor GC count | 16 → 23 | snapshot 사이 7회 증가 |
| minor GC pause 합계 | 0.508 → 0.545초 | snapshot 사이 약 37ms 증가. 특정 API의 지연 원인으로 연결할 수는 없음 |

snapshot 사이에는 측정용 setup 로그인 등도 포함된다. GC 증가를 목록 요청만의 비용으로 해석하지 않는다.
프로세스 CPU의 전후 순간값만으로 구간 평균·최댓값이나 병목을 확정하지 않는다.

## 7. 현재 판단과 다음 실험

**확인된 결론:** 실제 인증을 거친 smoke와, 이번 10 VUs·60초 조건의 첫 측정에서 기능 검증이 통과했다.
데이터 100,000건 전체를 한 번에 반환한 것이 아니라, 그 데이터에서 회원별 첫 페이지 10건을 요청했다.

**아직 내릴 수 없는 결론:** 최적화 효과의 비율, 동시 접속 수용량, 운영 SLO 충족 여부, 병목 원인.
첫 부하 측정은 1회뿐이며, 반복 측정과 연속 자원 수집 없이 병목을 확정하지 않는다.
warm-up을 분리했어도 계정 준비의 로그인·캐시·JIT·같은 PC의 다른 작업 영향을 완전히 통제한 것은 아니다.
기존 Node.js 실행과 응답 시간이 달라졌어도 보조 실행 방식 변경의 성능 효과로 주장하지 않는다.

| 단계별 부하 | 여러 실제 테스트 계정에 요청을 분산하고 동일 조건으로 반복 |
| 병목 근거 | 다음: 앱·DB·k6의 CPU/메모리, GC, pool 대기를 주기적으로 수집. SQL 비용 분석은 후속 범위 |
| 비교·기록 | 같은 환경·데이터·부하·warm-up 조건의 개선 전후와 변경 비용을 함께 기록 |

### 주기적 자원 수집 보강 (코드 작성, 아직 미실행)

첫 측정의 전후 snapshot 한계를 보완하기 위해 host의 Git Bash에서 `sample-resources.sh`를 병렬 실행하도록 추가했다.
별도 Python·Node.js·모니터링 서버는 필요하지 않으며, 부하 조건은 우선 그대로 유지한다.

| 항목 | 보강 내용 |
| --- | --- |
| 대상 구간 | warm-up 종료 후, 측정용 k6 기동 직전부터 완료까지 |
| 간격 | 처리 시간을 포함해 목표 2초. 실제 간격은 기록 시각으로 확인 |
| Docker 지표 | 앱·MySQL·Redis·측정용 k6의 CPU, 메모리/제한, 네트워크·블록 I/O, PIDs |
| 앱 메트릭 | Hikari 연결 수·pending·timeout, JVM 메모리·GC, 프로세스 CPU·uptime, HTTP 지표 |
| 식별 | 주기 번호·시작/종료 시각, 측정 k6 실행 여부 |
| 수집 품질 | 별도 오류 파일·수집 프로세스 종료 코드. API 통과와 수집 성공을 구분 |
| 종료 처리 | 부하 종료 또는 실행기 종료 시 수집 중단을 요청하고 프로세스 회수 |

다음은 새 RUN_ID에서 같은 10 VUs 조건으로 재실행해 수집 파일의 정상 생성과 관측 범위를 먼저 확인한다.
관측 최대값은 표본 중 최대값이며 실제 순간 최대값이 아니다. k6 시작/종료 경계에는 컨테이너 표본이 없을 수 있다.
scrape와 Docker stats도 동시에 실행되는 것은 아니며, 수집기 자체가 같은 PC의 CPU·I/O를 사용한다.
수집 없는 load-01과의 시간 차이를 앱 코드 변경의 개선 효과로 주장하지 않는다. 이 보강의 실제 실행 결과는 아직 없다.

실행 원본은 Git에서 제외되는 `perf/reservation-list/results/`에 두며, 저장소에는 이 문서의 핵심 조건·지표·판단만 남긴다.
토큰·인증 헤더·전체 요청/응답 원문을 문서에 포함하지 않는다. 이후 실험 결과는 이 문서에 이어서 갱신한다.
