# 주문 목록 부하 테스트 및 복합 인덱스 실험

## 목적과 범위

`GET /api/orders/me`의 응답 정확성과 응답 시간을 측정하고,
회원별 최신순 조회에 맞춘 복합 인덱스의 효과를 검토한다.

- 실제 HTTP 부하와 측정: Docker k6
- 데이터 준비·로그인·실행·결과 저장: Python 보조 스크립트
- 적용 범위: 개인 테스트 환경
- 공유 DB 적용과 애플리케이션 조회 코드 변경은 포함하지 않는다.

주문 목록 외 API의 부하 테스트나 주문 생성·결제·환불 업무를
검증하는 도구가 아니다.

## 준비 사항

- macOS 및 Docker Desktop
- Java 17
- Python 3
- 저장소 루트에서 명령 실행

앱 실행기는 `JAVA_HOME`을 우선 사용하고, 없으면 `PATH`에서
Java를 찾는다. Java 17이 아니면 실행을 중단한다.
다른 운영체제에서의 실행은 별도 검증하지 않았다.

## 개인 테스트 환경

| 구성 | 설정 |
|---|---|
| Spring Boot | 호스트 실행, `127.0.0.1:18086` |
| JVM 힙 | 초기 256MB, 최대 512MB |
| DB 커넥션 풀 | 최대 10개 |
| MySQL | 전용 Compose, `127.0.0.1:13316` |
| DB 이름 | `attraction_perf` |
| Redis | 전용 Compose, `127.0.0.1:16396` |
| k6 | Docker 이미지 digest 고정 |

앱 실행 시 실제 서비스 환경변수를 상속하지 않는다.
설정 파일의 인증 관련 값은 로컬 테스트용이다.
PG 주소는 로컬 비수신 포트이며 실제 결제를 호출하지 않는다.

웹훅·보상·환불·주문 취소 스케줄러는 비활성화한다.
티켓 만료 스케줄러는 24시간 간격이며 대상 티켓 데이터가 없다.

Hibernate의 `update`는 신규 개인 테스트 DB의 스키마 준비에만
사용한다. 공유 DB의 배포 방법을 변경하지 않는다.

## 테스트 데이터와 요청 시나리오

### 데이터

- 최초 준비 기본값: 회원 20명, 회원별 주문 1,000건
- 실제 인덱스 비교 측정: 회원 100명, 총 주문 100,000건
- 주문은 조회용 합성 COMPLETED 데이터
- 주문 항목·결제·티켓은 포함하지 않음
- 생성 시각이 같은 주문을 포함해 주문 ID 보조 정렬도 검증

회원별 주문 1,000건이라는 분포는 실험 조건이다.
실제 서비스의 일반적인 회원 주문 이력을 대표한다고 가정하지 않는다.

### 요청

- VU마다 서로 다른 회원 계정 사용
- 페이지당 10건
- 첫·중간·마지막 페이지 순환
- 응답을 받은 뒤 기본 1초 대기
- 부하 모드는 일정한 VU 수를 유지하는 닫힌 모델
- 사용 가능한 VU 수는 준비된 계정 수 이하
- 지원 측정 시간: 30초, 60초, 90초

로그인은 측정 전에 수행한다.
시작 전 토큰 유효기간과 미인증 요청의 401 응답을 확인한다.
미인증 확인 요청 1건은 전체 HTTP 요청 수에는 포함되지만,
`order_list_duration`에는 포함되지 않는다.

### 응답 검증

- HTTP 200
- 업무 성공 여부
- 페이지 정보와 전체 주문 수
- DB 기준 주문 ID와 정렬 순서
- 금액과 주문 상태

자동 통과 기준은 응답 정확성이다.
응답 시간에 대한 성능 합격 기준은 아직 설정하지 않았다.

## 실행 방법

### 1. 개인 환경 시작

```bash
docker compose -f perf/order-list/compose.yaml up -d --wait
bash gradlew bootJar --console=plain
python3 perf/order-list/start-app.py
```

이미 18086 포트에서 앱이 응답하면 중복 실행을 거부한다.
앱 로그와 PID는 `.local/`에 저장한다.

### 2. 최초 데이터 준비

신규 개인 DB에서 한 번만 실행한다.

```bash
python3 perf/order-list/prepare.py --seed --users 100 --orders-per-user 1000
```

기존 주문이 있으면 최초 생성을 거부한다.
DB를 자동 초기화하거나 기존 데이터를 삭제하지 않는다.

기본값으로 준비한 20명 데이터를 100명까지 확장하려면:

```bash
python3 perf/order-list/prepare.py --extend --users 100 --orders-per-user 1000
```

이미 지정한 주문 수를 가진 대상 회원은 유지한다.
기존 주문 수가 0건 또는 지정한 건수와 다르면 중단한다.
여러 단계로 추가하므로 전체 작업이 하나의 트랜잭션은 아니다.
실패하면 저장 상태를 확인한 뒤 재실행 여부를 판단한다.

### 3. 소규모 확인과 부하 측정

```bash
python3 perf/order-list/run.py smoke-01
python3 perf/order-list/run.py baseline-01 --mode load --vus 100 --duration 60s
```

소규모 모드는 기본 2 VU가 각각 5회 반복한다.
부하 모드는 지정한 시간 동안 반복한다.

실행 ID는 매번 다르게 지정한다.
같은 이름의 결과 폴더가 있으면 덮어쓰지 않고 중단한다.
매 실행 전에 로그인 토큰과 DB 기준 예상 결과를 갱신한다.

## 복합 인덱스 실험

적용 SQL은 `index-order-list.sql`에 보관한다.

```sql
CREATE INDEX idx_orders_user_created_id
ON orders (user_id, created_at DESC, id DESC);
```

- 개인 테스트 DB에 수동 적용한다.
- 애플리케이션에서 자동 실행하지 않는다.
- 실행 전 기존 인덱스를 확인한다.
- 같은 이름의 인덱스가 있으면 다시 생성하지 않는다.
- 공유 DB 적용은 별도 검토한다.

전후 비교 시 데이터·서버 설정·요청 시나리오를 유지하고,
준비 절차를 맞춘 뒤 각 조건에서 반복 측정한다.
준비 실행은 비교 측정과 구분해 보관한다.

`EXPLAIN ANALYZE`도 실제 SELECT를 실행하므로 캐시에 영향을 준다.
실행 계획 수집 순서 역시 전후에 맞춰야 한다.

## 수행한 실험과 해석

- 초기 준비 코드 기준: `10759c4`
- 실제 전후 측정의 서버 코드 기준: `49b39a1`
- 데이터 확장: 회원 100명, 주문 100,000건
- 부하 조건: 100 VU, 60초, 응답 후 1초 대기
- 적용 전·후 각각 세 번의 비교 측정 수행
- 인덱스는 개인 테스트 DB에만 적용

실행 계획에서 세 페이지 모두 별도 Sort 단계가 제거됐다.
실제 읽은 행 수는 다음과 같다.

| 페이지 | 적용 전 | 적용 후 |
|---|---:|---:|
| 첫 페이지 | 1,000 | 10 |
| 중간 페이지 | 1,000 | 510 |
| 마지막 페이지 | 1,000 | 1,000 |

API 측정에서도 적용 후 응답 시간이 낮게 관측됐다.
그러나 실제 실험은 전후 측정일과 준비 절차가 달라,
인덱스만의 효과를 확정한 결과로 해석하지 않는다.

## 결과 파일

결과는 `results/<실행 ID>/`에 저장한다.

| 파일 | 의미 |
|---|---|
| metadata.json | 코드·도구 버전, 실행 조건, 시작·종료 시각 |
| fixture.json | 회원별 주문 수와 검증 페이지의 예상 ID |
| summary.json | 최종 지표. 주문 목록 응답 시간은 `order_list_duration` 사용 |
| metrics.json | 시간대별 k6 원본 지표 |
| terminal.txt | 실행 출력 |
| dashboard.html | HTML 보고서. 짧은 실행에서는 생성되지 않을 수 있음 |
| db-before.txt | 데이터 수, 스키마와 인덱스 |
| plans-before.txt | 조회 계획의 보조 재현 자료 |
| sql-digests-before/after.txt | 누적 SQL 통계의 전후 스냅샷 |
| resource-samples.jsonl | DB·Redis 컨테이너와 앱 프로세스 자원 표본 |

`plans-before.txt`는 각 실행 직전의 계획을 뜻한다.
인덱스 적용 후 실행이라면 적용된 인덱스가 반영된다.
실제 앱 SQL은 SQL digest와 대조한다.

SQL 통계는 누적값이므로 전후 차이를 계산해 사용한다.
자원 표본은 JVM GC·힙·DB 연결 대기 전체를 수집한 자료가 아니다.
metadata의 JVM·커넥션 풀 값은 기본 실행 설정을 기록한 것이며,
실행 중인 서버에서 자동으로 탐지한 값은 아니다.

## 자료 보관과 검증 한계

- `.local/`의 계정·토큰·앱 로그는 Git에 올리지 않는다.
- `results/` 원본 결과도 Git 추적에서 제외한다.
- 공유할 결과는 내용을 확인하고 별도로 전달한다.
- 캡처와 원본 결과를 함께 보관한다.
- 앱·DB·부하 발생기가 같은 Mac의 자원을 공유한다.
- 배포 서버의 성능이나 2,000명 수용 여부로 일반화하지 않는다.
- 주문 생성·변경 시 인덱스 유지 비용은 아직 검증하지 않았다.
- 응답 정확성 통과와 성능 목표 달성은 구분한다.
