# DB 스키마 마이그레이션 (Flyway)

테이블·컬럼·인덱스·제약을 바꿀 때는 엔티티와 함께 **마이그레이션 SQL 파일을 추가**한다.
앱이 기동할 때 Flyway가 아직 적용하지 않은 파일을 순서대로 실행하고, 그 뒤 Hibernate가 엔티티와 스키마가 일치하는지 검증한다. (`ddl-auto: validate`)

- 위치: `src/main/resources/db/migration/`
- 적용 기록: DB의 `flyway_schema_history` 테이블
- 운영에도 앱 배포 때 같은 방식으로 적용된다. DB에 직접 DDL을 실행하지 않는다.

## 1. 파일 작성 규칙

```
V{번호}__{설명}.sql
V3__add_ticket_products_sale_period.sql
```

- 번호는 현재 가장 큰 번호 + 1. 밑줄은 **두 개**(`__`)다.
- 설명은 영어 소문자 snake_case로, 무엇을 바꾸는지 쓴다.
- 파일 맨 위에 Jira 번호와 목적을 주석으로 남긴다.
- MySQL 8.4 문법으로 쓴다. (운영 RDS 버전)
- 같은 번호를 다른 브랜치에서 동시에 쓰면 나중에 머지하는 쪽이 번호를 올린다.

### 이미 적용된 파일은 고치지 않는다

Flyway는 적용한 파일의 checksum을 기록한다. dev에 머지된 파일을 수정하면 그 파일을 이미 적용한 DB(운영, 다른 팀원 로컬)에서 앱이 기동하지 못한다. (`Validate failed: Migration checksum mismatch`)
잘못된 내용은 새 번호의 파일로 바로잡는다.

## 2. 작업 순서

1. 엔티티를 수정한다.
2. 같은 변경을 SQL로 쓴 마이그레이션 파일을 추가한다.
   - 컬럼 타입·길이·NULL 여부·제약 이름을 엔티티와 맞춘다.
3. 로컬에서 앱을 띄워 Flyway 적용과 `validate`가 통과하는지 확인한다.
4. `FlywayMigrationIntegrationTest`를 실행한다. (Docker 필요, CI에서도 실행된다)
   - 운영과 같은 MySQL 8.4의 빈 DB에 모든 마이그레이션을 적용한 뒤 엔티티와 비교한다.
   - **테이블·컬럼을 빠뜨리거나 컬럼 타입이 다르면 이 테스트가 실패한다.** 다른 테스트는 엔티티로 스키마를 만들기 때문에(`create-drop`) 통과한다.
5. 테스트가 잡지 못하는 차이는 리뷰에서 엔티티와 SQL을 나란히 놓고 확인한다.
   - `validate`는 테이블·컬럼 존재와 컬럼 타입만 비교한다.
   - **컬럼 길이, NULL 여부, UNIQUE 제약, 인덱스, 외래 키**는 비교하지 않는다. 엔티티에만 추가하고 마이그레이션을 빠뜨려도 모든 테스트가 통과하고, 운영에만 제약이 없게 된다.

## 3. 배포 중 하위 호환

운영 배포(ASG Instance Refresh)는 새 인스턴스를 먼저 띄우고 기존 인스턴스를 나중에 내린다.
새 인스턴스가 기동하며 마이그레이션을 적용한 뒤 몇 분 동안은 **이전 버전 앱도 새 스키마로 동작**한다. 따라서 마이그레이션은 이전 버전 앱을 깨뜨리지 않아야 한다.

| 변경 | 방법 |
| --- | --- |
| 컬럼 추가 | NULL 허용이나 기본값을 둔다. (이전 버전 앱은 이 컬럼을 넣지 않는다) |
| 테이블·인덱스 추가 | 그대로 가능 |
| 컬럼 삭제 | 1차 배포: 코드에서 사용 중지 → 2차 배포: 컬럼 삭제 |
| 컬럼 이름 변경 | 1차: 새 컬럼 추가 + 양쪽에 쓰기 → 2차: 읽기를 새 컬럼으로 → 3차: 이전 컬럼 삭제 |
| NOT NULL 추가 | 1차: 기존 데이터 채우기 + 코드가 항상 값을 넣게 → 2차: NOT NULL 추가 |
| UNIQUE 제약 추가 | 기존 데이터에 중복이 없는지 운영에서 먼저 확인한다 |

큰 테이블의 ALTER는 테이블 잠금과 시간이 걸릴 수 있으니 리뷰 때 함께 확인한다.

## 4. 실패했을 때

MySQL의 DDL은 트랜잭션으로 되돌려지지 않는다. 파일 하나에 문장이 여러 개면 앞 문장만 적용된 채 실패할 수 있다.
가능하면 **파일 하나에 ALTER 하나**로 쓴다. (같은 테이블에 대한 여러 변경은 `ALTER TABLE` 한 문장으로 묶는다)

- 로컬: 로컬 DB를 지우고 다시 만든 뒤 앱을 띄우면 V1부터 다시 적용된다.
- 운영: 마이그레이션이 실패하면 새 인스턴스가 정상이 되지 않아 배포가 자동 롤백된다. 이전 버전 앱은 계속 동작한다.
  - `flyway_schema_history`에 실패(`success = 0`)로 기록되고, 이 기록이 남아 있으면 다음 배포도 기동하지 못한다.
  - 적용된 부분을 수동으로 되돌리고 실패 기록을 지운 뒤(`flyway repair`와 같은 작업), 고친 파일로 다시 배포한다. 혼자 처리하지 말고 공유한다.

## 5. 로컬 DB

- 빈 DB: 앱을 띄우면 V1부터 모두 적용된다.
- Flyway 도입 전에 Hibernate(`ddl-auto`)로 테이블을 만든 DB: V1이 적용된 것으로 표시하고(baseline) V2부터 적용한다.
  - baseline은 로컬 테이블이 실제로 V1과 같은지 확인하지 않는다. 다르면 아래처럼 기동이 실패한다. 이때는 로컬 DB를 지우고 다시 만든다.
    - V2 이후 마이그레이션이 이미 있는 컬럼·제약을 다시 추가하려다 실패한다. (`Duplicate column name` 등)
      MySQL DDL은 되돌려지지 않아 `flyway_schema_history`에 실패 기록이 남으므로, 다시 띄워도 계속 실패한다.
    - 마이그레이션은 통과해도 엔티티와 테이블·컬럼이 다르면 `validate`에서 실패한다.
  - **`docs/sql/kan-103-…`을 로컬에 직접 실행한 DB는 반드시 이 경우다.** `active_attraction` 컬럼이 이미 있어 V2가 실패한다. 처음부터 로컬 DB를 지우고 다시 만든다.

```sql
DROP DATABASE attraction_reservation;
CREATE DATABASE attraction_reservation;
```

## 6. 기존 `docs/sql/*.sql`과의 관계

- Flyway 도입 전에는 `docs/sql/`의 SQL을 각자 DB에 직접 실행했다.
- `V1__init.sql`은 Flyway 도입 시점(2026-11-05)의 운영 스키마이고, `V2`는 `docs/sql/kan-103-…`과 같다.
- 앞으로의 스키마 변경은 `docs/sql/`이 아니라 `db/migration/`에 추가한다.
- `docs/sql/`에 있지만 아직 엔티티가 없는 테이블(예: KAN-97 `attraction_paths`, `attraction_locations`)은 V1에 없다. 그 기능을 머지할 때 마이그레이션 파일로 추가한다.
