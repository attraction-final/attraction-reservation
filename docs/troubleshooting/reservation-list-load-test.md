# 내 예약 목록 HTTP 부하 테스트와 측정 기록

> **KAN-134** · 100 VUs의 load-10에서 **첫 10초 지연 집중**을 확인했다. initial p99는 전체/RESERVED 366.65/403.08ms, later는 39.35/14.12ms였다. 기능 검증과 구간 합계는 통과했으며 원인은 미확정이다. 다음은 측정 시작을 5초에 분산하는 비교이며 아직 미실행이다.

## 1. 목적과 현재 범위

[N+1 해결](reservation-list-n-plus-one.md)과 [회원 목록 인덱스 분석](reservation-list-index.md) 이후,
실제 HTTP 요청에서 인증·Service·Repository·DTO 직렬화가 함께 동작하는지 확인하는 단계를 마련했다.
DB 실행 계획의 개선을 HTTP 처리량 개선으로 바로 간주하지 않고, API 기준의 별도 실험을 진행하려는 목적이다.

| 현재 확인한 것 | 아직 확인하지 않은 것 |
| --- | --- |
| 실제 Spring Security를 거친 조회와 미인증 접근 차단 | 전체 API 권한 정책 |
| 회원별 예약 ID·정렬·상태 필터·페이지·건수·일부 DTO 필드 | 모든 날짜·페이지·정렬 조건 |
| smoke와 첫 10 VUs 측정의 응답 시간·오류 여부 | 더 높은 부하에서의 변화·장시간 안정성·성능 목표 충족 여부 |
| 준비부터 실행·결과 저장까지 자동화 | 운영 수용량과 최대 처리량 |

## 2. 실행 구성과 선택 이유

Python 보조 스크립트를 참고해 시작했지만 현재 PC에 Python 실행 환경이 없었다.
Node.js로 대체한 뒤, 추가 runtime 설치 없이 팀원이 재현할 수 있도록 **Docker + k6 + SQL + Git Bash 실행기**로 정리했다.
보조 언어 변경 자체를 애플리케이션 성능 개선으로 기록하지 않는다.

| 구성 | 역할 |
| --- | --- |
| 전용 Compose | 앱·MySQL·Redis·k6를 기존 개발 환경과 분리 |
| 준비용 k6 | 실제 회원가입·CSRF·로그인으로 테스트 계정 생성/재사용 확인 |
| MySQL client 컨테이너 | SQL로 합성 이력 생성 또는 기존 fixture 검증, 응답 기대 결과 추출 |
| 측정용 k6 | setup에서 실제 로그인 → VU별 목록 조회 → 집계 결과 저장. smoke는 2명, load는 10명 |
| Git Bash `run.sh` | 위 작업을 순서대로 실행하고 메타데이터·전후 메트릭·종료 코드 기록 |

Node.js·Python·host의 MySQL client는 필요하지 않다. k6의 JavaScript는 k6 자체 runtime에서 실행한다.
회원 준비용 실행은 실제 목록 smoke와 분리했다. 토큰 발급은 측정 전 setup에서 수행하며 목록 전용 Trend에는 포함하지 않는다.
실행 방법은 [테스트 README](../../perf/reservation-list/README.md)에 정리했다. 팀원의 `perf/order-list`는 변경하지 않았다.

쓰기 스케줄러를 비활성화했으며, 앱·DB·k6는 같은 PC의 Docker 자원을 공유한다.

## 4. 실행 중 발견한 문제와 조치

| 항목 | 확인 사실 | 조치·검증 상태 |

| `smoke-02` 준비 후 중단 | fixture 기대 결과는 만들어졌지만 metadata의 gitHead가 비었고 k6 결과·종료 코드가 없었음. 전역 `MSYS_NO_PATHCONV=1` 때문에 Git이 `/d/...` 경로를 찾지 못하는 오류를 읽기 전용 명령으로 재현 | 경로 변환 예외를 Docker 명령에만 적용하고 Git은 프로젝트 디렉터리로 이동해 실행. 이후 `smoke-03`에서 끝까지 완료 |

기존 결과를 덮어쓰지 않고 새로운 RUN_ID로 재실행한다.

### 전후 메트릭의 해석 범위

| 항목 | 전 → 후 | 확인할 수 있는 것·한계 |
| --- | --- | --- |
| Hikari timeout_total | 0 → 0 | 두 snapshot 사이 해당 pool timeout counter 증가는 없음 |
| Hikari active / pending | 각각 0 → 0 | 시작·종료 근처 관측값. 실행 중 최대 사용량이나 대기 부재의 근거는 아님 |
| minor GC count | 16 → 23 | snapshot 사이 7회 증가 |
| minor GC pause 합계 | 0.508 → 0.545초 | snapshot 사이 약 37ms 증가. 특정 API의 지연 원인으로 연결할 수는 없음 |

snapshot 사이에는 측정용 setup 로그인 등도 포함된다. GC 증가를 목록 요청만의 비용으로 해석하지 않는다.
프로세스 CPU의 전후 순간값만으로 구간 평균·최댓값이나 병목을 확정하지 않는다.

**아직 내릴 수 없는 결론:** 최적화 효과의 비율, 동시 접속 수용량, 운영 SLO 충족 여부, 병목 원인.
10 VUs는 수집기 사용 유무가 달랐고 20 VUs 반복에서는 marker를 추가했다.
50 VUs는 세 번 관측했고 마지막 실행에서 수집·정리 순서를 변경했다. 이번 표본만으로 병목이나 개선 효과를 확정하지 않는다.
100 VUs의 load-08·09·10에서 각각 시작 직후 1개 표본의 커넥션 대기를 관측했다. load-10에서 초기 지연 집중도 확인했다.
warm-up을 분리했어도 계정 준비의 로그인·캐시·JIT·같은 PC의 다른 작업 영향을 완전히 통제한 것은 아니다.
기존 Node.js 실행과 응답 시간이 달라졌어도 보조 실행 방식 변경의 성능 효과로 주장하지 않는다.

| 다음 항목 | 확인할 내용 |
| --- | --- |
| 저장 수정 회귀 | 완료: smoke-04 통과 및 결과 파일의 관련 패턴 미검출 확인 |
| 첫 측정 조건 | 완료: p95 기준 없이 10 VUs·60초, 기능 오류 0 요구 |
| warm-up 분리 | 완료: load-01에서 20초 별도 프로세스로 실행 |
| 단계별 부하 | 완료: 100 VUs 반복·구간별 집계. 다음은 최대 100 VUs를 유지한 첫 요청 분산 시작과 비교 |
| 수집 품질 | load-07 정상 종료에서 일반 수집·경계·정리 오류 0. 복구·중단 경로는 미검증 |
| 병목 근거 | 주기적 자원 수집 확보. SQL 비용·요청별 지연과 자원 구간 연결 분석은 후속 범위 |
| 비교·기록 | 같은 환경·데이터·부하·warm-up 조건의 개선 전후와 변경 비용을 함께 기록 |

### 주기적 자원 수집 구성 (load-02에서 실행 확인)

첫 측정의 전후 snapshot 한계를 보완하기 위해 host의 Git Bash에서 `sample-resources.sh`를 병렬 실행하도록 추가했다.
별도 Python·Node.js·모니터링 서버는 필요하지 않으며, 부하 조건은 우선 그대로 유지한다.

| 항목 | 보강 내용 |
| --- | --- |
| 대상 구간 | warm-up 종료 후, 측정용 k6 기동 직전부터 완료까지 |
| 간격 | 처리 시간을 포함해 목표 2초. 실제 간격은 기록 시각으로 확인 |
| Docker 지표 | 앱·MySQL·Redis·측정용 k6의 CPU, 메모리/제한, 네트워크·블록 I/O, PIDs |
| 앱 메트릭 | Hikari 연결 수·pending·timeout, JVM 메모리·GC, 프로세스 CPU·uptime, HTTP 지표 |
| 식별 | 주기 번호·시작/종료 시각, 측정 k6 실행 여부 |
| 수집 품질 | 별도 오류 파일·수집 프로세스 종료 코드. API 통과와 수집 성공을 구분 |
| 종료 처리 | 부하 종료 또는 실행기 종료 시 수집 중단을 요청하고 프로세스 회수 |

load-02에서 수집 파일의 생성과 관측 범위를 확인했다. 마지막 Docker 수집 1회의 누락은 위에 기록했다.
관측 최대값은 표본 중 최대값이며 실제 순간 최대값이 아니다. k6 시작/종료 경계에는 컨테이너 표본이 없을 수 있다.
scrape와 Docker stats도 동시에 실행되는 것은 아니며, 수집기 자체가 같은 PC의 CPU·I/O를 사용한다.
수집 없는 load-01과의 시간 차이를 앱 코드 변경의 개선 효과로 주장하지 않는다.

### 20 VUs 지원 (load-03에서 실행 확인)

`TEST_VUS=20`으로 실행하면 서로 다른 회원 20명을 warm-up과 측정에서 동일하게 사용한다.
기존 100,000건은 그대로 두고, 기대 결과 SQL이 후보 회원 20명·조건별 2행씩 총 40행을 추출하도록 확장했다.
smoke는 처음 2명, 기본 load는 처음 10명을 계속 사용한다.
이 단계에서는 10·20 VUs를 지원했고 시간·대기·자원 제한·수집 방식은 바꾸지 않았다.
성능 합격 기준 없이 먼저 관측하고, 요청률·지연·자원·pool 대기를 함께 확인한다.
회원 수 증가에 따라 요청하는 데이터의 작업 집합도 커지므로 모든 차이를 단일 원인으로 설명하지 않는다.
새 SQL·20 VUs 프로필의 실제 실행은 load-03에서 확인했다.

### setup/VU 경계 marker (load-04에서 실행 확인)

목록 부하 자체와 setup 인증 준비를 구분하기 위해 k6 집계에 다음 Gauge를 추가했다.

| 지표 | 의미 |
| --- | --- |
| reservation_list_setup_started_at_ms | setup 진입 시각 |
| reservation_list_setup_finished_at_ms | 실제 로그인까지 끝난 setup 완료 직전 시각 |
| reservation_list_vu_started_at_ms | 각 VU 첫 iteration 시작 시각. min/max로 시작 범위를 확인 |

값은 UTC epoch milliseconds다. 기존 allowlist의 metrics 안에 저장하며 setup_data나 토큰을 다시 저장하지 않는다.
load-04에서 같은 20 VUs를 반복해 marker와 CPU 주기의 시간 범위를 대조했다.
시각이 겹치는 것만으로 원인을 확정하지 않고, 가능하면 동일 조건 반복 관측까지 함께 본다.
marker의 실제 저장을 확인했다. 기존 load-03에 새 경계값이 있는 것처럼 해석하지 않는다.

### 50 VUs 지원 (load-05에서 실행 확인)

지원 VU를 10·20·50으로 확장하고 기대 결과 SQL의 후보를 회원 50명·조건별 2행씩 총 100행으로 늘렸다.
smoke와 10·20 VUs는 필요한 수만 선택하며 기존 데이터 100,000건을 변경하지 않는다.
다음은 같은 스크립트에서 RUN_ID만 바꿔 반복한다. warm-up 20초·측정 60초·iteration당 1초 대기·자원 제한·수집 방식은 유지한다.

```bash
TEST_VUS=50 bash perf/reservation-list/run.sh load-07 load
```

성능 합격 기준은 계속 미설정이다. SQL 후보 범위와 50 VUs 실행은 load-05·06에서 검증했다.
동시 사용자와 작업 집합이 함께 증가하므로 요청률·지연·자원·pool 대기를 종합해서 본다.

### 수집 종료 순서 개선 (load-07 정상 종료에서 실행 확인)

부하는 50 VUs로 유지하고 다음 순서로 바꿨다.

```text
k6 실행 (--rm 없이 이번 실행 owner label 지정)
  → k6 종료 코드 확보
  → 수집 중단 요청, 진행 중 수집 완료까지 기다림
  → owner와 Compose 소속이 일치하는 측정용 k6만 정리
```

같은 이름의 기존 컨테이너가 있으면 중단하며, 앱·DB·Redis나 다른 실행의 컨테이너를 정리 대상으로 삼지 않는다.
사용자 중단 시에도 EXIT trap에서 수집기를 회수하고 이번 실행 소유의 k6만 종료·정리한다.
컨테이너를 보존해도 프로세스 종료 중 stats 스트림이 끝날 수 있으므로 다음 수집기 보완을 함께 적용했다.

| 변경 | 기록·검증 기준 |
| --- | --- |
| 성공한 stats에 k6 표본이 없는 경우 | stopped 상태 확인 시 경계 이벤트로 기록, 다른 상태는 실제 수집 오류로 기록 |
| batch stats 실패 후 k6가 exited/dead인 경우 | 원문을 경계 이벤트 파일에 보존하고 앱·DB·Redis 표본을 재조회 |
| 재조회한 서버 표본 | recoveredAfterK6Stop=true와 새 관측 시작 시각으로 구분 |
| 그 밖의 stats 실패·복구 실패 | sampling-errors.txt에 남김. 경계라는 이유로 일괄 무시하지 않음 |
| 정리 상태 | cleanup-exit-code.txt와 cleanup-errors.txt에 별도 기록 |

load-07에서 기능 검증·일반 수집 오류·경계 이벤트·정리 상태를 확인했다. 복구 분기는 실행되지 않았다.
정상 종료 경계의 k6 표본이 없을 수 있다는 한계는 유지하며, 모든 지표가 빈틈없이 수집된다고 주장하지 않는다.
이번 변경은 테스트 도구의 종료 순서 보완이다. 앱 성능을 개선한 변경이 아니며, 정상 종료 외 경로는 검증이 남아 있다.

### 100 VUs 지원 (load-08에서 실행 확인)

지원 VU를 10·20·50·100으로 확장하고 SQL의 기대 결과 후보를 회원 100명·조건별 2행씩 총 200행으로 늘렸다.
smoke와 이전 load는 필요한 회원 수만 선택하며 기존 데이터 100,000건은 바꾸지 않는다.

```bash
START_MODE=staggered TEST_VUS=100 bash perf/reservation-list/run.sh load-11 load
```

warm-up 20초·측정 60초·iteration당 1초 대기·컨테이너 자원 제한·수집·정리 방식을 유지한다.
이번에도 p95 기준은 미설정이며 기능 오류 0을 요구한다. 요청률·지연·pool 대기와 앱/DB/k6 자원을 함께 확인한다.
더 많은 로그인 준비와 데이터 작업 집합의 영향을 구분하고 최대 수용량이나 운영 SLO로 일반화하지 않는다.
새 SQL 후보 범위와 100 VUs 실행은 load-08·09에서, 구간별 집계는 load-10에서 확인했다. 다음은 최대 VUs를 유지하고 시작 방식만 바꿔 비교한다.

### 시간 구간별 집계 (load-10에서 실행 확인)

k6 scenario 시작을 공통 기준으로 요청 시작 시각에 따라 initial [0,10초), later [10초,60초), drain [60초,종료)로 구분한다.
각 구간의 전체/RESERVED duration·요청 수·응답 불일치율을 기록하고 기존 전체 집계도 유지한다.
60초 이후 진행 중 iteration이 시작한 추가 요청은 drain으로 분리해 later에 합치지 않는다.
10초 이전에 시작해 그 이후 끝난 요청은 initial에 포함된다. 구간별 percentile을 평균해 전체 percentile로 만들지 않는다.
initial/later 각 조회 조건에는 실제 요청 표본이 있어야 하며, 오류는 구간·전체 모두 거절한다. drain 발생은 강제하지 않는다.
scenario 시작 시각 Gauge와 자원 표본을 대조하고 구간별 요청 수 합도 전체와 비교한다.

이 변경은 100 VUs·동시 시작·대기·데이터·pool을 유지한 관측 보강이다. 초기 요청 집중을 제거한 실험이 아니다.
10초 이후를 이름만으로 안정 상태라고 가정하지 않고, 실제 수치로 초기와 이후의 차이를 본다.
새 구간별 지표와 구간 합계를 load-10에서 확인했다. 이후 부하 증가는 분석 결과와 발생기 한계를 보고 정하며 100 VUs를 최종 수용량으로 확정하지 않는다.

### 다음 단계: 첫 요청 분산 시작 (코드 작성, 아직 미실행)

START_MODE 기본값은 simultaneous다. staggered를 선택하면 측정용 load의 첫 요청 목표 시각을 VU ID 순서로 공통 scenario 시작 0~5초에 배치한다.
이미 지난 목표 시각은 추가 대기하지 않으며 실제 시작 범위는 `reservation_list_vu_first_request_at_ms`의 min/max로 검증한다.
기존 VU 첫 iteration 진입 Gauge는 유지해 sleep 전 진입과 실제 첫 요청을 혼동하지 않는다.
warm-up은 동시 시작 그대로 유지하며 매 iteration의 조회 2회·1초 대기·데이터·pool·자원 제한도 유지한다.

최대 100 VUs·60초는 같아도 첫 5초의 요청 활동이 점진적으로 늘어 총 요청 수와 요청률이 달라질 수 있다.
따라서 시작 방식의 비교로 해석하며 동일한 도착 패턴에서 앱을 최적화한 결과로 표현하지 않는다.
initial/later/drain 정의와 전체 통계는 유지한다. 새 분산 시작 프로필은 아직 실행 검증 전이다.

실행 원본은 Git에서 제외되는 `perf/reservation-list/results/`에 두며, 저장소에는 이 문서의 핵심 조건·지표·판단만 남긴다.
토큰·인증 헤더·전체 요청/응답 원문을 문서에 포함하지 않는다. 이후 실험 결과는 이 문서에 이어서 갱신한다.
