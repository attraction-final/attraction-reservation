# 로컬 통합 부하 — 2,000 VU 검증과 DB 연결 풀 비교

## 목적과 결론

주문 목록·내 정보 조회·주문 생성 및 취소를 함께 실행하여,
개별 API 실험에서 확인하지 못한 공유 자원 사용 상황을 검사했다.

개인 실험 환경에서 최대 DB 연결 수 10개와 20개를 비교했다.
10개는 2분 본 측정 3회 모두 기준을 통과했고,
20개는 3회 중 1회만 전체 기준을 통과했다.
20개 설정은 채택하지 않고 10개로 복구했다.

복구 후 2,000 VU·5분 최종 실행에서는 주문 생성 시간 초과 5건과
두 조회 API의 HTTP P95 기준 초과가 발생했다.
따라서 안정적인 동시 사용자 2,000명 수용을 입증하지 못했다.

이번 작업의 결과는 조건별 측정, 개선 후보 미채택,
실패 요청과 DB 상태 대조 및 정리 기록이다.
새로운 백엔드 성능 개선을 달성한 사례로 설명하지 않는다.

## 검증 범위

이미 로그인한 사용자가 아래 행동을 반복하는 시나리오다.

| 사용자 배정 | 비율 | 2,000 VU에서 인원 |
|---|---:|---:|
| 주문 목록 조회 | 70% | 1,400명 |
| 내 정보 조회 | 20% | 400명 |
| 주문 생성 후 취소 | 10% | 200명 |

주문 사용자는 생성과 취소 요청을 각각 보내므로,
사용자 배정 비율과 실제 HTTP 요청 비율은 다르다.

각 행동 완료 후 3~5초 대기한다.
일정한 VU 수를 유지하는 폐쇄형 부하이며,
2,000건을 한 번씩 보내는 집중 요청과 다르다.

비율·대기 시간·목표 사용자 수는 프로젝트의 실험 가정이다.
실제 운영 트래픽 자료에서 산출한 수치는 아니다.

로그인과 데이터 준비는 측정 전에 수행한다.
로그인·재발급·실제 PG 결제·예약 등 전체 서비스 흐름을
모두 포함한 검증은 아니다.

## 환경과 데이터

| 항목 | 조건 |
|---|---|
| 기준 커밋 | 69a1f4d2 |
| 포함된 기존 개선 | 주문 생성 saveAndFlush → save |
| 실행 환경 | 같은 Mac에서 앱·Docker·부하 도구 실행 |
| Mac 메모리 | 16GiB |
| Docker 할당 | CPU 10개 / 메모리 약 7.75GiB |
| Java | 17, 앱 힙 256~512MB |
| 앱 / 관리 포트 | 18096 / 18097 |
| MySQL DB | attraction_service_capacity_perf |
| Redis 논리 DB | 4 |
| 최종 최대 DB 연결 수 | 10개 |

별도 확인 시 Mac 스왑 약 10.8GiB 사용을 관측했다.
이 수치만으로 특정 실행의 실패 원인을 확정하지 않는다.

회원은 실제 가입 API로 준비한 ACTIVE·USER·LOCAL 회원 2,000명이다.
회원별 조회용 취소 주문 100건, 총 200,000건을 준비했다.
조회용 주문·항목·결제는 관계와 금액을 맞춰 SQL로 생성한 합성 이력이다.
실제 주문 생성이나 결제 처리 성능 측정으로 계산하지 않는다.

조회는 첫 페이지·중간 페이지·마지막 페이지를 순환한다.
조회 사용자와 생성·취소 사용자를 구분하여 조회 기준이 변하지 않게 했다.

생성·취소 사용자는 공통 상품 1개를 사용한다.
가격 10,000원·수량 1개·시작 재고 10,000개로,
재고 부족보다 공통 상품에 대한 경합을 포함하는 조건이다.
각 실행 후 실제 API로 생성·취소된 주문과 재고를 DB에서 대조한다.

## 측정 전 정한 기준

| 항목 | 기준 |
|---|---|
| 주문 목록·내 정보 | 각각 HTTP P95 1,000ms 이하 |
| 주문 생성·취소 | 각각 HTTP P95 2,000ms 이하 |
| 예상하지 않은 HTTP·업무 실패 | 0건 |
| 응답 검증·DB 대조 | 모두 통과 |
| 시간 초과·중단 반복 | 0건 |

시간 기준은 프로젝트에서 정한 목표이며 보편적인 업계 기준이 아니다.
P99는 통과 기준과 별도로 기록하여 느린 요청도 확인했다.

HTTP 시간은 k6 response.timings.duration이다.
연결 대기 등을 모두 포함한 사용자 체감 시간과 동일하지 않다.
행동 전체 경과 시간도 별도 기록하며, 마지막 대기 시간은 제외한다.

## 진행 순서

1. 10 VU 기본 검사
2. 100 → 500 → 1,000 → 2,000 VU, 단계별 2분 탐색
3. 부하 도구의 불필요한 데이터 복사 수정
4. 수정 후 2,000 VU 재탐색과 JFR 진단
5. 연결 풀 10개·20개 각각 재시작·예열 후 2분 본 측정 3회
6. 연결 풀 10개 복구·예열 후 5분 최종 실행
7. 실패 실행의 DB 대조·정리와 증빙 보관

단계별 실행은 별도의 일정 VU 실행이다.
한 실행 안에서 사용자를 점진적으로 늘리는 방식은 아니다.

## 부하 도구 수정과 오류 처리

초기 스크립트는 VU마다 전체 회원 기준을 복사하고,
상품 ID 하나를 읽으려고 기준 JSON 전체를 다시 해석했다.

상품 ID를 공유 배열로 읽고 전체 회원 배정 검사를 setup으로 옮겼다.
이는 부하 도구의 초기화 비용을 줄이기 위한 수정이다.
백엔드 성능 개선 수치로 계산하지 않는다.

초기 2,000 VU 탐색에서는 HTTP 요청 37,974건 중
1,139건이 시간 초과로 기록됐다.
DB에 생성됐지만 클라이언트가 생성 응답을 확인하지 못한 주문이 있어,
미취소 주문 115건을 실제 API로 취소한 뒤 재고 복구를 확인했다.

10 VU 기본 검사에서는 짧은 실행의 결과에 vus_max가 없어
검증 도구가 중단됐다.
기존 결과와 오류 기록을 보존하고 검사 코드를 수정한 뒤,
새 부하 없이 재검증했다.

이후 생성·취소 이력이 누적되면서 DB 상태 JSON이
MySQL 명령행 클라이언트 수신 한도를 초과했다.
조회 클라이언트에 64MiB 한도를 명시하고 상태를 다시 수집했다.
DB 서버·앱 설정 변경이나 백엔드 개선으로 계산하지 않는다.

## JFR 진단

수정된 도구로 2,000 VU·2분 진단 실행을 수행했다.
로그인은 기록 시작 전에 끝내고,
실제 HTTP 요청 구간과 겹치는 이벤트를 분석했다.

| 항목 | 관측 결과 |
|---|---:|
| DB 연결 획득 대기 이벤트 | 99,857개 |
| 연결 대기 평균 / 최대 | 155.12ms / 981.90ms |
| DB 소켓 읽기 평균 | 24.92ms |
| GC 정지 시간 합계 / 최대 | 517.31ms / 23.97ms |
| MySQL 서버 전체 잠금 대기 증가 | 8,203회 |
| MySQL 누적 잠금 대기 증가 | 165,257ms |

연결 획득 대기가 관측되어 연결 풀 10개와 20개를 비교했다.
연결 수를 늘리면 DB 경합이 악화될 가능성도 있어 효과를 가정하지 않았다.

이벤트 수는 요청 수가 아니다.
여러 스레드의 대기 합계는 실제 실행 시간을 넘을 수 있다.
소켓 읽기에는 SQL 실행·잠금·통신 영향이 섞인다.
MySQL 카운터는 서버 전체 값이다.
스택 깊이 16의 제한으로 앱 상세 호출 경로는 확인하지 못했다.
진단 실행은 일반 성능 비교에서 제외했다.

## 연결 풀 비교

설정별 앱 재시작과 2분 예열 1회 후,
2,000 VU·2분 본 측정을 3회 수행했다.
JFR은 사용하지 않았고 잠자기 방지를 적용했다.
본 측정 6회의 JAR 해시와 부하 스크립트는 동일하다.

### 실행별 HTTP P95

|---|---:|---:|---:|---:|---:|---|
| 10 | 1 | 165.95 | 157.64 | 182.44 | 180.27 | 통과 |
| 10 | 2 | 187.53 | 180.12 | 217.47 | 218.62 | 통과 |
| 10 | 3 | 280.58 | 276.78 | 303.11 | 307.76 | 통과 |
| 20 | 1 | 1,222.75 | 1,213.45 | 1,358.49 | 1,332.12 | 조회 지연 미충족 |
| 20 | 2 | 3,818.00 | 3,773.47 | 4,053.94 | 3,845.12 | 지연 미충족 |
| 20 | 3 | 48.11 | 43.56 | 118.78 | 121.03 | 통과 |

### 실행별 HTTP P95의 중앙값

| 기능 | 풀 10개(ms) | 풀 20개(ms) |
|---|---:|---:|
| 주문 목록 | 187.53 | 1,222.75 |
| 내 정보 | 180.12 | 1,213.45 |
| 주문 생성 | 217.47 | 1,358.49 |
| 주문 취소 | 218.62 | 1,332.12 |

실행별 지표 3개의 중앙값이며 전체 요청을 합친 백분위수가 아니다.
본 측정 6회 모두 응답·DB 정확성 검증은 통과했다.

20개 설정 예열에서는 생성 HTTP 409가 1건 발생했고,
같은 구간에 MySQL 잠금 대기 시간 초과 로그가 확인됐다.
예열은 본 비교에 포함하지 않지만 실패 기록은 보존했다.

판단: 안정적인 개선 근거가 없어 20개 설정을 채택하지 않았다.
개인 실험 설정을 10개로 복구했다.
실행 간 편차가 크므로 관측 차이 전체를 설정 변경 효과로 확정하지 않는다.

## 복구 후 5분 최종 검증

조건: 연결 풀 10개, 재시작·예열 후 2,000 VU·300초, JFR 미사용.

| 항목 | 결과 |
|---|---:|
| HTTP 요청 | 151,000건 |
| 완료 반복 | 137,961회 |
| 주문 생성 시도 | 13,044건 |
| 생성 성공 응답 | 13,039건 |
| 취소 성공 응답 | 13,039건 |
| 주문 생성 시간 초과 | 5건 |
| 응답 검증 통과 / 실패 | 576,202개 / 25개 |

| 기능 | HTTP P95(ms) | HTTP P99(ms) | 지연 기준 |
|---|---:|---:|---|
| 주문 목록 | 2,034.16 | 4,676.89 | 미충족 |
| 내 정보 | 2,028.32 | 4,662.67 | 미충족 |
| 주문 생성 | 1,834.69 | 4,529.11 | 충족 |
| 주문 취소 | 1,500.09 | 4,714.97 | 충족 |

최종 판정은 미통과다.
완료 반복 수는 모든 행동의 성공 건수를 뜻하지 않는다.
검증 실패 25개는 실패 요청 5건에 대한 여러 검사 결과이며,
실패 요청 25건으로 계산하지 않는다.

DB 조회 오류 수정 후 수집한 상태와 실행 전 상태를 대조했다.
DB 신규 주문 13,039건은 취소 상태였고,
정리 시 추가로 취소할 주문은 0건이었다.
조회 이력·주문·항목·결제 건수와 재고 10,000개 복구를 확인했다.

이는 DB 상태 대조와 정리 완료이며,
원래 요청 실패와 지연 기준 미달을 성공으로 바꾸지 않는다.
검증 도구의 최초 오류 및 이후 수집 시점을 별도 기록했다.

## 실행 도구와 재현

| 파일 | 역할 |
|---|---|
| application-perf.yaml | 전용 DB·포트·Redis·연결 풀 설정 |
| start-app.py | 실험 앱 실행 |
| prepare-users.py | 실제 가입 API로 회원 준비 |
| prepare-products.sql | 조회용·생성 취소용 상품 준비 |
| prepare-history.py | 회원별 합성 조회 이력 준비·검증 |
| prepare-tokens.py | 측정 전 접근 토큰 준비 |
| prepare-fixture.py | 사용자 배정과 조회 비교 기준 준비 |
| service-capacity.js | 혼합 부하와 응답 검사 |
| service-state.py | 일관된 읽기 전용 DB 상태 조회 |
| run-service.py | 준비·증빙·자원 표본·실행·검증 연결 |
| verify-service.py | 응답 기록과 실행 전후 DB 대조 |
| cleanup-service.py | 실험 주문 취소와 재고·이력 보존 확인 |

자원 표본 수집은 기존 perf/auth-capacity/run-login.py를 재사용한다.
각 결과 폴더에 해당 도구 사본도 보관한다.

전용 DB와 앱을 준비한 뒤 상품·회원·조회 이력 순서로 준비한다.

    docker compose -f perf/order-list/compose.yaml exec -T mysql mysql --default-character-set=utf8mb4 -uperf -pperf-local-only attraction_service_capacity_perf < perf/service-capacity/prepare-products.sql
    python3 perf/service-capacity/prepare-users.py --users 10 < /dev/null
    python3 perf/service-capacity/prepare-history.py < /dev/null

기본 검사와 측정은 새 결과 이름을 사용한다.

    caffeinate -i python3 perf/service-capacity/run-service.py 새-기본검사-이름 --mode smoke --vus 10 < /dev/null
    caffeinate -i python3 perf/service-capacity/run-service.py 새-측정-이름 --mode load --vus 2000 --duration 120s < /dev/null

2,000 VU 실행 전에는 회원과 이력을 2,000명까지 준비해야 한다.
300s는 5분 측정이며 --jfr은 별도 진단 실행용이다.

부하 직전에 토큰을 새로 준비하며 잔여 시간을 검사한다.
실행 차단 파일이 남으면 결과와 DB 상태부터 확인한다.
정리 대상 확인 없이 차단 파일을 삭제하거나 부하를 다시 보내지 않는다.

각 결과 폴더에 다음을 보관한다.

- 기준 커밋·소스 변경·JAR 해시·설정·도구 사본

## 해석의 한계와 종료 범위

같은 Mac의 CPU·메모리·스왑·디스크·네트워크 자원을 공유한다.
실행 순서·예열·시간 차이·DB 이력 누적의 영향을 분리하지 못했다.
일부 도구 오류는 기록을 보존하고 수정 후 재조회·검증했다.

2분 통과만으로 5분 이상 안정성이나 최대 처리량을 주장하지 않는다.
5분 미통과의 원인을 연결 풀 또는 특정 SQL 하나로 확정하지 않는다.
운영 환경의 전체 서비스 수용 능력으로 일반화하지 않는다.

이번 범위는 혼합 부하 측정, 연결 풀 후보 비교·복구,
5분 검증의 실패와 데이터 정리까지다.
추가 개선 후보를 계속 늘리지 않고 결과와 미해결 한계를 남긴다.
