# 기능 요구사항 명세서

## 1. 기본 정보
- **기능명:** 환불 (전체 환불 / 부분 환불)
- **작성 목적:** 환불 기능의 API 계약, 검증 규칙, 오류 응답, 처리·재시도 정책을 코드를 보지 않고 이 문서만으로 확인할 수 있게 정리한다.
- **관련 화면 / 메뉴:** 없음 (API만 제공)

## 2. 기능 개요
- **기능 설명:** 결제 완료된 주문을 전체 또는 주문 상품·수량 단위로 환불한다. 환불 요청을 먼저 기록하고 PG(결제사) 결제를 취소하며, 취소에 실패하면 자동으로 재시도한다.
- **개발 목적 / 해결하려는 문제:** 사용자는 결제한 주문을 전체 또는 일부 환불할 수 있어야 한다. PG 취소가 실패하거나 처리 중 서버가 종료돼도 환불 요청이 사라지지 않아야 하고, 같은 상품이 두 번 환불되면 안 된다.
- **사용자 및 실행 조건:**
  - 결제 완료(또는 부분 환불) 상태인 본인 결제만 환불할 수 있다.
  - 상품마다 남은 환불 가능 수량까지만 환불할 수 있다.
- **기능 범위:**
  - 전체 환불 API, 부분 환불 API
  - 환불 요청 기록(환불·환불 상품)과 환불 가능 수량 계산
  - PG 부분 취소, 실패 시 자동 재시도, 재시도 한도 초과 시 수동 확인 대상으로 분리
  - 환불 완료 시 결제·주문 상태 변경
- **제외 범위:**
  - 재고(좌석) 복구 — 추후 작업 (10장)
  - 로그인 인증 연동 — 현재는 사용자 ID를 요청 파라미터로 받는다 (6장)
  - PG에서 오는 취소 웹훅으로 환불 상태를 맞추는 처리
  - 환불 내역 조회 API

## 3. 기존 기능 및 시스템 활용
- **재사용할 기존 기능:**
  - PG 결제 취소 기능 (금액 불일치 보상 취소에서 쓰던 것)
  - 결제 비관적 락 조회 (결제 승인·사용자 취소에서 쓰던 것)
  - 공통 응답 형식과 공통 예외 처리
- **재사용 방식:**
  - PG 결제 취소는 **확장**했다. 기존 호출 방식(결제·사유·금액)은 그대로 두고, "PG 취소 가능 금액"을 함께 보낼 수 있는 방식을 추가했다. 기존 보상 취소는 동작이 바뀌지 않는다.
  - 재시도 구조(점유 → PG 호출 → 결과 기록, 백오프, 멈춘 처리 회수, 스케줄러)는 기존 보상 취소와 같은 방식을 따른다.
- **기존 기능의 유지 조건:** 기존 테스트가 모두 통과해야 한다. 결제 승인·웹훅·보상 취소 동작은 바뀌지 않는다.
- **추가 구현이 필요한 부분:** 환불 상태 관리, 환불 가능 수량 계산, 환불 전용 처리기와 스케줄러, 결제·주문의 환불 상태 변경
- **사전 확인 사항 (확인됨):** PortOne이 "PG 취소 가능 금액"이 맞지 않을 때 돌려주는 오류의 형식. PortOne server-sdk 0.24.0의 `CancellableAmountConsistencyBrokenError` 기준 `type`은 `CANCELLABLE_AMOUNT_CONSISTENCY_BROKEN`이다.

## 4. 상세 요구사항

### 공통
- **사용자 식별:** 쿼리 파라미터 `userId` (필수, 숫자). 인증 연동 전 임시 방식이다.
- **결제 식별:** 경로의 `pgId` (결제 생성 시 발급되는 결제 식별자)
- **응답 형식:** 모든 응답은 `{ success, message, data }` 형식이다. 실패 응답의 `data`는 없거나, 입력값 검증 실패일 때 필드별 오류다.
- **환불 금액:** 환불 상품마다 `주문 당시 가격 × 환불 수량`을 더한 값이다.
- **응답의 `status`:** 저장 직후 PG 취소를 한 번 시도한 뒤의 환불 상태다. 응답까지 최대 약 45초 걸릴 수 있다.

  | status | 의미 |
  |---|---|
  | `COMPLETED` | PG 취소까지 끝남 |
  | `FAILED` | 즉시 시도가 실패함. 자동으로 재시도된다 |
  | `REQUESTED` | 같은 결제의 다른 환불이 처리 중이라 대기 중. 그 환불이 끝난 뒤 자동으로 처리된다 |
  | `PROCESSING` | PG 취소 중이거나, PG 취소 후 결과 기록에 실패해 확인이 필요함 (5-2) |
  | `DEAD` | 재시도하지 않는 실패. PG 내역을 수동으로 확인해야 한다 (5-2) |

- **환불 가능 결제 상태:** 결제 완료(`PAID`), 부분 환불(`PARTIALLY_REFUNDED`)

### REQ-001. 전체 환불
- **설명:** 결제의 모든 주문 상품을 남은 환불 가능 수량만큼 환불한다.
- **실행 조건:** `POST /api/payments/{pgId}/refunds?userId={userId}`
- **입력값:**
  ```json
  { "reason": "단순 변심" }
  ```
  | 필드 | 규칙 |
  |---|---|
  | `reason` | 필수, 공백 불가, 200자 이하 |
- **처리 규칙:**
  - 모든 주문 상품의 남은 환불 가능 수량 전부를 환불한다.
  - 남은 수량이 0인 상품은 건너뛴다.
  - 환불할 수량이 하나도 없으면 거부한다.
- **결과 / 출력값:**
  ```json
  {
    "success": true,
    "message": "환불 요청에 성공했습니다.",
    "data": { "refundId": 1, "refundAmount": 40000, "status": "COMPLETED" }
  }
  ```
- **예외 및 오류 처리:**

  | 상태 | 메시지 | 상황 |
  |---|---|---|
  | 400 | 입력값을 확인해주세요 | `reason`이 없거나 공백이거나 200자 초과 (`data`에 필드별 오류) |
  | 400 | 필수 요청값이 누락되었습니다. | `userId` 누락 |
  | 400 | 요청 본문 형식이 올바르지 않습니다. | JSON 형식 오류 |
  | 400 | 환불 수량이 올바르지 않습니다. | 남은 환불 가능 수량이 하나도 없음 |
  | 404 | 결제 내역을 찾을 수 없습니다. | 결제가 없거나 본인 결제가 아님 (존재 여부를 숨기기 위해 같은 응답) |
  | 409 | 환불할 수 없는 결제 상태입니다. | 결제가 결제 대기·결제 실패·결제 취소·전체 환불 상태 |
  | 409 | 다른 요청에 의해 데이터가 변경되었습니다. 다시 시도해주세요. | 같은 결제의 다른 요청 처리를 3초 넘게 기다림 |

### REQ-002. 부분 환불
- **설명:** 선택한 주문 상품을 지정한 수량만큼 환불한다.
- **실행 조건:** `POST /api/payments/{pgId}/refunds/partial?userId={userId}`
- **입력값:**
  ```json
  {
    "items": [
      { "orderItemId": 100, "quantity": 2 },
      { "orderItemId": 200, "quantity": 1 }
    ],
    "reason": "단순 변심"
  }
  ```
  | 필드 | 규칙 |
  |---|---|
  | `items` | 필수, 1개 이상 |
  | `items[].orderItemId` | 필수. 해당 결제의 주문에 있는 주문 상품이어야 한다. 같은 상품을 두 번 넣을 수 없다 |
  | `items[].quantity` | 필수, 1 이상, 남은 환불 가능 수량 이하 |
  | `reason` | 필수, 공백 불가, 200자 이하 |
- **처리 규칙:** 상품마다 요청 수량이 남은 환불 가능 수량 이하인지 확인하고, 모두 통과하면 하나의 환불로 기록한다. 하나라도 실패하면 아무것도 기록하지 않는다.
- **결과 / 출력값:** REQ-001과 같은 형식이다. `message`는 "부분 환불 요청에 성공했습니다."이다.
- **예외 및 오류 처리:**

  | 상태 | 메시지 | 상황 |
  |---|---|---|
  | 400 | 입력값을 확인해주세요 | `items`가 없거나 비어 있음, `orderItemId`·`quantity` 누락, `quantity`가 1 미만, `reason` 오류 (`data`에 필드별 오류) |
  | 400 | 필수 요청값이 누락되었습니다. | `userId` 누락 |
  | 400 | 요청 본문 형식이 올바르지 않습니다. | JSON 형식 오류 |
  | 400 | 같은 주문 상품을 중복해서 환불할 수 없습니다. | 같은 `orderItemId`가 두 번 이상 |
  | 400 | 해당 주문의 주문 상품이 아닙니다. | 결제의 주문에 없는 주문 상품 |
  | 400 | 환불 수량이 올바르지 않습니다. | 남은 환불 가능 수량 초과 |
  | 404 | 결제 내역을 찾을 수 없습니다. | 결제가 없거나 본인 결제가 아님 |
  | 409 | 환불할 수 없는 결제 상태입니다. | 결제가 결제 대기·결제 실패·결제 취소·전체 환불 상태 |
  | 409 | 다른 요청에 의해 데이터가 변경되었습니다. 다시 시도해주세요. | 같은 결제의 다른 요청 처리를 3초 넘게 기다림 |

## 5. 처리 흐름

### 5-1. 환불 요청 기록 (하나의 트랜잭션)
1. 사용자가 전체 환불 또는 부분 환불을 요청한다. (부분 환불은 이 단계에서 입력값과 상품 중복을 먼저 검증한다.)
2. 결제를 비관적 락으로 조회한다. 같은 결제에 대한 다른 환불 요청은 이 락이 풀릴 때까지 기다린다(최대 3초).
   - 결제가 없으면 404
3. 본인 결제인지 확인한다.
   - 본인 결제가 아니면 404
4. 결제가 결제 완료 또는 부분 환불 상태인지 확인한다.
   - 아니면 409
5. 주문 상품마다 남은 환불 가능 수량을 계산한다.
   - `남은 환불 가능 수량 = 주문 수량 − 이 상품의 기존 환불 수량 합계`
   - 기존 환불 수량에는 **모든 상태**의 환불을 포함한다. 진행 중(`REQUESTED`·`PROCESSING`), 재시도 대기(`FAILED`)는 아직 PG 취소될 수 있고, `DEAD`는 PG에서 취소됐는지 알 수 없으므로 수동으로 확인하기 전까지 포함한다.
6. 환불 상품을 검증한다.
   - 부분 환불: 주문에 있는 상품인지, 수량이 1 이상이고 남은 수량 이하인지
   - 전체 환불: 남은 수량이 있는 상품만 남은 수량 전부로 담고, 하나도 없으면 400
7. 환불을 `REQUESTED` 상태로 기록하고 커밋한다. 이때 결제 락이 풀린다.
8. 같은 요청 안에서 PG 취소를 한 번 시도하고(5-2), 시도 후 환불 상태를 응답한다.

### 5-2. 환불 PG 취소 처리 (트랜잭션 밖에서 PG 호출)
- **처리 시점:** 요청 직후 즉시 1회 시도한다. 실패했거나 시도하지 못한 환불은 스케줄러가 30초 간격으로 최대 20건씩 처리한다.
- **처리 대상:** `REQUESTED` 환불, 재시도 시각이 지난 `FAILED` 환불, `PROCESSING`으로 5분 넘게 멈춘 환불
- **점유 (짧은 트랜잭션):**
  1. 결제 → 환불 순서로 잠근다.
  2. 다시 확인해 처리 대상이 아니면 건너뛴다. 즉시 시도와 스케줄러, 여러 서버가 동시에 같은 환불을 처리하려 해도 한 곳만 처리한다.
  3. **같은 결제의 다른 환불이 `PROCESSING`이면 건너뛴다.** 같은 결제의 환불은 PG 호출까지 한 번에 하나씩 처리한다. 건너뛴 환불은 상태가 그대로라 앞선 환불이 끝난 뒤 스케줄러가 처리한다.
  4. `PROCESSING`으로 바꾸고 시도 횟수를 1 늘린다.
  5. PG 취소 가능 금액을 계산한다: `결제 금액 − 완료(COMPLETED)된 환불 금액 합계`. PG에 실제 반영된 환불만 뺀다.
- **PG 부분 취소:** 환불 금액, 환불 사유, PG 취소 가능 금액을 보낸다. PG는 취소 가능 금액이 자신이 가진 값과 다르면 거절하므로, 같은 취소가 두 번 처리되는 것을 막는다.
  - 통신 실패는 같은 요청 키로 최대 3회 다시 보낸다(1회당 연결 5초 + 응답 10초).
  - PG가 "이미 취소된 결제"라고 응답하면 성공으로 보지 않는다. 부분 취소에서 이 응답은 다른 경로로 전체 취소됐다는 뜻이라 이번 환불이 반영됐다고 볼 수 없다. 재시도하지 않고 `DEAD`로 보낸다. 전체 취소(보상 취소)에서는 기존과 같이 성공으로 본다.
    - 이때 PG는 전체 취소 상태지만 결제는 `PAID` 또는 `PARTIALLY_REFUNDED`, 주문은 `COMPLETED` 또는 `PARTIALLY_REFUNDED`로 남는다. 남은 수량으로 다시 환불을 요청할 수 있고, 그 환불도 같은 응답을 받아 바로 `DEAD`가 된다. 결제·주문 상태는 수동으로 맞춰야 한다 (10장 "`DEAD` 확인 수단").
- **성공 (짧은 트랜잭션):** 결제 → 환불 순서로 잠근 뒤, 환불을 `COMPLETED`로 바꾸고 결제·주문 상태를 함께 바꾼다.
  - 모든 주문 상품의 완료된 환불 수량이 주문 수량과 같아지면 → 결제·주문 `REFUNDED`
  - 그렇지 않으면 → 결제·주문 `PARTIALLY_REFUNDED`
  - 아직 재시도 중인 다른 환불이 있으면 `PARTIALLY_REFUNDED`로 남는다.
- **실패:**
  - `FAILED`로 바꾸고 1분, 2분, 4분, 8분 뒤에 재시도한다.
  - 5번째 시도도 실패하면 `DEAD`가 되고 오류 로그를 남긴다. 이후 자동으로 처리하지 않으므로 PG 내역을 확인해 수동으로 처리한다.
  - 실패 사유는 최대 500자까지 기록한다.
  - PG가 "PG 취소 가능 금액이 맞지 않는다"(`CANCELLABLE_AMOUNT_CONSISTENCY_BROKEN`)고 거절하면 앞선 요청이 이미 처리됐을 수 있으므로 재시도하지 않고 시도 횟수와 관계없이 바로 `DEAD`로 보낸다.
- **PG 취소는 성공했는데 결과 기록에 실패한 경우:** 실패로 기록하지 않는다. 실패로 기록하면 재시도하면서 취소를 다시 보내기 때문이다. 오류 로그를 남기고 `PROCESSING`으로 둔다. 5분 뒤 다시 점유되면 PG 취소 가능 금액이 달라 PG가 거절하므로, 바로 `DEAD`가 되어 수동 확인 대상이 된다.

## 6. 제약사항 및 주의사항
- **기존 동작 중 유지해야 할 부분:** 결제 승인, 결제 웹훅 처리, 금액 불일치 보상 취소의 동작
- **변경하면 안 되는 부분:** PG 결제 취소의 기존 호출 방식(결제·사유·금액). 보상 취소가 그대로 사용한다.
- **권한 / 보안 조건:**
  - 본인 결제만 환불할 수 있다. 다른 사용자의 결제는 결제가 없는 것과 같은 404로 응답한다.
  - **현재는 사용자 ID를 요청 파라미터로 받으므로 누구나 다른 사용자 ID로 요청할 수 있다. 인증을 연동하기 전까지 운영에 노출하지 않는다.**
- **성능 및 데이터 제약:**
  - 즉시 시도를 요청 안에서 기다리므로 PG 응답이 느리면 응답도 최대 약 45초 걸린다.
  - 같은 결제의 환불 요청은 결제 락 때문에 순서대로 처리되고, 3초 넘게 기다리면 409로 끝난다.
- **기술적 제약:**
  - 트랜잭션 안에서 PG를 호출하지 않는다.
  - 환불 요청 기록과 PG 취소 처리 모두 결제 → 환불 순서로 잠근다.
  - 점유와 결과 기록은 다른 처리가 커밋한 최신 상태를 읽는 격리 수준(READ COMMITTED)으로 실행한다. MySQL 기본 격리 수준에서는 락을 기다린 뒤에도 기다리기 전의 데이터를 읽어, 같은 결제의 환불이 동시에 PG로 나가는 문제를 MySQL 테스트로 확인했다.
  - 처리 중 멈춘 환불을 다시 점유하는 기준(5분)은 PG 취소 최대 소요 시간(약 45초)보다 길어야 한다.
  - 스케줄러 스레드는 3개다(웹훅·보상 취소·환불). 서로의 PG 지연에 밀리지 않게 하기 위해서다.
  - 운영 DB는 테이블을 자동 생성하지 않으므로 환불 테이블을 미리 만들어야 한다(11장).

## 9. 환불 상태 전이
| 상태 | 의미 | 전이 가능 상태 |
|---|---|---|
| `REQUESTED` | 환불 기록됨, PG 취소 대기 | `PROCESSING` |
| `PROCESSING` | PG 취소 중 | `COMPLETED`, `FAILED`, `DEAD`, `PROCESSING` |
| `FAILED` | PG 취소 실패, 재시도 대기 | `PROCESSING` |
| `COMPLETED` | PG 취소 완료 | 없음 |
| `DEAD` | 재시도 한도 초과 또는 재시도하면 안 되는 실패, 수동 확인 필요 | 없음 |

- `PROCESSING → PROCESSING`은 5분 넘게 멈춘 처리를 다시 점유하는 경우다.
- `DEAD`는 `FAILED`가 아니라 재시도 중(`PROCESSING`)에 5번째로 실패할 때 정해진다. PG가 "이미 취소된 결제" 또는 "PG 취소 가능 금액 불일치"로 거절하면 시도 횟수와 관계없이 `PROCESSING`에서 바로 `DEAD`가 된다.
- 허용되지 않은 전이는 409 "유효하지 않은 환불 상태 전이입니다."로 막는다(내부 처리용).

### 결제·주문 상태와의 관계
| 결제·주문 상태 | 환불 요청 | 환불 완료 시 |
|---|---|---|
| 결제 완료 | 가능 | 부분 환불 또는 전체 환불 |
| 부분 환불 | 가능 | 부분 환불 또는 전체 환불 |
| 전체 환불 | 불가 (409) | — |
| 결제 대기·결제 실패·결제 취소 | 불가 (409) | — |

## 10. 미해결 사항
| 항목 | 현재 상태 | 영향 |
|---|---|---|
| PG 취소 가능 금액 불일치 오류 구분 | 해결. server-sdk로 `type` 값을 확인하고 바로 `DEAD`로 보낸다 | 실제 PortOne 응답으로는 아직 확인하지 않았다 (아래 "실제 PortOne 연동") |
| 실제 PortOne 연동 | 가짜 PG로만 테스트 | 취소 가능 금액 필드가 실제로 받아들여지는지 확인 필요 |
| 재고 복구 | 미구현 | 환불돼도 좌석이 돌아오지 않는다 |
| 인증 연동 | 사용자 ID를 요청 파라미터로 받음 | 인증 전까지 운영 노출 금지 |
| `DEAD` 확인 수단 | 오류 로그만 남음 | 알림·조회 수단과 수동 환불 절차 필요 |
| PG 취소 웹훅 반영 | 미구현 | 우리가 보낸 취소의 결과는 즉시 시도·재시도로만 반영된다. PG 취소는 성공했지만 결과 기록에 실패했거나 응답이 타임아웃 난 환불은 `DEAD`가 되어 수동 확인 대상이 된다. 우리 시스템 밖에서 한 취소(PortOne 콘솔 등)는 감지하지 못한다 |

## 11. 데이터
운영 DB는 테이블을 자동으로 만들지 않으므로(검증만 함) 배포 전에 아래 테이블을 만들어야 한다. 시각 컬럼은 소수 초까지 저장한다(재시도 시각 비교가 어긋나지 않게).

**`refunds` (환불, 환불 1건 = PG 취소 요청 1건)**
| 컬럼 | 설명 |
|---|---|
| `id` | PK |
| `payment_id` | 환불할 결제 (필수) |
| `refund_amount` | 환불 금액 (필수) |
| `status` | 환불 상태 (9장, 필수) |
| `reason` | 환불 사유, 200자 (필수). PG 취소 사유로도 보낸다 |
| `requested_at` | 요청 시각 (필수) |
| `completed_at` | PG 취소 완료 시각 |
| `attempt_count` | PG 취소 시도 횟수 (필수) |
| `next_retry_at` | 다음 재시도 시각 (필수). 처음에는 요청 시각 |
| `last_error` | 마지막 실패 사유, 500자 |
| `created_at`, `updated_at` | 생성·수정 시각 (필수). `updated_at`은 멈춘 처리 판단 기준 |

**`refund_items` (환불 상품)**
| 컬럼 | 설명 |
|---|---|
| `id` | PK |
| `refund_id` | 소속 환불 (필수) |
| `order_item_id` | 환불할 주문 상품 (필수) |
| `quantity` | 환불 수량 (필수) |
