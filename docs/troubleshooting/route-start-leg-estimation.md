# 경로 추천 첫 구간 추정의 올림·부동소수점 점검

> **KAN-142 · 사용자 현재 위치 → 첫 어트랙션 도보 거리·시간 추정 (`HaversineStartLegEstimator`)**

| 항목 | 핵심 내용 |
| --- | --- |
| 배경 | 실측 구간(`attraction_paths`)은 어트랙션끼리만 있어, 사용자 위치에서 출발하는 첫 구간은 하버사인 직선거리로 추정한다 |
| 의심한 문제 | ① 부동소수점 때문에 `ceil`이 1 큰 값을 줄 수 있다 ② 이중 올림으로 오차가 쌓인다 ③ 직선거리 반올림은 "보여주기용"이라는 설명 |
| 확인 결과 | ① 현재 기본값(1.68, 52.8)에서는 발생하지 않음. 설정값을 바꾸면 발생(1.34, 45.3 등) ② 한 번 올림과 다른 경우 0.767%, 실제값보다 최대 약 1.015분 길게 나옴 ③ 틀린 설명. 반올림한 직선거리로 서비스 지역(2,000m)을 판정한다 |
| 처리 | 코드는 바꾸지 않음. 안전한 쪽(길게)으로만 틀리는 것을 확인하고 한계를 문서로 남김 |
| 남은 범위 | 설정값 변경 시 재검증, `walk = 264m → 5분` 같은 경계값 단위 테스트는 미추가 |

## 1. 계산 흐름

```java
double straightMeters = Haversine.distanceMeters(userLocation, attractionLocation);
int estimatedWalkMeters = (int) Math.ceil(straightMeters * properties.getDetourFactor());              // × 1.68
int estimatedMinutes = (int) Math.ceil(estimatedWalkMeters / properties.getWalkingSpeedMetersPerMinute()); // ÷ 52.8
return new StartLeg((int) Math.round(straightMeters), estimatedWalkMeters, estimatedMinutes);
```

| 단계 | 값 | 근거 |
| --- | --- | --- |
| 직선거리 | 하버사인(지구를 반지름 6,371,000m 구로 봄) | 위경도는 평면 좌표가 아니라 피타고라스를 쓸 수 없다 |
| 우회 계수 | 1.68 | `attraction_paths` 실측 90건의 `도보 거리 / 직선거리` 중앙값 (사분위 1.34 ~ 1.98) |
| 보행 속도 | 52.8 m/분 (≈ 3.17 km/h) | 실측 90건의 `distance_m / move_minutes` 중앙값 (사분위 46.9 ~ 59.2) |
| 도보 거리·시간 | `ceil` (올림) | 시간을 짧게 잡으면 사용자가 늦게 도착한다. 짧게 틀리는 것보다 길게 틀리는 편이 안전하다 |
| 직선거리 | `round` (반올림) | 응답 표시와 서비스 지역 판정에 쓴다 (3-3 참고) |

`StartLegEstimator` 인터페이스로 분리해 두어, 실제 도보 길찾기 API를 쓰게 되면 구현체만 추가하면 된다.

### 테스트 값 재현

`HaversineTest`의 기대값 `new StartLeg(145, 244, 5)`를 같은 공식으로 다시 계산했다. 사용자 위치는 (37.2930, 127.2010), 범퍼카는 (37.2923658, 127.1995663)이다. 컨트롤러 테스트의 `Leg.fromUserLocation(1L, 145, 244, 5)`도 같은 값을 쓴다.

| 단계 | 계산 | 결과 |
| --- | --- | --- |
| 직선거리 | Haversine | 145.114078m → `round` = **145** |
| 도보 거리 | 145.114078 × 1.68 = 243.791650 | `ceil` = **244** |
| 이동 시간 | 244 / 52.8 = 4.621212 | `ceil` = **5** |

4.62분을 4분으로 안내하면 사용자가 늦게 도착하므로 5분으로 올린다.

## 2. 의심한 함정

코드 주석과 리뷰 과정에서 다음 세 가지가 나왔다.

1. **부동소수점 + `ceil`**: 1.68과 52.8은 2진수로 정확히 표현되지 않는다. 결과가 정확히 정수여야 할 때(예: 264 / 52.8 = 5) `5.000000000000001`이 나오면 `ceil`이 6을 준다.
2. **이중 올림**: 거리에서 한 번, 시간에서 또 한 번 올린다. "최대 +1m, +1분의 보수적 오차가 쌓인다"고 주석에 적었다.
3. **직선거리 반올림**: "판단에 쓰는 값이 아니라 보여주기용이라 `round`"라고 설명했다.

추측으로 두지 않고 하나씩 실제로 계산해 확인했다.

## 3. 확인 결과

검증은 로컬 Java 17에서 일회성 스크립트로 했다. 정답값은 `BigDecimal`로 정확히 계산해 `double` 결과와 비교했다.

### 3-1. 부동소수점 + ceil: 현재 기본값에서는 발생하지 않음, 설정값에 따라 발생

`264 / 52.8`은 정확히 `5.0`이 나오고 `ceil`도 5다.

| 대상 | 범위 | `double` `ceil`이 정답과 다른 수 |
| --- | --- | --- |
| `walk / 52.8` | walk = 264k (k = 1 ~ 10,000) | 0건 |
| `walk / 52.8` | walk = 0 ~ 100,000 (정수 전체) | 0건 |
| `straight × 1.68` | straight = 0 ~ 100,000 (정수 전체) | 0건 |

같은 검사를 다른 설정값으로 돌리면 결과가 달라진다.

| 설정값 | 범위 | 틀린 수 | 첫 예 |
| --- | --- | --- | --- |
| 우회 계수 1.1 | 직선 0 ~ 10,000 | 460건 | `50 × 1.1 = 55.00000000000001` → 56 (정답 55) |
| 우회 계수 **1.34** | 직선 0 ~ 10,000 | 17건 | `750 × 1.34 = 1005.0000000000001` → 1006 (정답 1005) |
| 보행 속도 45.3 | 도보 0 ~ 100,000 | 47건 | `1359 / 45.3 = 30.000000000000004` → 31 (정답 30) |
| 1.15, 1.2, 1.3, 1.4, 1.5, 1.7, 1.98 / 46.9, 50.5, 55.3, 59.2, 60.1 | 같음 | 0건 | - |

- 1.34는 실측 우회 계수의 사분위 하한이다. 튜닝하면서 충분히 넣어 볼 수 있는 값이다.
- 그래서 이 함정은 "지금은 없지만 설정을 바꾸면 생길 수 있는 문제"다. 설정값은 `application.yaml`의 `route-recommendation.*`로 바꿀 수 있다.
- 실제 요청에서는 하버사인 직선거리가 정수가 아니어서 `직선 × 우회 계수`가 정확히 정수가 되는 일은 드물다. 반면 도보 거리는 이미 정수로 올린 값이라 `도보 / 보행 속도`는 정확히 정수가 될 수 있다. 실제 요청에서 영향이 있는 쪽은 보행 속도 쪽이다.
- 틀려도 1분(또는 1m) 길게 나온다. 사용자가 늦게 도착하는 방향은 아니다. 영향이 큰 곳은 기대값을 손으로 정한 경계값 테스트다.

### 3-2. 이중 올림: 영향은 작지만 "최대 +1분"보다 조금 크다

0 ~ 2,000m(서비스 지역 기준)의 직선거리 1,000,000개를 무작위로 만들어 비교했다(seed 42).

| 항목 | 결과 |
| --- | --- |
| 이중 올림 결과 ≠ 한 번만 올린 결과 `ceil(직선 × 1.68 / 52.8)` | 7,674건 (0.767%), 차이는 항상 +1분 |
| 도보 거리의 최대 초과 (정수 도보 거리 − 실제 값) | 1m 미만 |
| 이동 시간의 최대 초과 (정수 분 − 실제 분) | 약 1.015분 |

- 주석의 "최대 +1m, +1분"은 거의 맞다. 정확히는 도보 거리에서 올린 1m 미만이 시간에 1/52.8분(약 0.019분) 더해진다. 그래서 이론상 최대 초과는 `1 + 1/52.8 ≈ 1.019분`이다.
- 올림은 모두 길게 틀리는 방향이라 안전 마진으로 받아들였다.

### 3-3. 직선거리 반올림은 판단에도 쓰인다 (설명 정정)

"직선거리는 보여주기용"이라는 설명은 틀렸다. `RouteRecommendationService#validateServiceArea`가 반올림한 `straightDistanceM`으로 서비스 지역을 판정한다.

```java
int nearestMeters = startLegs.values().stream()
        .mapToInt(StartLeg::straightDistanceM)   // round 된 값
        .min()
        .orElseThrow();
if (nearestMeters > properties.getMaxStartDistanceMeters()) { // 2000
    throw new BusinessException(ErrorCode.LOCATION_OUT_OF_SERVICE_AREA, ...);
}
```

| 실제 직선거리 | `round` | 판정 |
| --- | --- | --- |
| 2,000.49m | 2,000 | 허용 |
| 2,000.5m | 2,001 | 거부 |

실제 경계는 "2,000m 이내"가 아니라 "2,000.5m 미만"이다. 차이가 0.5m뿐이고, 경계 자체가 최근접 어트랙션 기준 원이라 원래 정밀하지 않다. 그래서 그대로 두었다. 대신 응답 메시지의 거리와 판정에 쓴 거리가 같은 값이라는 점은 장점이다.

## 4. 결론

| 의심 | 판정 | 조치 |
| --- | --- | --- |
| 부동소수점 + ceil | 현재 기본값에서는 없음. 설정을 바꾸면 발생 | 설정 변경 시 3-1 검사를 다시 돌린다 |
| 이중 올림 | 0.767%에서 +1분, 최대 초과 약 1.015분 | 안전 마진으로 수용 |
| 직선거리 round | 판정에도 쓰임 (경계 2,000.5m 미만) | 설명을 정정, 동작은 유지 |

## 5. 남은 확인

- 경계값 단위 테스트(`도보 264m → 5분`, `528m → 10분`)는 추가하지 않았다. 지금 `estimate`가 좌표를 받기 때문에 도보 거리를 직접 넣을 수 없다.
- 설정값을 바꿔야 할 때 고를 수 있는 방법:
  - 올리기 전에 아주 작은 값을 빼기: `Math.ceil(x - 1e-9)`
  - `BigDecimal`로 계산하기
- 하버사인 추정과 실제 길찾기 결과의 차이는 측정하지 않았다. `StartLegEstimator` 주석은 "오차가 별로 안 나서 추천 결과에 영향이 없을 것"이라는 판단만 적고 있다.

## 6. 배운 점

- `ceil`은 정답이 정확히 정수인 지점에서만 부동소수점 오차에 민감하다. 그래서 "오차가 날 수 있다"는 추측보다 그 지점을 전수로 검사하는 편이 빠르고 정확했다.
- 같은 코드라도 설정값에 따라 문제가 생기거나 사라진다. 설정으로 바꿀 수 있는 숫자는 기본값만 검증하면 안 된다.
- 코드 주석이나 설명에 적힌 "이 값은 표시용"을 그대로 믿지 말고, 실제로 어디서 쓰는지 사용처를 찾아 확인해야 한다.
