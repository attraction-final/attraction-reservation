# 어트랙션 소요 시간 변경과 기존 슬롯 시간표 보호

> **KAN-125 · 운영 예정·진행 중 슬롯이 있는 경우 소요 시간 변경 제한**
>
> 미래 슬롯이 있는 상태에서 어트랙션 소요 시간을 변경하면, 어트랙션은 20분인데 기존 슬롯은 10분인 상태가 실제 DB에 저장됐다.
> 기존 시간표를 자동 변경하지 않고, 취소되지 않은 미종료 슬롯이 있을 때 소요 시간 변경을 거부하도록 보완했다.
> 경계값·정상 변경·슬롯 등록·시각 수정과의 동시 실행을 포함한 새 테스트 15개가 통과했다. 관련 회귀 실행 XML에서도 **58개 Test Suite, 419개 테스트, 실패·오류·스킵 0개**를 확인했다.

## 1. 문제와 정책 결정

기존 코드는 어트랙션 소요 시간과 슬롯의 시작·종료 시각을 각각 저장한다.

- 어트랙션 수정은 `durationMinutes`를 변경한다.
- 슬롯 등록은 등록 시점의 소요 시간으로 `endsAt`을 계산한다.
- 기존 슬롯은 어트랙션 소요 시간이 바뀌어도 자동 수정되지 않는다.
- 슬롯 시각 수정은 그 시점의 소요 시간으로 종료 시각을 다시 계산한다.

읽은 원본의 **BR-SLT-01**은 슬롯 길이와 어트랙션 소요 시간이 같다고 설명했지만 기준 시점을 구분하지 않았다. 사용자 시나리오 **4-4**에도 기존 슬롯이 있는 경우의 소요 시간 변경 정책은 없었다.

기존 슬롯을 자동으로 늘리면 다음 슬롯과 겹치거나 이미 예약된 이용 시간에 영향을 줄 수 있다. **BR-SLT-02**의 시간 중복 금지, **BR-SLT-03**의 운영 시간 제한, **BR-SLT-06**의 예약된 슬롯 시각 변경 제한도 고려해야 한다.

따라서 이 항목은 처음부터 단순한 계산 오류로 취급하지 않고, 기존 시간표를 어떻게 보존할지 먼저 결정했다.

### 이번에 확정한 기준

- 취소되지 않은 운영 예정·진행 중 슬롯이 있으면 소요 시간 변경을 거부한다.
- 제한 대상 조건은 `status != CANCELLED`이면서 `endsAt > 현재 KST`다.
- `OPEN`, `CLOSED`, `SUSPENDED` 슬롯은 모두 검사 대상이다.
- 예약이 없는 슬롯도 제한 대상에 포함한다.
- 종료 정각에는 이미 종료된 것으로 판단한다.
- 슬롯이 없거나 과거 슬롯·취소 슬롯만 있으면 변경을 허용한다.
- 요청에서 소요 시간을 생략하거나 기존 값과 동일하게 보내면 이 제한을 적용하지 않는다.
- 거부되는 수정 요청은 함께 보낸 설명 등 다른 필드도 저장하지 않는다.
- 기존 슬롯의 저장된 시작·종료 시각은 자동 변경하지 않는다.
- 소요 시간 변경 후 생성하는 슬롯에는 새 소요 시간을 적용한다.

이는 작업 중 사용자와 확정한 정책이다. 사용자는 BR-ATR-09, BR-SLT-01과 시나리오 4-4·5-2의 문구를 수정했다고 알렸으며, 수정한 원본을 이후 참고 자료에 업데이트할 예정이라고 설명했다. 이번 작업에서 그 최신 원본 전체를 다시 읽은 것으로 간주하지 않는다. 원본 `sources`는 수정하지 않았다.

## 2. 수정 전 재현

[AttractionDurationIntegrationTest](../../src/test/java/com/example/attractionreservation/domain/attraction/service/AttractionDurationIntegrationTest.java)에 실제 Service·MySQL을 사용하는 첫 테스트를 추가했다.

```text
기준 시각: 2026-11-08 10:00 KST
어트랙션 소요 시간: 10분
슬롯: 2026-11-08 14:00~14:10, OPEN, 예약 인원 0명
요청: 소요 시간 20분 + 설명 변경
기대: 요청 거부, 어트랙션과 슬롯 모두 기존 값 유지
```

최초 실패 XML의 시작 시각은 **2026-11-06 10:49:52 KST**였다. 테스트 1개가 실행됐고 두 검증이 실패했다.

```text
거부 예외: 기대 BusinessException / 실제 null

기대:
durationMinutes=10
description=기존 설명
slot=14:00~14:10

실제:
durationMinutes=20
description=함께 변경 요청한 설명
slot=14:00~14:10
```

슬롯은 유지됐지만 소요 시간 변경이 허용되어, 이후 운영할 시간표와 어트랙션 정보가 서로 달라졌다. 응답만 비교한 것이 아니라 Service 트랜잭션 종료 후 새 트랜잭션에서 실제 DB 상태를 비교했다.

## 3. 구현 보완

### 제한 대상 슬롯 조회

[AttractionSlotRepository](../../src/main/java/com/example/attractionreservation/domain/attractionSlot/repository/AttractionSlotRepository.java)에 다음 Derived Query를 추가했다.

```java
existsByAttraction_IdAndStatusNotAndEndsAtAfter(
        attractionId, SlotStatus.CANCELLED, now
)
```

메서드 이름에 따라 해당 어트랙션·취소 상태 제외·종료 시각 초과 조건으로 존재 여부를 조회한다. 예약 인원이나 예약 테이블은 조건에 넣지 않는다.

`EndsAtAfter`는 `>`이므로 종료 시각이 기준 시각과 같으면 제한 대상에서 빠진다.

### 어트랙션 수정 전 검사

[AttractionService.updateAttraction()](../../src/main/java/com/example/attractionreservation/domain/attraction/service/AttractionService.java)의 흐름을 다음과 같이 보완했다.

```text
기존 어트랙션 비관적 잠금 획득
→ 기존 소요 시간 보관
→ 기존 이름 중복 검사
→ 소요 시간이 실제로 달라지는지 판단
→ 달라진다면 KstTime.now() 기준으로 제한 대상 슬롯 조회
→ 슬롯이 있으면 예외
→ 없으면 기존 수정·flush·커밋 후 캐시 삭제 및 완료 로그 처리
```

소요 시간 변경 여부는 요청 값의 null 확인과 기존 값의 `equals()` 비교로 판단한다. `&&`의 단락 평가를 사용하여 생략·동일 값 요청에서는 슬롯 쿼리도 실행하지 않는다.

전용 오류는 다음과 같다.

```text
ErrorCode: ATTRACTION_DURATION_CHANGE_NOT_ALLOWED
HTTP: 409 Conflict
message: 운영 예정이거나 진행 중인 슬롯이 있어 소요 시간을 변경할 수 없습니다.
```

이름·설명 등을 먼저 변경했다가 되돌리는 대신 `attraction.update()` 전에 거부한다. 슬롯을 일괄 수정하거나 자동으로 연장하는 코드는 추가하지 않았다.

## 4. 테스트 환경과 검증 범위

- `@DataJpaTest`, `@ActiveProfiles("test")`
- Testcontainers MySQL `mysql:9.6`, `ddl-auto=create-drop`
- 기본 테스트 트랜잭션은 `NOT_SUPPORTED`
- fixture 생성·최종 조회는 별도 `TransactionTemplate` 사용
- 실제 AttractionService·AttractionSlotService·Repository 사용
- Redis 캐시 삭제용 `AttractionDetailCacheEvictor`만 mock 처리
- KstTime static mock은 `now()`만 고정하고 다른 유틸 메서드는 실제 실행
- 어트랙션 이름에 UUID를 붙여 유일성 제약과 충돌하지 않도록 구성
- 테스트가 만든 해당 어트랙션의 슬롯만 정리한 뒤 어트랙션 삭제

과거·진행 중 슬롯 fixture는 엔티티 메서드로 시각을 구성한다. 과거 슬롯을 실제 관리자 시각 수정 API로 변경할 수 있다고 검증한 것은 아니다.

### 경계값·정상 수정 11개

1. 예약 없는 미래 OPEN 슬롯의 소요 시간 변경 거부: 1개
2. 미래 CLOSED·SUSPENDED 슬롯의 변경 거부: 2개
3. 진행 중 슬롯의 변경 거부: 1개
4. 종료 정각·이미 종료된 슬롯의 변경 허용: 2개
5. 취소된 미래 슬롯의 변경 허용: 1개
6. 소요 시간 생략·동일 값 요청에서 설명 수정 허용: 2개
7. 슬롯이 없는 경우 변경 허용: 1개
8. 변경 후 실제 슬롯 등록 Service에서 새 길이 적용 및 과거 슬롯 보존: 1개

거부 테스트는 정확한 ErrorCode와 DB 상태 유지를 확인한다. 허용 테스트도 기존 슬롯 시각이 그대로인지 확인하며, 새 슬롯은 응답과 DB 양쪽에서 변경된 20분 길이를 검증한다.

## 5. 동시 실행 검증 4개

소요 시간 변경 제한은 조회 후 수정이므로, 슬롯 등록·시각 수정과 겹칠 때도 검토해야 한다.

어트랙션 수정과 슬롯 등록·시각 수정은 모두 기존 `findActiveByIdForUpdate()`를 사용한다. 이번에는 새 잠금 종류를 추가하지 않고 공통 어트랙션 행 잠금 아래 검사가 실행되는지 검증했다.

### 슬롯 등록과 소요 시간 변경: 2개

최초에는 과거 슬롯만 존재하도록 구성하여 두 작업이 각각 가능한 상태로 시작한다.

```text
슬롯 등록 선행:
10분 슬롯 저장·커밋 → 기다리던 소요 시간 변경은 거부
최종: 소요 시간 10분, 새 슬롯도 10분

소요 시간 변경 선행:
20분으로 수정·커밋 → 기다리던 슬롯 등록이 새 값을 사용
최종: 소요 시간 20분, 새 슬롯도 20분
```

두 경우 모두 과거 슬롯의 시작·종료 시각은 유지한다. 저장된 슬롯 개수도 검증한다.

### 기존 슬롯 시각 수정과 소요 시간 변경: 2개

최초부터 미래 슬롯이 존재하므로 어느 작업이 먼저여도 소요 시간 변경은 허용되지 않는다.

```text
슬롯 시각 수정 선행:
16:00~16:10으로 수정 → 소요 시간 20분 변경은 거부

소요 시간 변경 선행:
기존 미래 슬롯 때문에 변경 거부·롤백 → 슬롯은 16:00~16:10으로 수정
```

최종 소요 시간은 10분이고, 거부된 요청의 설명은 저장되지 않는다. 슬롯 개수는 1개로 유지한다.

### 순서 제어와 한계

- 실제 Service를 별도 스레드에서 실행한다.
- Repository AOP advisor는 잠금 조회의 호출·획득 시점만 알리고 결과를 바꾸지 않는다.
- 슬롯 등록 경합은 선행 작업을 외부 트랜잭션의 커밋 직전에 멈춘다.
- 슬롯 시각 수정 경합은 선행 작업의 어트랙션 잠금 획득 직후 멈춘다.
- 후행 작업이 잠금 조회를 호출한 것을 확인한 뒤 선행 작업을 재개한다.
- static mock은 각 작업 스레드 안에서 생성한다.
- 정리 전에 작업 스레드를 종료하고 advisor를 제거한다.

500ms 동안 후행 요청이 끝나지 않았다는 검사만으로 DB 잠금 대기 자체를 증명하지 않는다. 최종 업무 오류·슬롯 길이·어트랙션 값·행 개수도 함께 검증한다. MySQL 잠금 대기 테이블을 조회한 것은 아니다. 예상한 업무 오류 이외의 DB 오류·데드락은 통과로 처리하지 않는다.

## 6. 실제 검증 결과

사용자가 다음 명령을 실행한 뒤 생성된 XML을 읽어 확인했다. 에이전트는 빌드·테스트를 직접 실행하지 않았다.

```bash
./gradlew test --tests "*AttractionDurationIntegrationTest" --rerun-tasks
```

```bash
./gradlew test --tests "*Attraction*" --tests "*Reservation*" --rerun-tasks
```

문서 작성 시점의 결과:

```text
관련 회귀 실행: 58개 Test Suite, 419개 테스트
failures=0, errors=0, skipped=0

AttractionDurationIntegrationTest: 15개 테스트
failures=0, errors=0, skipped=0
해당 Suite 시작 시각: 2026-11-06 14:33:17 KST
```

15개는 419개에 포함된 수치이며 두 값을 합산하지 않는다. 프로젝트 전체 테스트·Spring Security 권한·Redis 캐시 동작·운영 DB 적용 결과까지 검증한 것은 아니다.

## 7. 변경 범위와 남은 확인

- 운영 예정·진행 중 슬롯의 존재 검사와 전용 오류 추가
- 기존 어트랙션 잠금, 슬롯 저장 구조, 과거 시간표 보존 동작 유지
- 어트랙션 및 슬롯 시각 수정 API의 요청·응답 구조 변경 없음
- 새 DB 컬럼이나 마이그레이션 SQL 추가 없음
- 수정한 최신 요구사항 원본이 참고 자료에 동기화되면 정책 문구와 다시 대조 필요
- PR CI에서 통과 여부 확인 필요

이번 검증은 새로 정한 소요 시간 변경 정책과 명시한 경합 상황을 대상으로 한다. 모든 운영 상태 변경·삭제·예약 경합 전체를 새로 검증한 것으로 확대 해석하지 않는다.
