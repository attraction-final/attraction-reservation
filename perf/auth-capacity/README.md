# 일반 로그인 부하 확대와 병목 개선 후보 비교

## 1. 실험 목적과 최종 판단

일반 로그인의 10 VU 기준 측정에서 출발해, 부하를 높일 때 처리 건수와 응답 시간이 어떻게 달라지는지 확인했다.

200 VU에서 지속적인 지연이 관측돼 JFR로 실행 경로와 DB 연결 대기를 조사했다. 이후 다음 두 후보를 비교했다.

- DB 연결 풀 최대 크기: 10개 → 20개
- 로그인 트랜잭션 범위: 로그인 전체 → 회원 조회

두 후보 모두 이 환경에서 전반적인 성능 개선을 확인하지 못해 복구했다.

최종 상태:

- 연결 풀 최대 크기 10개 유지
- 서비스·레포지토리 코드는 기준 코드로 복구
- BCrypt 보안 강도 유지
- 실험 도구와 재현 문서 추가
- 동시 요청 2,000건 수용 여부는 미검증

이번 기록은 성공적인 최적화 사례가 아니라, 부하 확대와 진단을 근거로 개선 후보를 시험하고 채택하지 않은 과정이다.

## 2. 시나리오와 판단 기준

### 부하 탐색

대상은 `POST /api/auth/login`이다.

각 VU에 서로 다른 회원을 배정하고 다음을 반복했다.

1. 최초 실행 시 CSRF 정보 준비
2. 이메일·비밀번호 로그인
3. 응답 검증
4. 1초 대기

10 → 20 → 50 → 100 → 200 VU로 부하를 확대했다.

초기 탐색에는 실제 트래픽 요구에서 도출한 응답 시간 목표가 없었다. 따라서 실패가 없다는 이유만으로 충분한 성능이라고 판단하지 않았다.

### 트랜잭션 변경 비교

변경 전후 비교에서는 다음 조건을 고정했다.

- 200 VU
- 60초 반복 실행
- 요청 후 1초 대기
- 연결 풀 최대 크기 10개
- 같은 회원 파일·테스트 스크립트·앱 설정
- 각 조건에서 앱 재시작 후 10 VU·60초 예열
- 예열을 제외한 본 측정 각 3회

인증 실패와 중단 여부를 먼저 확인하고, 평균·P95·성공 처리율과 자원 관측을 함께 비교하기로 했다.

구체적인 응답 시간 SLO나 최소 개선율은 정하지 않았다. 일부 지표만 좋아지거나 편차가 커서 판단하기 어려우면 개선으로 채택하지 않는 방식으로 해석했다.

## 3. 실행 환경과 선택 이유

| 항목 | 조건 |
| --- | --- |
| 앱 소스 기준 | `db8f2cc` |
| Java | Corretto OpenJDK 17.0.19 |
| 앱 힙 | 최소 256MB / 최대 512MB |
| 앱 주소 | `127.0.0.1:18090` |
| 관리 주소 | `127.0.0.1:18091` |
| MySQL | `127.0.0.1:13316/attraction_auth_perf` |
| Redis | `127.0.0.1:16396`, 논리 DB 1 |
| 회원 | ACTIVE·USER·LOCAL |
| 부하 도구 | 고정 이미지 해시의 k6 |
| 요청 제한 시간 | 10초 |
| 부하 종료 유예 | 10초 |

기존 로그인 실험의 전용 DB와 회원을 재사용했다. 처음에는 회원 100명을 준비했고, 200 VU 실행 전에 200명으로 늘렸다.

VU마다 다른 회원을 사용해 같은 회원의 갱신 토큰 키를 덮어쓰는 간섭을 피했다.

로컬 HTTP 검사에서는 Secure 쿠키를 명시적인 Cookie 헤더로 전달했다. 서버의 쿠키 보안 설정은 변경하지 않았다.

앱·MySQL·Redis·k6는 같은 Mac의 CPU와 메모리를 공유했다. Redis 논리 DB 분리는 키 공간 분리이며 자원 격리는 아니다.

## 4. 응답 검증과 지표의 의미

로그인 응답마다 다음 7개 항목을 확인했다.

- HTTP 200
- 업무 성공 응답
- 접근 토큰 존재
- Bearer 토큰 종류
- 접근 토큰 유효 시간 600초
- 갱신 토큰 쿠키 존재
- 응답 본문에 갱신 토큰 없음

검증 개수에는 VU별 최초 CSRF 준비 검사도 포함된다.

예를 들어 로그인 6,537건·200 VU 실행에서는 다음과 같다.

`6,537 × 7 + 200 = 45,959개`

이 검사는 로그인 응답 형식을 확인한다. 반복 부하에서 매번 JWT 서명을 검증하거나 본인 정보 API를 호출한 것은 아니다.

`auth_login_duration`은 로그인 HTTP 요청의 응답 시간이다. 최초 CSRF 조회는 이 지표에서 제외되지만 실행 시간과 서버 부하에는 영향을 준다.

성공 건수는 종료 유예 시간에 완료된 요청도 포함할 수 있다. 초당 성공 건수는 k6가 기록한 카운터의 rate이며 최대 처리량을 뜻하지 않는다.

VU는 요청과 대기를 반복하는 가상 사용자 수다. 200 VU는 요청 200건이 계속 동시에 처리된다는 뜻이 아니다.

## 6. JFR 진단

진단 도구의 영향을 구분하기 위해 JFR 실행은 일반 성능 비교에서 제외했다.

### 100 VU

진단 기록에서 DB 연결 확보를 기다리는 경로가 관측됐다.

`ConcurrentBag.borrow → HikariPool.getConnection → 트랜잭션 시작`

관측된 연결 대기의 최대 시간은 약 1.64초였다.

### 200 VU

첫 로그인 응답부터 마지막 응답까지의 시간 구간에 시작된 이벤트를 분석했다.

| 항목 | 관측 결과 |
| --- | ---: |
| 실행 표본 | 20,008개 |
| BCrypt 포함 표본 | 19,576개, 약 97.8% |
| DB 연결 풀 대기 이벤트 | 5,596건 |
| 관측된 연결 대기 평균 | 약 963ms |
| 관측된 연결 대기 최대 | 약 1,920ms |
| GC 정지 합계 | 약 30.72ms |
| GC 정지 최대 | 약 10.2ms |

실행 표본 비율은 응답 시간 비율이나 CPU 사용률이 아니다.

대기 이벤트는 요청 수와 일대일로 대응하지 않는다. 기록 설정과 스택 깊이에 따라 관측 범위가 달라질 수 있다.

DB 연결 대기는 관측했지만, 이를 곧바로 느린 SQL의 증거로 해석하지 않았다. 현재 로그인은 비밀번호 검증과 토큰 처리도 서비스 트랜잭션 안에서 수행하므로, 연결 보유 범위도 개선 후보로 검토했다.

## 7. 연결 풀 10개·20개 비교

100 VU에서 각 설정을 3회 측정했다.

아래 수치는 실행별 지표의 중앙값이며, 전체 요청을 합쳐 계산한 P95·P99가 아니다.

| 지표 | 10개 | 20개 |
| --- | ---: | ---: |
| 성공 건수 | 5,331건 | 5,266건 |

- P95 257.17ms
- P99 823.36ms
- 실패·중단 0건

복구해도 최초 수치로 그대로 돌아오지는 않았다. 실행 순서·재시작·공유 자원의 영향을 분리하지 못했으므로 P99 감소를 설정 변경만의 효과라고 확정하지 않았다.

전반적인 개선 근거가 부족해 연결 풀은 10개로 복구했다.

## 8. 로그인 트랜잭션 범위 변경 비교

### 변경 가설

기존에는 로그인 서비스 전체가 읽기 트랜잭션이었다.

`DB 연결 확보 → 회원 조회 → BCrypt 검증 → 토큰 생성·Redis 저장 → 연결 반환`

회원 조회가 끝난 뒤에는 MySQL 연결이 필요하지 않은 작업이 이어진다. 따라서 회원 조회에만 트랜잭션을 두면 연결 대기를 줄일 수 있다는 가설을 세웠다.

실험 변경:

- `AuthService.login()`의 `@Transactional(readOnly = true)` 제거
- `UserRepository.findByEmail()`에 읽기 트랜잭션 추가
- 비밀번호 검증 강도와 연결 풀 10개 유지

실험 중 통합 테스트에서는 실제 BCrypt 검증 시 트랜잭션이 활성화돼 있지 않고, 정상 토큰 발급과 Redis 저장이 유지됨을 확인했다.

### 판단과 복구

평균·P95·P99와 성공 처리율에서 개선을 확인하지 못했다. 변경 후 앱 CPU 표본도 더 높게 관측됐지만, CPU 경쟁이 성능 차이의 원인이라고 확정하지 않았다.

같은 Mac에서 순서대로 측정했으며 실행 순서·열 상태·다른 작업의 영향을 분리하지 못했다. 따라서 코드 변경만이 차이의 원인이라고 단정하지 않는다.

이번 조건에서는 변경을 채택할 근거가 부족해 서비스·레포지토리 코드를 복구했다.

실험용 통합 테스트도 최종 테스트 목록에서 제거하고 원본 결과 폴더에 보관했다. 변경 내용은 패치로 남겼다.

복구 후 기존 인증 테스트를 통과했고, 앱 재시작 후 로그인 5건·검증 36개 통과, 실패·중단 0건을 확인했다.

## 9. 실행 도구와 재현 방법

| 파일 | 역할 |
| --- | --- |
| `.gitignore` | 로컬 준비 자료·결과·캐시 제외 |
| `application-perf.yaml` | 개인 인증 실험 설정 |
| `start-app.py` | Java 17 확인 및 전용 앱 실행 |
| `prepare-users.py` | 회원 준비와 검증 기준 파일 생성 |
| `auth-login.js` | 로그인 요청·응답 검사·지표 수집 |
| `run-login.py` | 실행 조건 보관·k6 실행·자원 표본 수집 |

저장소 루트에서 실행한다.

MySQL·Redis와 전용 DB 준비는 `../auth-login/README.md`의 기존 환경 구성을 참고한다. 이 도구는 `attraction_auth_perf`가 존재하고 개인 테스트 계정에 권한이 있는 환경을 전제로 한다.

앱이 이미 실행 중이면 PID와 사용 포트를 확인하고 종료한 뒤 기동한다. 실행 중인 프로세스는 소스 파일이나 JAR를 바꿔도 자동 갱신되지 않는다.

```bash
export JAVA_HOME=$(/usr/libexec/java_home -v 17)
export PATH="$JAVA_HOME/bin:$PATH"

bash gradlew bootJar --console=plain
python3 perf/auth-capacity/start-app.py
python3 perf/auth-capacity/prepare-users.py --users 200
```

회원 준비는 기존 전용 회원을 재사용하고 부족한 회원만 가입 API로 생성한다. 기본값은 10명이며 `--users` 허용 범위는 1~2000명이다.

준비한 회원 수는 성능 검증 결과가 아니다.

새 실행 이름으로 측정한다.

```bash
python3 perf/auth-capacity/run-login.py example-login-200vu-01 --vus 200

tail -n 8 perf/auth-capacity/results/example-login-200vu-01/console.log
```

`run-login.py`는 60초 반복 부하 전용이다. 같은 결과 폴더가 있으면 실행을 거절한다.

앱 PID가 18090 포트를 사용하는지 확인하고 다음을 보관한다.

- 테스트 스크립트·설정·준비 도구·실행 도구 사본
- 소스 커밋 기록과 JAR SHA-256
- 회원 파일 해시·VU 수·시작 시각·앱 PID
- k6 원본 지표와 요약
- 실행 로그와 종료 코드
- 앱·Docker 자원 표본

커밋 번호만으로 커밋 전 변경 사항을 설명할 수 없으므로, 트랜잭션 변경 실험에서는 별도로 패치와 빌드 해시를 보관했다.

JAR 해시 기록만으로 실제 프로세스에 적재된 실행 파일까지 자동 증명하는 것은 아니다. 실험에서는 기동 순서와 PID도 함께 확인했다.

## 10. 자원 표본 해석 시 주의점

`resources.jsonl`에는 앱의 `ps` 출력과 MySQL·Redis·k6의 Docker 통계가 들어간다.

- 앱 `ps` 출력: PID, CPU 사용률, 상주 메모리(KiB)
- 앱 CPU는 여러 코어 사용량을 합산하므로 100%를 넘을 수 있음
- 자원 수집 명령 실행 후 5초를 대기하므로 정확히 5초 간격은 아님
- 컨테이너 생성 전이나 종료 후 수집은 실패할 수 있음
- 오류 표본과 유효 표본을 구분해야 함
- 자원 수집 자체도 같은 Mac의 자원을 사용함
- 메모리 표본만으로 메모리 누수나 부재를 판단하지 않음

## 11. 검증·결과 보관·한계

실험 및 복구 과정에서 다음 테스트를 통과했다.

- AuthControllerTest
- AuthServiceTest
- JwtProviderTest
- AuthRefreshIntegrationTest

트랜잭션 변경 실험 중에는 AuthLoginTransactionIntegrationTest도 통과했다. 이 테스트는 최종 서비스 동작의 요구사항으로 채택하지 않았으며 결과 자료로 보관했다.

최종 서비스 코드에는 트랜잭션 실험 변경이 남아 있지 않다.

원본 결과와 JFR은 `results/`에, 회원 기준 파일과 PID·로그는 `.local/`에 보관하고 Git에서 제외했다.

개인 실험용 공개 비밀번호는 테스트 코드에 포함돼 있다. 실제 서비스 인증 정보가 아니다. 실행 중 발급된 토큰·쿠키 원문을 측정 출력에 기록하지 않도록 구성했다.

이 실험의 한계:

- 응답 시간 SLO와 최대 허용 부하를 확정한 수용 테스트가 아님
- 200 VU에서 요청·대기를 반복한 제한된 로그인 시나리오
- 동시 요청 2,000건 검증이 아님
- 외부 소셜 로그인·재발급·로그아웃 반복 부하는 포함하지 않음
- 요청별 실제 사용 가능성과 모든 인증 예외 조합을 부하 중 검증한 것은 아님
- 같은 Mac의 공유 자원과 실행 순서에 따른 편차 존재
- 장시간 안정성·배포 환경의 최대 처리량을 증명하지 않음
