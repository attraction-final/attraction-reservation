# 내 정보 조회 — 2,000건 집중 요청 검증과 DB 연결 풀 비교

## 목적과 결론

기존의 2,000 VU 반복 부하 측정과 구분하여, 서로 다른 회원 2,000명이 내 정보 조회를 각각 한 번씩 집중적으로 요청하는 상황을 확인했다.

개인 실험 환경에서 2,000건씩 3회 실행한 결과, 총 6,000건이 모두 성공했고 회원 정보 검증 18,000개가 통과했다. HTTP 실패와 중단 반복은 없었다.

실행별 HTTP 응답 시간 P95는 767.19~832.21ms였으며, 중앙값은 798.91ms였다. 부하 도구의 HTTP 호출 시작 시각 분산은 27~65ms였다.

위 결과는 최초 집중 요청 검증 결과다. 이후 전체 호출 경과 시간 계측과 별도 JFR 진단을 추가하고, DB 연결 풀 10개와 20개를 각각 3회 비교했다.

후속 비교에서는 전체 호출 경과 시간 P95의 실행별 중앙값이 1,587.05ms에서 1,442.05ms로 9.14% 감소했다. HTTP 응답 P95 중앙값은 822.97ms에서 563.39ms로 31.54% 감소했다.

서비스 코드는 변경하지 않았다. 개인 실험 설정만 변경했으며, 운영 설정에 적용한 결과는 아니다.

## 확인하려는 질문

- 2,000건의 조회 요청을 짧은 시간에 집중시켰을 때 누락·오류 없이 처리되는가?
- 응답이 각 요청 회원의 정보와 정확하게 일치하는가?
- HTTP 응답 시간 P95가 실험 목표인 2초 미만인가?
- 부하 발생기에서 요청 호출이 충분히 짧은 시간에 집중되는가?

이는 개인 환경의 실험 목표이며, 팀에서 합의한 운영 SLO는 아니다.

## 도구 검증과 부하 확대

먼저 실제 API로 회원 10명의 로그인과 본인 정보 조회를 확인했다.

조회 응답의 ID·이메일·닉네임·권한·상태·가입 방식과 필드 구성을 준비한 회원 정보와 비교했다. 초기 검사에서는 기대값에 가입 방식 필드가 빠져 실패했으며, 현재 응답 DTO에 맞게 검사 기준을 수정한 후 10명 모두 통과했다.

이후 요청 수를 단계적으로 늘렸다.

| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 10건 | 10건 | 30개 | 52.16ms | 53.21ms | 53.23ms | 1ms |
| 100건 | 100건 | 300개 | 89.26ms | 112.71ms | 114.19ms | 6ms |
| 500건 | 500건 | 1,500개 | 277.15ms | 414.81ms | 420.84ms | 11ms |

각 단계는 1회 탐색 실행이며, 모두 중단 없이 완료됐다. 요청 수가 다른 실행 간 차이를 성능 개선율로 해석하지 않았다.

## 최초 2,000건 집중 요청 검증

| 지표 | 1회차 | 2회차 | 3회차 |
| --- | ---: | ---: | ---: |
| 조회 성공 | 2,000건 | 2,000건 | 2,000건 |
| 검증 통과 | 6,000개 | 6,000개 | 6,000개 |
| 중단 | 0건 | 0건 | 0건 |
| 평균 | 391.94ms | 418.01ms | 403.00ms |
| P95 | 767.19ms | 832.21ms | 798.91ms |
| P99 | 800.01ms | 865.97ms | 820.78ms |
| 호출 시각 분산 | 27ms | 65ms | 29ms |
| k6 종료 코드 | 0 | 0 | 0 |

- 총 조회 성공: 6,000건
- 총 응답 검증 통과: 18,000개
- HTTP 실패·시간 초과·중단: 0건
- 실행별 P95 중앙값: 798.91ms

중앙값은 실행별 P95 세 개의 중앙값이다. 요청 6,000건을 합쳐 계산한 P95가 아니다.

세 실행에 저장된 소스 커밋·JAR 해시·앱 설정·부하 스크립트가 동일한지 확인했다.

## 후속 진단과 연결 풀 개선 비교

### 변경 근거

별도 진단 실행에서 2,000건 모두 성공했지만, 전체 호출 경과 시간 P95는 2,703ms로 HTTP 응답 P95 1,648.66ms보다 길었다. HTTP 연결 준비 구간의 지연도 함께 관측됐다.

JFR의 대기 이벤트 중 클라이언트 요청 구간과 겹치고, 스택에 Hikari 연결 획득 경로가 포함된 이벤트를 확인했다.

- 해당 대기 이벤트: 3,989개
- 이벤트 지속 시간 평균: 121.97ms
- 최대: 251.60ms
- 관측 경로: `ConcurrentBag.borrow → HikariPool.getConnection → … → UserService.getMe`
- 같은 구간과 겹치는 GC 일시 정지: 11개, 합계 약 63.30ms

요청 구간은 k6의 전체 호출 경과 시간 표본과 기록 시각을 이용해 근사했다. JFR 이벤트 수는 요청 수가 아니며, 여러 스레드의 대기 시간을 합쳐 전체 응답 시간으로 해석하지 않았다.

DB 연결 획득 대기가 관측돼 최대 연결 수 확대를 개선 후보로 선택했다. HTTP 연결 준비 지연도 있으므로 DB 연결 풀만이 유일한 원인이라고 판단하지 않았다.

### 비교 방법

- 최대 DB 연결 수만 10개에서 20개로 변경
- 동일 JAR·부하 스크립트·회원 집합 사용, 토큰은 실행 전 재발급
- 설정별 앱 재시작 후 2,000건 예열 1회
- 설정별 본 측정 3회, 측정 중 JFR 미사용
- 주지표: 전체 호출 경과 시간 P95
- 보조 지표: HTTP 응답 시간과 구간별 시간, 정확성·오류·호출 시각
- 변경 후 본 측정에는 유휴 잠자기 방지용 `caffeinate -i` 추가

### 실패 실행과 제외 근거

- 20개 예열: 조회와 검증은 모두 성공했지만 호출이 예정 시각보다 약 19.6초 늦어 종료 코드 99였다. 호출 분산은 23ms였다. 이후 현재 호스트·컨테이너 시각에서 큰 차이는 확인되지 않았지만 당시 지연 원인은 확정하지 못했다. 예열은 양쪽 모두 한 번만 수행했다.
- 20개 첫 측정 시도: 토큰 예상 유효 시간이 지난 상태여서 setup에서 중단됐다. 조회 시도 0건, 종료 코드 107로 측정값이 없었다.
- 위 기록은 삭제하지 않았다. 예열과 요청 미실행 결과를 성능 비교에 넣지 않았다.
- 20개 정상 1회차 결과 폴더는 `user-me-burst-pool20-measure-01-retry-01`이다. 나머지는 각 풀의 `measure-02`, `measure-03`이다.

### 재현 시 주의

현재 설정은 연결 풀 20개다. 전후 비교를 재현하려면 10개와 20개 각각에서 설정을 확인하고 앱을 재시작한 뒤 같은 예열·본 측정 절차를 수행한다.

재현 시에는 잠자기 방지를 포함한 실행 조건을 양쪽에 동일하게 적용하고, 실행 순서와 시간 차이도 기록한다. 기존 결과를 덮어쓰지 않는다.

## 수치 해석과 한계

### 호출 집중과 서버 내부 동시 처리는 다르다

공통 시작 시각을 정하고 각 VU가 대기 후 조회를 호출했다. 기록한 시각은 부하 도구에서 HTTP 함수를 호출하기 직전의 시각이다.

따라서 “부하 도구에서 2,000건의 호출을 27~65ms 안에 시작했다”고 설명할 수 있다. 서버에 같은 순간 도착했거나 서버 내부에서 정확히 2,000건이 동시에 처리됐다고 단정할 수는 없다.

### HTTP 응답 시간과 전체 대기 시간은 다르다

HTTP 응답 시간은 `response.timings.duration`이다. 후속 비교에는 HTTP 호출 직전부터 반환 직후까지 `Date.now()` 차이로 측정한 전체 호출 경과 시간도 추가했다.

전체 호출 경과 시간은 연결 준비 등을 포함하지만, 시작 시각까지의 15초 대기와 응답 반환 후 JSON 해석·검증은 포함하지 않는다. 밀리초 단위의 클라이언트 관측값이다.

개선 비교의 주지표는 전체 호출 경과 시간 P95로 정했다. `httpBlocked`와 `httpConnecting`은 겹치는 구간이 있을 수 있어 단순 합산하지 않는다.

15초의 공통 시작 대기는 응답 시간에 포함되지 않는다. 반면 Counter의 초당 건수에는 실행 대기 구간이 반영되므로, 출력된 rate를 서버의 최대 처리량으로 사용하지 않았다.

### 환경과 실행 순서의 영향이 있다

앱과 부하 발생기가 같은 Mac의 자원을 공유했다. 로그인 준비와 앞선 실행에 따른 캐시·JIT 예열 등의 영향도 있을 수 있다.

2,000건 실행의 응답 시간이 1,000건 탐색보다 낮았지만, 이를 요청 수 증가에 따른 성능 향상으로 해석하지 않았다.

최초 검증과 후속 비교 측정을 직접 비교하지 않는다. 별도 JFR에서 DB 연결 획득 대기가 관측됐지만, 연결 풀 변경 후 같은 방식의 JFR을 수집하지 않았으므로 대기 감소 자체를 전후 비교로 입증한 것은 아니다.

### 검증 범위

이번 결과는 개인 환경의 내 정보 조회 API에 대한 짧은 집중 요청 결과다.

다음은 검증하지 않았다.

- 배포 환경의 전체 서비스 동시 사용자 2,000명 수용
- 2,000건 집중 요청이 계속 반복되는 상황
- 장시간 안정성
- 로그인·주문 등 여러 API가 섞인 사용 흐름
- 최대 처리량

## 최종 판단

개인 환경에서 내 정보 조회 2,000건 집중 요청이 3회 모두 설정한 정확성·HTTP 응답 시간·호출 시각 기준을 충족했다.

최초 검증 후 JFR에서 관측한 DB 연결 획득 대기를 근거로 최대 연결 수 10개와 20개를 비교했다.

전체 호출 경과 시간 P95가 감소하고 정확성이 유지돼, 20개를 이번 개인 실험 조건의 유효한 개선 후보로 판단했다. 현재 개인 실험 설정은 20개로 보관한다. 운영 설정은 변경하지 않았다.

같은 Mac의 공유 자원, 실행 순서와 시간 차이, 변경 후 추가한 잠자기 방지 조건이 있어 감소분 전체를 연결 풀 변경의 인과 효과로 확정하지 않는다. 다른 부하와 배포 환경에 최적값을 일반화하지 않는다.

기존의 반복 부하 실험과 이번의 집중 요청 검증은 요청 방식과 실행 조건이 다르므로 결과를 직접 비교하지 않는다.

## 파일 구성

| 파일 | 역할 |
| --- | --- |
| `application-perf.yaml` | 전용 DB·포트·연결 풀·예약 작업 설정 |
| `start-app.py` | 개인 실험 앱 실행 |
| `prepare-users.py` | 실제 회원가입 API로 전용 회원 준비 |
| `check-user-me.py` | 로그인 및 본인 정보 조회 기능 검사 |
| `prepare-tokens.py` | 측정 전 접근 토큰 준비 |
| `user-me-burst.js` | 회원별 조회 1회, 정확성·HTTP 응답 시간·전체 호출 경과 시간·호출 시각 기록 |
| `.gitignore` | 로컬 인증 자료와 원본 결과 제외 |

## 실행 방법

저장소 루트에서 실행한다. 개인 MySQL·Redis와 전용 앱이 준비돼 있어야 한다. 실행 설정은 이 실험 전용이며 운영 환경에 사용하지 않는다.

빈 전용 DB에서 앱을 시작하면 Flyway가 스키마를 생성한다.

```bash
python3 perf/user-me-burst/start-app.py
```

최초 기능 확인은 회원 10명으로 수행한다.

```bash
python3 perf/user-me-burst/prepare-users.py --users 10
python3 perf/user-me-burst/check-user-me.py user-me-smoke-01
```

본 측정용 회원을 준비한다.

```bash
python3 perf/user-me-burst/prepare-users.py --users 2000
```

아래 측정 블록은 토큰 발급 성공 직후 부하 실행을 이어서 수행한다. 복사한 명령 사이에 장시간 대기하지 않는다.

아래 예시의 결과 폴더는 새 이름이어야 한다. 이미 존재하면 중단하고 다른 이름을 사용한다.

```bash
mkdir perf/user-me-burst/results/user-me-burst-2000-example-01
```

결과 폴더 생성에 성공한 뒤 실행 조건을 보관한다.

```bash
cp perf/user-me-burst/user-me-burst.js \
perf/user-me-burst/results/user-me-burst-2000-example-01/

cp perf/user-me-burst/application-perf.yaml \
perf/user-me-burst/results/user-me-burst-2000-example-01/

git rev-parse HEAD \
> perf/user-me-burst/results/user-me-burst-2000-example-01/source-commit.txt

shasum -a 256 build/libs/attraction-reservation-0.0.1-SNAPSHOT.jar \
> perf/user-me-burst/results/user-me-burst-2000-example-01/app-jar-sha256.txt
```

측정을 실행한다.

```bash
python3 perf/user-me-burst/prepare-tokens.py --users 2000 &&
caffeinate -i docker run --rm \
--user "$(id -u):$(id -g)" \
-v "$PWD/perf:/scripts:ro" \
-v "$PWD/perf/user-me-burst/results/user-me-burst-2000-example-01:/results" \
-e VUS=2000 \
grafana/k6@sha256:3e4186aea62e11a45560bfc51e19eeafe82fc07ce069c78aff44b7ff893d9a5e \
run --out json=/results/metrics.json \
/scripts/user-me-burst/user-me-burst.js \
> perf/user-me-burst/results/user-me-burst-2000-example-01/console.log 2>&1

perf_burst_exit=$?
echo "$perf_burst_exit" \
> perf/user-me-burst/results/user-me-burst-2000-example-01/exit-code.txt
```

`summary.json`, `burst-report.json`, `console.log`, 종료 코드를 확인한다. 기준을 충족하지 못한 경우에도 결과를 보관한다.
## 검증과 자료 보관

후속 연결 풀 비교 6회에서도 총 12,000건 성공·검증 36,000개 통과·HTTP 실패 및 중단 0건을 확인했다. 저장된 커밋·JAR 해시·부하 스크립트는 동일했고, 앱 설정 차이는 최대 DB 연결 수 한 항목이었다.


- 회원·인증 관련 테스트와 bootJar 통과
- 회원 10명의 로그인 및 본인 정보 조회 검사 통과
- 10·100·500·1,000건 탐색 실행 통과
- 2,000건 본 측정 3회 기준 충족
- 세 실행의 커밋·JAR 해시·앱 설정·부하 스크립트 일치 확인
- 원본 결과와 요약 파일 별도 압축 백업

`.local/`과 `results/`는 Git에서 제외한다.

접근 토큰은 `.local/accounts.json`에만 저장하고 파일 권한을 600으로 설정한다. 토큰·쿠키·비밀번호 원문은 결과 보고서에 기록하지 않는다. 결과 백업에도 `.local/`은 포함하지 않는다.
