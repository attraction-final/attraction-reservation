# 운영 api 오토스케일링 — 부하 중 확장 검증과 헬스체크 조정

## 목적과 결론

운영 ECS api 서비스(CPU 60% 목표 추적, task 1~3개)가 부하를 받을 때 실제로 확장되고, 확장 뒤 요청을 처리하는지 확인했다.

처음 측정에서는 확장이 사실상 동작하지 않았다. 부하로 느려진 task가 대상 그룹 헬스체크에 실패해 교체되기를 반복했고, 그 사이 CPU 지표가 끊겨 확장이 17분 뒤에야 시작됐다. 실패율은 45.3%였다.

대상 그룹 헬스체크 판정 기준만 바꾼 뒤 같은 조건으로 다시 측정했다. 7분 뒤 2개, 10분 뒤 3개로 확장됐고, 확장이 끝난 뒤에는 초당 600건을 실패 없이 p95 19~29ms로 처리했다. 전체 실패율은 2.7%였다.

## 확인하려는 질문

- CPU가 목표를 넘으면 task가 늘어나는가? 얼마나 걸리는가?
- 확장이 끝난 뒤 같은 부하를 실패 없이 처리하는가?
- 확장 중에 요청이 실패하는가?

## 환경과 조건

| 항목 | 조건 |
| --- | --- |
| 대상 | 운영 `GET https://api.xevbn.click/api/attractions` (공개 조회 API) |
| 일시 | 2026-11-18 18:10~19:52 KST (꺼 둔 인프라를 다시 켜서 측정) |
| api task | 1 vCPU / 2GB, 1~3개, CPU 평균 60% 목표 추적 (확장 대기 60초, 축소 대기 300초) |
| 부하 도구 | k6 v2.2.0, 개인 PC(Windows)에서 인터넷으로 호출 |
| 부하 방식 | `constant-arrival-rate` 초당 600건, 최대 VU 1,500, 요청당 제한 10초 |
| 측정 시간 | 기준값 10분, 확장 측정 각 25분 |
| 시작 상태 | 매 측정 api task 1개 |

초당 600건은 task 1개는 포화되고 3개면 여유가 있는 부하로 골랐다. 2026-11-11 측정에서 task 1개가 초당 약 366건에서는 p95 24ms였고, 초당 약 678건에서는 CPU 98%·p95 1.42s였다.

응답 시간은 인터넷 구간을 포함한 k6 기준이다.

## 실행

```bash
cd perf/autoscale
k6 run -q --out csv=.local/after.csv autoscale.js           # 기본: 초당 600건, 25분
k6 run -q -e DURATION=10m --out csv=.local/baseline.csv autoscale.js
```

환경 변수 `BASE`, `RATE`, `DURATION`, `MAX_VUS`로 대상과 부하를 바꾼다. `.local/`의 결과 파일은 수백 MB라 커밋하지 않는다.

운영에 부하를 거는 테스트다. 실행 전에 대상과 시간을 팀에 알린다.

## 원인: 헬스체크가 과부하를 장애로 판정

ALB는 서비스 포트(8080)의 `/readyz`로 task를 확인한다. 부하로 요청이 쌓이면 헬스체크 요청도 그 뒤에서 기다리다가 5초 제한을 넘긴다.

- 두 번 연속 실패하면 unhealthy가 되고 ECS가 task를 교체했다. 교체 중에는 정상 task가 0개가 되어 실패가 몰렸다.
- 새 task는 healthy가 되려면 5번 연속 성공(2분 30초)해야 했다. 뜨자마자 쌓인 요청을 받아 그 전에 다시 실패했다.
- task가 계속 바뀌어 CPU 지표가 끊겼고, 확장 조건(60% 초과가 3분 연속)이 늦게 채워졌다.

서비스 포트가 요청을 받지 못하면 task를 빼야 한다는 설계는 유지했다. 판정 기준만 바꿨다 (`deploy/terraform/alb.tf`).

| 항목 | 이전 | 변경 | 이유 |
| --- | --- | --- | --- |
| `interval` | 30 | 15 | 판정 주기를 줄인다 |
| `timeout` | 5 | 10 | 과부하로 느려진 응답을 실패로 보지 않는다 |
| `healthy_threshold` | 5 | 2 | 새 task가 시작 대기(120초) 안에 healthy가 된다 (30초) |
| `unhealthy_threshold` | 2 | 4 | 멈춘 task를 빼는 시간은 약 1분으로 같게 둔다 |

## 한계와 남은 일

- 확장 중(8~15분)에는 실패가 남았다. 이 구간에 헬스체크 실패로 인한 교체가 2회 있었고, 새 task가 예열되기 전에 요청을 받은 영향으로 본다. 대상 그룹 `slow_start`로 새 task에 요청을 천천히 늘리는 방법을 검토한다.
- task 1개에서 3개까지 10분이 걸린다. 급격한 부하에는 늦다. 최소 task 수를 2로 두는 것도 검토한다(단일 장애점 제거와 함께).
- 조회 API 하나로만 측정했다. 결제·예약처럼 DB 쓰기가 많은 흐름의 확장 효과는 확인하지 않았다.
- 측정마다 1회만 실행했다.
