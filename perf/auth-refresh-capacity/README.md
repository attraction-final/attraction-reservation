# 토큰 재발급 — 부하 확대와 로그아웃 경합 검증

## 목적과 현재 결론

기존 10 VU 기준 실험을 확장하여 재발급 반복 부하와
재발급·로그아웃 경합 상황의 정확성을 확인했다.

200 VU 반복 측정 3회에서 재발급 35,400건과 응답 검증
247,800개가 통과했다. 각 실행 후 회원 200명의 Redis 갱신 토큰
해시와 절대 만료 시각이 유지됨을 확인했다.

경합 검사 30회에서는 로그아웃 완료 후 새로 보낸 재발급 90건이
모두 401로 거절됐고, Redis 토큰 키는 삭제된 상태를 유지했다.

현재 측정에서 추가 성능 변경을 정당화할 뚜렷한 병목은
확인하지 못했다. 애플리케이션 성능 코드와 인증 정책은 변경하지 않았다.

이 결과는 검사한 조건의 정확성과 성능 기록이다.
전체 서비스의 동시 사용자 2,000명 수용 능력을 검증한 결과는 아니다.

## 기존 실험과 이번 실험의 차이

| 항목 | 기존 perf/auth-refresh | 이번 실험 |
|---|---|---|
| 반복 부하 | 10 VU 기준 측정 | 10 → 50 → 100 → 200 VU |
| 로그인 준비 | k6 실행 안에서 준비 | 측정 시작 전에 준비 |
| 시간 기록 | 재발급 HTTP 응답 시간 | HTTP 응답 시간과 전체 호출 시간 |
| Redis 검사 | 별도 기본 검사 | 각 부하 실행 후 참여 회원 전체 검사 |
| 로그아웃 검사 | 순차적인 무효화 확인 | 재발급과 로그아웃의 요청 구간을 겹쳐 검사 |

기본 API 검사는 새 환경의 동작을 확인하기 위해 재사용했다.
기존 실험과 측정 조건이 다르므로 시간 차이를 개선 효과로 계산하지 않는다.

## 환경과 측정 조건

| 항목 | 조건 |
|---|---|
| 기준 커밋 | c3682c30 |
| 전용 MySQL DB | attraction_auth_refresh_capacity_perf |
| Redis 논리 DB | 3 |
| 앱 / 관리 포트 | 18094 / 18095 |
| 최대 DB 연결 수 | 10개 |
| 회원 | ACTIVE / USER / LOCAL, VU별 서로 다른 회원 |
| 실행 환경 | 같은 Mac의 앱·MySQL·Redis·k6가 자원 공유 |
| 부하 방식 | 일정한 VU 수로 60초 반복 |
| 반복 간 대기 | 요청·검증 후 1초 |
| 로그인 | 부하 시작 전에 준비 |
| k6 | 고정된 이미지 SHA256 사용 |

이 부하는 요청과 대기를 반복하는 폐쇄형 부하다.
200 VU는 초당 200건 고정 유입이나 200건 동시 서버 처리를 뜻하지 않는다.

재발급은 접근 토큰만 발급한다.
갱신 토큰을 교체하거나 Redis 절대 만료 시각을 연장하지 않는
현재 정책을 검사했다.

## 지표 정의

- HTTP 응답 시간: k6 response.timings.duration
- 전체 호출 시간: HTTP 호출 직전부터 반환 직후까지의 경과 시간
- 전체 호출 시간에는 이후 응답 검증과 반복 간 대기를 포함하지 않음
- 전체 호출 시간은 서버 내부 처리 시간과 다름

### 정확성

- 3회 합계 재발급 35,400건 성공
- 응답 검증 247,800개 통과
- HTTP 및 업무 실패율 0
- 완료 반복 수 대조와 중단 반복 0건 확인
- 실행별 회원 200명의 Redis 토큰 해시·절대 만료 시각 유지 확인

응답에서는 HTTP 상태, 업무 성공, 접근 토큰 응답 형식,
대상 회원 ID·토큰 유형·유효 기간 및 갱신 토큰 미발급 등을 확인한다.
k6의 JWT 내용 해석은 서명 검증을 대신하지 않는다.

별도 기본 API 검사에서 정상 재발급 20건과 본인 정보 조회 20건,
쿠키 누락·잘못된 토큰·CSRF 누락·로그아웃 후 토큰 거절을 확인했다.

## 재발급·로그아웃 경합

서로 다른 회원 30명에 대해 회원별 재발급 요청과 로그아웃 요청을
함께 시작했다. 회원 간 검사는 순차 진행했다.

### 검사 기준

- 로그아웃은 HTTP 200 및 업무 성공
- 경합 중 재발급은 처리 순서에 따라 200 또는 401 허용
- 재발급 성공 시 접근 토큰 응답 형식 확인
- 두 요청 종료 후 Redis 토큰 키 삭제 확인
- 로그아웃 완료 후 새로 보낸 재발급 3건은 모두 401
- 후속 요청 이후에도 Redis 토큰 키가 다시 생기지 않아야 함

### 결과

| 항목 | 결과 |
|---|---:|
| 검사 횟수 | 30회 |
| 부하 도구 기준 요청 구간 겹침 | 30회 |
| 경합 중 재발급 200 | 30회 |
| 경합 중 재발급 401 | 0회 |
| 로그아웃 성공 | 30회 |
| 로그아웃 완료 후 재발급 거절 | 90건 |
| 종료 후 Redis 토큰 키 | 30명 모두 삭제 유지 |

경합 중 재발급 200은 로그아웃 삭제 전에 토큰 검사를 통과했을 수 있다.
응답 순서만으로 서버 내부 처리 순서를 확정하지 않는다.

서버 내부 처리 순서를 강제하지 않았고,
경합 중 재발급 401 경로는 이번 실행에서 관측하지 못했다.
모든 실행 순서의 안전성을 증명한 결과는 아니다.

이미 발급된 접근 토큰은 로그아웃으로 즉시 무효화하는 정책이 아니다.
이번 검사는 갱신 토큰 무효화와 후속 재발급 거절을 대상으로 한다.

## 성능 변경을 추가하지 않은 이유

검사한 부하에서 실패나 Redis 상태 이상은 없었다.
실행 간 지연 변동은 있었지만 특정 병목을 확정하지 못했다.

사전에 지연 목표를 정한 실험이 아니므로 성능 목표 달성이나
운영 환경의 충분한 수용 능력을 선언하지 않는다.
측정 근거 없이 연결 풀·캐시·인증 정책을 변경하지 않았다.

| 상태 | 범위 |
|---|---|
| 완료 | 기본 API 정책 검사 |
| 완료 | 10 → 200 VU 재발급 반복 부하 |
| 완료 | 200 VU 3회 측정과 Redis 상태 대조 |
| 완료 | 재발급·로그아웃 경합 30회 |

허용 지연·실패율·데이터 정확성·유지 시간을 정한다.

재발급 집중 요청은 토큰 만료 시점이 몰리는 상황을 확인하는 별도 실험이다.
모든 도메인에 같은 수의 요청을 보내는 것을 전체 서비스 검증으로 보지 않는다.

## 도구 역할

| 도구 | 역할 |
|---|---|
| Java | 실제 인증·재발급·로그아웃 처리 |
| Docker | MySQL·Redis·k6 실행 |
| k6 | 반복 부하 발생과 시간·응답 측정 |
| Python | 회원·세션 준비, 결과 기록, Redis 대조와 경합 검사 |

Python 경합 검사는 정확성 검사이며 k6 성능 수치와 합산하지 않는다.

## 실행과 보관

전용 DB와 앱을 준비한 뒤 회원을 준비한다.

    python3 perf/auth-refresh-capacity/prepare-users.py --users 200 < /dev/null

새 이름으로 반복 부하를 실행한다. 세션 준비는 자동으로 진행한다.

    caffeinate -i python3 perf/auth-refresh-capacity/run-refresh.py 새-측정-이름 --vus 200 < /dev/null

부하와 검증이 끝난 뒤 별도 이름으로 경합 검사를 실행한다.

    caffeinate -i python3 perf/auth-refresh-capacity/check-refresh-logout.py 새-경합-이름 --trials 30 < /dev/null

결과 이름은 재사용하지 않는다. 중복 이름으로 중단된 실행은 측정에 포함하지 않는다.
같은 회원을 사용하는 로그인·부하·경합 검사를 동시에 실행하지 않는다.
부하 종료 후 Redis 대조가 끝나기 전에 세션을 다시 준비하지 않는다.

기본 check-refresh.py는 회원 기준 10명을 요구한다.
회원 수를 확대한 상태에서 기본 검사를 재실행하려면 이 조건을 확인한다.

각 부하 결과 폴더에 커밋·소스 변경·JAR 해시·설정·도구 사본,
k6 결과·검증 결과·자원 표본을 보관한다.
JAR 해시만으로 실행 중 JVM이 해당 파일을 로드했음을 증명하지는 않는다.

경합 결과에는 실행 도구 사본, 응답 상태, 요청 구간 겹침,
후속 거절 및 Redis 검사 결과를 보관한다.
경합 검사는 부하 측정과 동일한 전체 환경 증빙을 별도로 수집하지 않았다.

.local/의 원문 인증 정보와 results/는 Git에서 제외한다.
토큰·쿠키·비밀번호 원문을 결과 파일이나 화면에 출력하지 않는다.

2026-11-10 백업: auth-refresh-capacity-20261110.tar.gz
백업은 results/를 포함하고 .local/은 제외했다.
