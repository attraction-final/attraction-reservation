# 원장과 PG의 불일치: 어떻게 어긋나고, 어떻게 막고 되돌렸나

결제·환불을 구현하면서 가장 중요하게 본 것은 **원장(우리 DB)과 PG(PortOne)가 서로 다른 사실을 말하는 상황**이다.
"고객 돈은 나갔는데 주문은 취소됨", "환불 완료로 기록했는데 실제로는 환불되지 않음", "환불이 두 번 나감" 같은 상황은 고객에게 직접 피해가 가고, 나중에 발견하기도 어렵다.

이 문서는 불일치를 유형별로 나눠, 각각 어떤 상황에서 생기는지, 어떤 방법을 고민했고 왜 지금 방식을 택했는지, 무엇이 아직 남았는지를 정리한다.
동작 명세는 기능별 문서에 있고, 각 절 끝의 "더 보기"는 필요할 때만 열면 된다.

## 0. 배경

### 용어

| 용어 | 뜻 |
|---|---|
| 원장 | 우리 DB의 결제(`payments`), 환불(`refunds`), 보상 요청(`payment_compensations`) 기록 |
| PG | PortOne. 실제로 돈이 움직이는 곳 |
| `pgId` | 결제마다 우리가 발급하는 UUID. PortOne `paymentId`로도 쓰여 원장과 PG를 잇는 키다 |
| 승인 | PG에서 결제가 끝난 것을 확인하고 원장을 `PAID`로 바꾸는 일 |
| 보상 | PG에서는 결제됐지만 원장에 반영하면 안 되는 결제를 PG에서 **전체 취소**하는 일 |
| 환불 | 고객 요청으로 결제의 전부 또는 일부를 PG에서 **부분 취소**하는 일 |
| 점유 | 스케줄러·요청 스레드 여러 곳이 같은 처리 대상을 고를 때, 행을 잠그고 `PROCESSING`으로 바꿔 한 곳만 처리하게 하는 것 |
| `DEAD` | 자동으로 맞출 수 없어 사람이 확인해야 하는 상태. ERROR 로그를 남긴다 |

### 결제가 원장에 반영되는 세 경로

```
고객 ── 결제창(PortOne) ── 결제 완료
  │
  ├─ ① 승인 API     POST /api/payments/{pgId}/confirm   (고객 브라우저가 호출)
  ├─ ② 웹훅          PortOne → 우리 서버                  (PortOne이 호출)
  └─ ③ 만료 자동 취소  30분 지난 PENDING 주문 정리           (스케줄러)

세 경로 모두: PG 조회 → 원장과 비교 → 원장 반영
```

세 경로는 같은 결제에 대해 순서 없이, 동시에, 중복으로 들어올 수 있다.

### 왜 어긋나는가

1. **원장과 PG를 한 트랜잭션으로 묶을 수 없다.** DB 커밋과 PG 호출 중 하나만 성공하고 서버가 죽을 수 있다(dual write).
2. **PG 호출이 타임아웃되면 결과를 모른다.** PG는 처리했는데 응답만 못 받았을 수 있다.
3. **웹훅은 늦거나 오지 않을 수 있고, 고객이 승인 API를 호출하지 않을 수도 있다**(결제 후 탭을 닫는 경우).
4. **여러 경로가 같은 결제를 동시에 바꾼다.**

### 원칙

모든 결정은 아래 네 원칙에서 나왔다.

1. **돈이 움직였는지는 PG가, 움직여야 할 금액과 상태는 원장이 기준이다.** 클라이언트가 보낸 금액이나 웹훅 본문은 믿지 않고 항상 PG를 다시 조회한다.
2. **트랜잭션 안에서 PG를 호출하지 않는다.** "무엇을 할지"를 먼저 커밋하고, 커밋 뒤에 PG를 호출한다.
3. **결과를 모르면 다시 보내지 않고 조회로 확정한다.** 모르는 상태를 실패로 뭉개면 재시도가 중복 취소를 만든다.
4. **자동으로 맞출 수 없으면 추측하지 않고 사람에게 넘긴다.**

## 1. PG는 결제됐는데, 원장은 모르거나 취소·실패로 두었다

**가장 피해가 큰 불일치다.** 고객 돈은 나갔는데 주문은 없거나 취소된 상태다. 고객이 문의하기 전까지 우리는 모른다.

### 1-1. 승인 API가 호출되지 않았다

- **상황**: 고객이 결제를 마치고 승인 API가 호출되기 전에 브라우저를 닫는다. 원장은 `PENDING`, PG는 `PAID`.
- **고려한 방법**
  - 웹훅을 받은 스레드에서 바로 승인 처리 → 처리 중 오류가 나면 PortOne의 재전송 정책(횟수·간격)에 복구를 맡기게 된다. 웹훅 응답 시간도 PG 조회 시간에 묶인다.
  - **웹훅을 받으면 서명만 검증하고 DB에 저장한 뒤 바로 200, 처리는 스케줄러가 한다(Inbox)**
- **결정**: Inbox를 택했다. 받은 웹훅은 DB에 남아 있으므로 처리에 실패해도 우리가 1·2·4·8분 간격으로 재시도한다. 5번 실패하면 `DEAD`가 된다.
  - 웹훅 본문의 상태는 쓰지 않는다. `paymentId`만 꺼내고, 승인 API와 같은 로직으로 PG를 다시 조회해 판단한다. 웹훅 종류나 도착 순서가 뒤섞여도 결과가 같다.
- **남은 것**: 웹훅도 오지 않으면 1-2의 만료 취소가 마지막 기회다.

### 1-2. 만료 자동 취소가 결제 완료 주문을 취소했다 (KAN-131)

- **상황**: 승인 API도 웹훅도 반영되지 않은 결제 완료 주문을, 30분 만료 스케줄러가 시간만 보고 취소했다. 결과는 원장 `CANCELLED`, PG `PAID`. 보상 요청도 만들어지지 않아서 아무도 돈을 돌려주지 않는다.
- **결정**: 만료 취소 전에 PG를 조회한다(승인 API·웹훅과 같은 `syncPayment`).
  - PG에서 결제 완료가 확인되면 그 자리에서 승인하고 만료 취소하지 않는다.
  - PG에 결제가 없거나 미결제일 때만 취소한다.
  - PG 조회가 3번 연속 실패하면 PG 장애로 보고 이번 주기를 끝낸다. 장애 중에 만료 주문마다 타임아웃을 기다리지 않기 위해서다. 남은 주문은 다음 주기에 다시 확인한다.
- **남은 것**: PG 확인 **직후** 결제되고 웹훅도 오지 않으면 여전히 `CANCELLED` + `PAID`다. 이 경우는 1-3의 보상이 처리하지만, 승인 API나 웹훅 중 하나는 도착해야 한다. 둘 다 오지 않는 경우를 잡으려면 대사 배치가 필요하다(5장).

### 1-3. 고객이 취소한 뒤에 결제가 완료됐다

- **상황**: 결제창이 열린 채로 고객이 다른 탭에서 주문을 취소한다. 주문 취소와 함께 재고도 복구된다. 그 뒤 결제창에서 결제를 마친다. 원장 `CANCELLED`, PG `PAID`.
- **결정**: 주문을 되살리지 않고 PG 결제를 전체 취소(보상)한다. 주문은 이미 취소됐고 재고도 다른 고객에게 돌아갔으므로, 되살리면 재고와 어긋난다.
- **처음 구현과 문제 (KAN-37)**: 승인 처리(`approvePayment`)가 락 안에서 `CANCELLED`를 발견하면 예외를 던져 롤백하고, 바깥에서 **별도 트랜잭션**으로 보상 요청을 저장했다.
  - 롤백과 별도 저장 사이에 서버가 죽으면 보상 요청이 사라진다. 그러면 결제 완료 웹훅이 다시 오는 것에만 복구를 기대게 된다.
  - 1-4에서 없앤 dual write가 다른 모양으로 남아 있던 것이다. "예외면 롤백"이라는 기본 동작 때문에 판단과 기록이 서로 다른 트랜잭션으로 갈라졌다.
- **고친 결정 (KAN-39)**: `approvePayment`가 `CANCELLED`를 발견하면 예외 대신 **같은 트랜잭션에서 보상 요청을 저장**하고 정상 반환한다. 판단과 기록이 한 커밋에 들어가므로 둘 중 하나만 남는 경우가 없다.

### 1-4. 금액이 다르다: 결제를 실패 처리하고 PG를 취소해야 한다

- **상황**: 원장 주문 금액은 25,000원인데 PG에는 30,000원이 결제됐다(클라이언트 변조 등). 원장에 반영하면 안 되므로 결제를 실패 처리하고 PG 결제를 취소해야 한다.
- **처음 구조의 문제**: `결제 FAILED 커밋 → PG 취소 호출` 순서로 했다.
  - 커밋 직후 PG 취소가 실패하거나 서버가 죽으면 원장 `FAILED`, PG `PAID`로 남는다.
  - 이후 들어오는 요청(웹훅 재처리 등)은 결제가 이미 `FAILED`라 아무것도 하지 않는다. **다시는 복구할 기회가 오지 않는다.**
- **고려한 방법**
  1. PG 취소를 트랜잭션 안에서 호출 → PG 응답을 기다리는 동안 커넥션과 결제 락을 잡는다. PG 취소가 성공한 뒤 커밋이 실패하면 반대 방향의 불일치(원장 `PENDING`, PG 취소됨)가 생긴다.
  2. 호출한 곳에서 실패 시 재시도 → 서버가 죽으면 재시도도 함께 사라진다.
  3. **결제 실패 처리와 "PG 취소해야 함"이라는 기록(보상 요청)을 같은 트랜잭션에 커밋하고, 커밋 뒤에 PG를 호출한다(Outbox)**
- **결정**: 3번을 택했다.
  - 커밋 직후 같은 스레드에서 PG 취소를 1회 즉시 시도한다. 대부분 여기서 끝난다.
  - 실패하거나 시도 전에 서버가 죽어도 보상 요청이 DB에 남아 있으므로, 스케줄러(30초 간격)가 1·2·4·8분 백오프로 재시도한다. 5번 실패하면 `DEAD`가 되고 수동 환불한다.
  - **커밋된 보상은 반드시 PG 취소가 시도된다.** 보상 요청 저장이 실패하면 결제 실패 처리도 함께 롤백되어 다음 요청에서 다시 판단한다.
- **왜 재시도해도 안전한가**: Outbox는 같은 호출이 두 번 이상 나갈 수 있다(즉시 시도와 스케줄러가 겹치거나, 성공 후 기록 전에 죽는 경우). 보상은 **전체 취소**로 보내므로 두 번째 호출은 PG가 "이미 취소됨"으로 응답하고, 이를 성공으로 본다. 부분 취소인 환불에는 이 전제가 성립하지 않는다(4-3).

### 1-5. 세 경로가 같은 결제를 동시에 처리한다

- **상황**: 금액 불일치 결제에 승인 API, 웹훅, 만료 취소가 동시에 도착한다. 셋 다 "실패 처리 + 보상 요청"을 하면 보상 요청이 세 건이 된다. 승인과 고객 취소가 겹치면 한쪽의 변경이 사라진다(lost update).
- **결정**
  - 같은 결제를 바꾸는 모든 경로(승인, 실패 처리, 고객 취소, 만료 취소)가 결제 행을 **비관적 락**으로 조회한다. 하나라도 락 없이 바꾸면 이 보장이 깨진다.
  - 락 안에서 상태를 다시 확인한다. 실패 처리는 `PENDING`일 때만 하고 `true`를 반환하며, `true`를 받은 한 요청만 보상 요청을 만든다. `pg_id` UNIQUE 제약이 마지막 방어선이다.
  - 락 밖에서는 이미 `PAID`·`FAILED`인지 미리 보고 불필요한 PG 호출을 줄이되, 최종 판단은 락 안에서 한다.
- **낙관적 락을 버린 이유 (KAN-22)**: 처음에는 `@Version`을 썼다. 그런데 여러 경로가 같은 결제에 겹치는 것은 예외가 아니라 정상 흐름이다. 낙관적 락은 충돌 시 한쪽을 실패시키고 재시도를 호출한 쪽에 떠넘긴다.
- **바꾸다가 발견한 것**: JPA 락 타임아웃 힌트(3초)를 걸었는데 MySQL에서는 6초를 그대로 기다렸다. MySQL `FOR UPDATE`에는 대기 시간 문법이 없어 힌트가 무시된다(기본 50초). DB 연결마다 `innodb_lock_wait_timeout = 3`을 설정해 3초에 실패하는 것을 확인했다.
  - 이후 다른 곳에서도 MySQL에 대한 JPA 힌트는 실측 전까지 믿지 않았다. 웹훅 점유에서 `SKIP LOCKED`를 쓰지 않은 이유이기도 하다.

**확인 방법**: 동시 승인·취소·락 타임아웃은 Testcontainers MySQL(`PaymentServiceConcurrencyTest`)로 확인했다. 결제 실패와 보상 요청이 함께 커밋·롤백되는지는 실제 트랜잭션으로 확인했다(`PaymentCompensationOutboxTest`). 만료 취소의 PG 결과별 분기는 `OrderCancelServiceTest`로 확인했다.

## 2. 원장은 취소·환불 완료인데, PG는 취소되지 않았다

**고객은 환불됐다고 안내받았는데 돈이 돌아오지 않는다.** 원장에서는 완료라서 아무도 다시 보지 않는다.

### 2-1. HTTP 200이 취소 완료를 뜻하지 않는다 (KAN-66, KAN-67)

- **상황**: PortOne 취소 API는 HTTP 200이어도 응답 안의 취소 상태가 셋 중 하나다: `SUCCEEDED`(완료), `REQUESTED`(접수만 됨), `FAILED`(실패). 200만 보고 완료로 기록하면, 접수만 된 취소가 완료로 남는다.
- **고려한 방법**
  1. `REQUESTED`를 실패로 기록하고 재시도 → 이미 접수된 취소를 다시 보내게 된다. 접수된 취소가 나중에 처리되면 **두 번 취소된다**(원칙 3 위반).
  2. `REQUESTED`를 완료로 기록 → 이 절의 문제 그대로다.
  3. **"PG가 받았지만 결과는 모른다"는 상태를 따로 두고, 조회로만 확정한다**
- **결정**: 3번을 택했다. 보상과 환불에 `PG_PENDING` 상태를 추가했다.
  - 취소 응답이 `REQUESTED`이거나, 응답 본문을 해석하지 못했거나, 결과를 확인하지 못했으면(4-2) `PG_PENDING`이 된다.
  - `PG_PENDING`에서는 **취소를 다시 보내지 않는다.** PG 결제 조회 응답의 취소 내역(`cancellations`) 중 같은 ID의 상태로 확정한다: `SUCCEEDED`면 완료, `FAILED`면 실패(재시도), 그 밖은 다음 확인 예약.
  - 확인 간격은 1분에서 30분까지 대략 두 배씩 늘린다. 24시간 안에 확정되지 않으면 `DEAD`로 수동 확인한다.
- **함께 정한 것**: 확인마다 PG를 조회하므로, PG 장애로 `PG_PENDING`이 쌓이면 같은 스케줄러의 취소 처리가 밀린다. 그래서 한 주기의 확인 건수(5건)를 취소 처리 건수(20건)와 따로 제한했다.
- **남은 것**: 실제 PortOne 테스트 채널에서 `REQUESTED` 응답을 받아 본 적은 아직 없다. 공식 API 문서의 응답 구조를 기준으로 구현했다.

**확인 방법**: 취소 응답 상태별 반환과 해석 불가 응답은 `PortOneClientTest`로, 조회 결과별 확정은 `PaymentCompensationProcessorTest`와 환불 테스트(TC-035, TC-038)로 확인했다.

**더 보기**: [payment-compensation.md 5장](payment-compensation.md#pg-취소-결과-확인-pg_pending)

## 3. PG는 취소됐는데, 원장은 미완료로 남았다

**고객은 돈을 돌려받았는데 원장은 환불 실패·처리 중이다.** 그대로 두면 재시도가 취소를 또 보내 4장의 중복 취소로 이어진다.

생기는 경우는 세 가지다.
- PG는 취소를 처리했는데 응답이 타임아웃됐다.
- 취소 성공 응답을 받은 직후 서버가 죽었다.
- 응답은 받았는데 원장 기록(DB)이 실패했다.

### 3-1. 다시 보내기 전에 먼저 조회한다 (KAN-66)

- **상황**: 환불이 `FAILED`로 기록됐지만 실제로는 PG에서 취소됐다(타임아웃). 1분 뒤 재시도가 취소를 그대로 보내면 두 번 취소된다.
- **결정**: 재시도(두 번째 시도부터)는 취소를 보내기 **전에** PG 결제를 조회한다.
  - 보상: PG 결제가 이미 `CANCELLED`면 완료로 기록한다. 접수된(`REQUESTED`) 취소 내역이 있으면 그 내역으로 `PG_PENDING`이 된다. 둘 다 취소를 보내지 않는다.
  - 환불: `PG 취소 누적 금액 − 원장의 완료 환불 합계 = 이번 환불 금액`이면 이미 반영된 것으로 보고 완료로 기록한다. 같은 결제의 환불은 한 번에 하나씩 처리하므로(4-4) 금액으로 판단할 수 있다.
  - **조회가 실패하면 취소를 보내지 않고 실패로 기록한다.** PG 조회가 실패할 때는 취소도 실패할 가능성이 높고, 결과를 모른 채 보내지 않는 편이 안전하다.
  - 첫 시도는 보낸 적이 없으므로 조회하지 않는다.

### 3-2. 취소는 성공했는데 기록에 실패했다

- **결정**: 실패로 기록하지 않는다. 실패로 기록하면 재시도가 취소를 다시 보내기 때문이다. 대신 `PG_PENDING`으로 기록해 조회로 완료되게 한다.
  - 그것마저 실패하면 행이 `PROCESSING`으로 남는다. 5분 뒤 멈춘 처리로 보고 다시 점유될 때 3-1의 조회가 완료를 확인한다.

### 3-3. 늦게 도착한 결과가 최신 결과를 덮어쓴다 (KAN-66)

- **상황**: 처리 A가 PG 응답을 오래 기다리는 사이 5분이 지나, 처리 B가 같은 행을 다시 점유해 끝까지 처리했다. 그 뒤 A의 "실패" 결과가 도착해 B의 "완료"를 덮어쓴다. 둘 다 `PROCESSING`에서 기록하므로 상태만 보고는 구분할 수 없다.
- **결정**: 점유할 때의 시도 횟수(`attempt_count`)를 결과 기록에 함께 넘기고, 행의 값과 같을 때만 기록한다. B가 다시 점유하면서 시도 횟수가 늘었으므로 A의 결과는 거부된다.
  - `PG_PENDING` 확인 결과는 `PG_PENDING`이 된 시각(`pg_pending_since`)으로 같은 확인 주기인지 확인한다.
  - 분산 락의 fencing token과 같은 발상이다. 별도 컬럼 없이 이미 있는 값을 토큰으로 썼다.
- 다시 점유하는 기준(5분)은 PG 취소 한 번의 최대 소요 시간(통신 재시도 포함 약 48초)보다 충분히 길게 잡았다.

### 3-4. 취소 웹훅으로 원장을 PG에 맞춘다 (KAN-55, KAN-89)

- **상황**: 3-1~3-3은 우리가 다시 시도할 때 맞춰진다. 그런데 환불이 `DEAD`가 되면 더 이상 시도하지 않는다. PG에서는 취소됐는데 원장은 `DEAD`로 남는다.
- **결정**: PG에서 취소가 일어나면 PortOne이 웹훅을 보낸다. 이 웹훅을 받으면 PG를 다시 조회해 **취소된 누적 금액**으로 원장을 맞춘다.
  - `차이 = PG 취소 누적 금액 − 원장의 완료 환불 합계`

  | 차이 | 판단 | 처리 |
  |---|---|---|
  | 0 | 이미 맞음 | 변경 없음 |
  | > 0, 금액이 정확히 같은 미완료 환불(`PROCESSING`·`FAILED`·`DEAD`)이 1건 | 그 환불이 PG에 반영된 것 | 그 환불을 완료로, 결제·주문 상태도 함께 변경 |
  | < 0 | PG 조회 뒤에 다른 환불이 완료됨(조회 시점 차이) | 재시도 |
  | 그 밖(후보 없음·2건 이상) | 자동으로 판단할 수 없음 | 웹훅 `DEAD`, 수동 확인 |

  - 아직 PG에 보낸 적이 없는 `REQUESTED`는 후보가 아니다.
  - 웹훅 본문의 금액은 쓰지 않는다. 항상 PG를 다시 조회한다.
- **고친 결정 (KAN-89)**: 처음에는 차이가 음수인 경우도 "판단 불가"로 `DEAD`에 넣었다. 그런데 이것은 트랜잭션 밖에서 조회한 PG 값이 그 사이 완료된 환불보다 오래된 것일 뿐이라, 다시 조회하면 맞는다. 재시도 대상으로 바꿨다.
- **감수한 것**
  - 우리 시스템 밖의 취소(PortOne 콘솔 등) 금액이 우연히 미완료 환불 1건과 같으면, 그 환불이 완료로 처리될 수 있다.
  - 반대로 금액이 같은 후보가 2건 이상이면 맞추지 않는다. 잘못 완료하는 것보다 수동 확인이 낫다고 판단했다(원칙 4).

**확인 방법**: 재시도 전 조회의 결과별 분기와 펜싱은 `PaymentCompensationProcessorTest`, `PaymentCompensationServiceTest`, 환불 TC-037·TC-041로 확인했다. PG 취소 응답을 기다리는 동안 웹훅이 먼저 완료해도 한 번만 완료되는지는 MySQL로 확인했다(`RefundProcessorConcurrencyTest`, TC-033).

**더 보기**: [payment-compensation.md 5·6장](payment-compensation.md#재시도-전-pg-확인), [refund-requirements.md 5-2·5-3](../requirements/refund-requirements.md#5-2-환불-pg-취소-처리-트랜잭션-밖에서-pg-호출)

## 4. PG에서 의도보다 더 많이 취소됐다 (중복 환불)

**돈이 의도보다 더 나간다.** 되돌리려면 고객에게 다시 청구해야 하므로 사실상 회수가 어렵다. 2장과 3장에서 "다시 보내지 않는다"를 반복한 이유가 이것이다.

### 4-1. 멱등 키를 고정했더니 실패한 취소를 다시 할 수 없었다

- **처음 생각**: 보상 요청 하나에 멱등 키(`Idempotency-Key`) 하나를 고정하면, 몇 번을 다시 보내도 PG가 한 번만 처리하니 중복이 원천 차단된다.
- **문제**: PortOne은 같은 키의 응답을 **실패 응답까지 포함해 3시간** 저장해 돌려준다. 키를 고정하면 일시 장애로 실패한 취소를 1분 뒤 재시도해도 저장된 실패 응답만 받는다. 3시간 동안 보상이 진행되지 않고, 재시도 5번이 모두 같은 실패로 끝나 `DEAD`가 된다.
- **결정**: 멱등 키는 **취소 호출마다 새로 만들고**, 한 호출 안의 재시도(통신 실패)에서만 같은 키를 쓴다.
- **그러면 호출 사이의 중복은 무엇이 막는가**: 멱등 키 대신 아래 장치들이 막는다.
  - 보상: 전체 취소라서 두 번째는 "이미 취소됨" → 성공 처리(1-4)
  - 환불: 취소 가능 잔액을 함께 보내 PG가 거절(4-3)
  - 공통: 재시도 전 조회(3-1), 결과를 모르면 `PG_PENDING`(2-1)

### 4-2. "앞선 요청 처리 중" 응답 뒤 결과를 모르면 실패가 아니다 (KAN-90)

- **상황**
  1. 취소 요청이 타임아웃된다.
  2. 같은 키로 다시 보냈더니 PortOne이 409 `IDEMPOTENCY_OUTSTANDING_REQUEST`(같은 키의 앞선 요청을 처리 중)로 응답한다.
  3. 잠시 기다려 다시 보냈지만 재시도 횟수(3회)를 다 쓸 때까지 결과를 받지 못한다.
- **처음 구현**: 이 경우를 실패로 기록했다.
- **리뷰에서 찾은 문제**: "처리 중" 응답을 받았다는 것은 **앞선 요청이 PG에 도달했다는 증거**다. 실패로 기록하면 1분 뒤 재시도가 **새 키로** 취소를 보낸다. 앞선 요청이 아직 PG 취소 내역에 나타나기 전이라면 3-1의 조회로도 걸러지지 않아 두 번 취소된다.
- **고친 결정**: 처리 중 응답을 한 번이라도 받았으면, 마지막 시도가 통신 실패여도 실패가 아니라 `UNKNOWN`(결과 모름)을 반환한다. 호출한 쪽은 `PG_PENDING`으로 조회로만 확정한다(2-1). 처리 중 응답 없이 통신 실패만 반복됐다면 PG에 도달했다는 증거가 없으므로 기존대로 실패다.
- **함께 정한 것**: 처리 중 응답 뒤 대기 시간 설정에 상한(10초)을 두었다. 대기가 길어 한 번의 취소가 5분을 넘기면, 아직 진행 중인 처리를 다른 처리가 멈춘 것으로 보고 다시 점유한다(3-3).

### 4-3. 부분 취소는 "이미 취소됨"으로 막을 수 없다 (KAN-51)

- **상황**: 40,000원 결제에서 10,000원 부분 환불을 보냈는데 타임아웃됐다. 재시도가 10,000원을 다시 보내면 PG는 정상적으로 또 10,000원을 취소한다. 보상과 달리 두 번째 요청이 "이미 취소됨"이 되지 않는다.
- **결정**: 부분 취소에 **"이번 취소 전에 PG에 남아 있어야 할 취소 가능 잔액"**(`currentCancellableAmount`)을 함께 보낸다.
  - 원장 기준 값은 `결제 금액 − 완료된 환불 합계`(위 예에서 40,000원)다.
  - 앞선 10,000원이 이미 반영됐다면 PG의 잔액은 30,000원이라 값이 다르므로 PG가 거절한다. 같은 취소가 두 번 반영되지 않는다.
  - 이 거절은 앞선 요청이 반영됐다는 뜻일 수 있고 재시도해도 결과가 같으므로, 재시도하지 않고 바로 `DEAD`로 보낸다.
  - 기존 보상(전체 취소)의 호출 방식은 바꾸지 않고, 잔액을 받는 메서드를 따로 추가했다.
- **부분 취소의 "이미 취소됨"은 성공이 아니다**: 보상에서는 "이미 취소됨"을 성공으로 본다. 그러나 부분 취소에서 이 응답은 다른 경로(콘솔 등)로 **전체 취소**됐다는 뜻이라, 이번 환불이 반영됐다고 볼 수 없다. 성공으로 처리하면 원장의 환불 내역과 PG가 어긋나므로 `DEAD`로 보낸다.

### 4-4. 같은 결제의 환불은 한 번에 하나씩 (KAN-67, KAN-132)

- **상황**: 같은 결제에 환불 A(10,000원)와 B(5,000원)가 동시에 처리된다. A가 아직 확정되지 않았으므로 둘 다 잔액을 40,000원으로 계산해 보낸다. 먼저 반영된 쪽 때문에 다른 쪽은 잔액 불일치로 `DEAD`가 된다. 4-3의 잔액 계산은 **"앞선 취소가 모두 확정됐다"는 전제**가 있어야 맞는다.
- **결정**: 같은 결제의 환불은 PG 결과가 확정될 때까지 하나씩 처리한다. 같은 결제에 `PROCESSING`이나 `PG_PENDING` 환불이 있으면 다음 환불을 점유하지 않는다.
  - 이렇게 막힌 환불이 스케줄러 후보 목록 앞쪽을 차지하면, 매 주기 락만 잡고 건너뛰어 다른 결제의 환불까지 밀린다. 그래서 후보 조회 단계에서도 같은 규칙으로 뺐다. 최종 판단은 락 안에서 한다.
- **빠져 있던 경우 (KAN-132)**: 처음 규칙은 `FAILED` 환불을 막는 대상에 넣지 않았다.
  - 그런데 `FAILED`는 타임아웃처럼 **PG에 반영됐는지 모르는 실패**일 수 있다. A가 그런 `FAILED`일 때 B가 점유되면, A가 반영되지 않았다고 가정한 잔액을 보내 B가 바로 `DEAD`가 됐다.
  - 고친 규칙:
    - 같은 결제에 `FAILED`가 있으면 `REQUESTED` 환불은 점유하지 않는다.
    - `FAILED`끼리는 먼저 실패한 것(id가 작은 쪽)부터 재시도한다.
    - 멈춘 `PROCESSING`은 `FAILED`가 있어도 다시 점유한다. 이미 PG로 나갔을 수 있는 건을 먼저 확정해야 하고, 서로 막아 둘 다 멈추는 것을 피하기 위해서다.

### 4-5. 락을 기다렸는데도 옛날 값을 읽었다 (REPEATABLE READ)

- **상황**: 4-4의 직렬화는 결제 행을 잠근 뒤 같은 결제의 다른 환불 상태를 읽어 판단한다. MySQL 기본 격리 수준(REPEATABLE READ)에서는 락을 기다린 뒤에도 **트랜잭션의 첫 조회 시점 스냅샷**을 읽는다. 앞선 처리가 커밋한 `PROCESSING`이 보이지 않아, 같은 결제의 환불 두 건이 동시에 PG로 나가는 것을 MySQL 테스트로 확인했다.
- **결정**: 다른 처리가 커밋한 최신 상태를 읽어야 하는 곳(점유, 결제·주문 상태를 바꾸는 완료 기록, 환불 요청 기록)을 READ COMMITTED로 실행한다.
- **주의**: 격리 수준은 새 트랜잭션을 시작할 때만 적용된다. 이미 열린 바깥 트랜잭션에 참여하면 바깥의 격리 수준을 따른다. 지금은 환불 처리기에 바깥 트랜잭션이 없어서 동작한다. 호출 구조를 바꿀 때 다시 확인해야 한다.

### 4-6. 환불 가능 수량은 보수적으로 센다

- 환불 가능 수량은 `주문 수량 − 기존 환불 수량`이다. 기존 환불에는 완료된 것뿐 아니라 **모든 상태**를 포함한다.
  - `REQUESTED`·`PROCESSING`·`FAILED`는 아직 PG에서 취소될 수 있다.
  - `DEAD`는 PG에서 취소됐는지 모른다.
- 이 중 하나라도 빼고 세면, 같은 티켓분을 다시 환불받을 수 있다. 정상 환불이 수동 확인 전까지 막히는 불편보다 과환불 방지를 우선했다.

**확인 방법**: 멱등 키 동작(호출마다 새 키, 호출 안 재시도는 같은 키, 처리 중 응답 뒤 `UNKNOWN`)은 `PortOneClientTest`로 확인했다. 아래는 Testcontainers MySQL로 확인했다.
- 즉시 시도와 스케줄러가 같은 환불을 6번 동시에 처리해도 PG 취소는 1번(TC-022)
- 같은 결제의 환불 2건은 PG 호출이 한 번에 1건이고, 두 번째의 잔액은 첫 번째를 뺀 값(TC-023)
- `PG_PENDING` 환불이 있으면 다음 환불을 점유하지 않음(TC-036)
- `FAILED` 차단 규칙(TC-048~050)

## 5. 원장이 모르는 PG 변경

우리 시스템을 거치지 않고 PG가 바뀌는 경우다. 원장에는 그 변경을 일으킨 기록이 없으므로, 무엇에 맞춰야 할지 자동으로 판단할 수 없다.

| 상황 | 현재 처리 | 남은 것 |
|---|---|---|
| PortOne 콘솔에서 직접 취소 | 취소 웹훅에서 금액 차이를 설명할 미완료 환불이 없으므로 웹훅 `DEAD` + ERROR 로그(3-4) | 확인 수단과 수동 처리 절차 |
| 콘솔에서 전체 취소한 결제에 고객이 부분 환불 요청 | PG가 "이미 취소됨"으로 응답 → 환불 `DEAD`(4-3). 결제·주문은 `PAID`로 남음 | 결제·주문 상태를 수동으로 맞춰야 함 |
| 만료 취소의 PG 확인 직후 결제 + 웹훅 미수신 + 승인 API 미호출 | 잡히지 않음(1-2) | **대사 배치** |

- **이미 결제 완료인 결제의 웹훅도 PG를 조회하게 바꾼 이유**: 외부 취소를 감지하려면 결제 완료 이후의 웹훅도 PG를 다시 봐야 한다.
  - 대가로 PG 장애 중에는 예전엔 바로 끝나던 결제 완료 웹훅도 실패·재시도가 되고, 장애가 길면 `DEAD`가 된다.
  - 차이가 0이면 결과는 예전과 같다.
- **대사 배치(미구현)**: PortOne 결제 목록과 원장을 주기적으로 비교하는 배치다. 웹훅·승인 API·만료 확인이 모두 놓친 결제를 잡는 마지막 안전망이다. 현재 남은 가장 큰 구멍이다.

## 7. 아직 하지 않은 것

- **대사 배치**: 5장. 원장과 PG를 비교하는 마지막 안전망이다.
- **`DEAD` 확인 수단과 수동 처리 절차**: 지금은 ERROR 로그만 남는다. 보상·환불·웹훅 `DEAD`를 조회하고 알리는 수단, 그리고 PG 취소 내역을 먼저 확인한 뒤 처리하는 절차가 필요하다.
- **실제 PortOne으로 확인**: 부분 취소의 잔액 전송, 취소 응답의 `REQUESTED`, 조회 응답의 취소 내역은 가짜 PG와 공식 문서, server-sdk 기준으로만 확인했다. 결제 수단(채널)이 확정되면 테스트 채널에서 확인한다.
- **동시성 검증 보강**: 승인 API·웹훅·만료 취소가 동시에 금액 불일치나 취소된 결제를 처리할 때 보상 요청이 1건인지 MySQL로 확인하는 테스트(현재는 락과 UNIQUE 제약, 단위 테스트로만 보장)
