# KAN-150 예약 생성 집중·분산 부하 검증

## 목적과 첫 시나리오

동일 슬롯에 요청이 몰릴 때 정원과 예약 데이터의 정합성을 확인하고, 이후 분산 요청과 잠금 경합·응답 지연을 비교한다.
focus-02와 최신 dev 반영 후 focus-03에서 HTTP·DB 정합성 검증을 통과했다. 프로덕션 코드는 변경하지 않았다.

| 첫 실행 | 조건 |
| --- | --- |
| 대상 | 실제 인증을 거친 POST /api/reservations |
| 사용자 | 서로 다른 회원 50명, 각 1회 |
| 공통 슬롯 | 정원 20명, 초기 예약 0건 |
| 목표 결과 | 201 성공 20건, 정원/마감 상태에 따른 409 업무 거절 30건 |
| DB 조건 | 예약 수=활성 예약 수=서로 다른 회원 수=reservedCount=20 |
| 소유 관계 | 예약 회원과 티켓 주문 회원 일치 |
| 자원 | 앱 2 CPU/1GiB/pool 10, MySQL 1 CPU/1GiB, k6 1 CPU/2GiB |
| 시간 | 실제 KST 10:00~21:10 미만에 준비, 오늘 21:50~22:00 슬롯 |

## 확인한 근거

- sources/비즈니스 규칙.md: BR-RSV-01·02·03·04·30·31·32, BR-TKT-07을 확인했다.
- ReservationService.createReservation(): 회원·티켓 소유자/상태/날짜·슬롯·운영 상태·중복/충돌 검사 후 정원 확보와 저장을 수행한다.
- AttractionSlotService.findSlot(): 슬롯 잠금 조회를 사용한다. 생성 서비스는 어트랙션 잠금 조회도 수행한다.
- tryReservationCapacity(): 조건부 UPDATE 후 refresh와 autoClosed 동기화를 수행한다.
- 현재 ApiResponse 오류 본문에는 errorCode가 없어, 409 상태와 실제 두 ErrorCode 메시지를 함께 검증한다.
- 기존 ReservationSlotConcurrencyIntegrationTest 등 실제 DB 동시성 테스트가 있다. 본 테스트는 HTTP 인증·동시 요청·DB 후검증을 추가하는 범위다.

모든 문서를 읽거나 전체 생성 경로를 실제 실행한 것은 아니다. 위는 읽은 관련 정책과 코드의 정적 확인이다.

## 판단 원칙

예상 업무 거절은 정상 결과로 구분하고, 다른 사유의 409와 5xx·401·timeout은 실패로 집계한다.
성공/거절 응답의 지연을 분리한다. 작은 50회 경쟁 테스트에서 운영 성능이나 최대 수용량을 주장하지 않는다.
50 VUs가 정확히 같은 순간 DB에 진입한다고 가정하지 않고 실제 요청 시작 범위를 기록한다.
실행마다 새 데이터만 추가하며 기존 결과나 예약을 자동 삭제하지 않는다. DB 정합성 검사와 HTTP 결과가 모두 맞아야 완료다.

## 준비 중 발견한 문제

focus-01은 SQL 준비 단계에서 중단됐다. 확인된 결과는 0바이트 fixture.jsonl뿐이며 본 측정 summary는 없다.
터미널의 실제 SQL 오류 내용은 아직 확인하지 못했다. 정적 확인으로 prepare.sql이 같은 쿼리에서 run_users 임시 테이블을 네 번 참조하는 문제를 발견했다.
MySQL 8.4는 같은 쿼리에서 TEMPORARY 테이블을 여러 번 참조하면 Can't reopen table 오류가 발생하므로, 단일 FROM과 집계 함수로 검증하도록 수정했다.
[MySQL 공식 문서](https://dev.mysql.com/doc/refman/8.4/en/temporary-table-problems.html)를 근거로 수정했고 focus-02·03에서 SQL 준비를 완료했다.
run.sh에 SQL 준비 오류와 종료 코드 저장도 추가했다. 기존 결과는 보존하고 새 RUN_ID로 실행한다.

| DB 예약 수 / reservedCount / 정원 | 20 / 20 / 20 | 20 / 20 / 20 |

두 실행 모두 티켓 소유 관계 검증과 CLOSED/autoClosed=true를 확인했다.
SQL 준비·HTTP·DB 검증·수집·정리 종료 코드는 모두 0이고 오류 파일은 비어 있었다. k6는 oomKilled=false/exitCode=0으로 종료했다.
정확히 같은 순간 DB에 도달했음을 보장하는 수치는 아니며, 요청 호출 시작 시각 범위를 기록한 것이다.

focus-03은 최신 dev를 merge한 뒤 빌드한 JAR로 실행했다(소스 HEAD b0577a31). focus-02와 JAR hash가 다르므로 지연 감소를 코드 최적화 효과로 확정하지 않는다.
두 실행 모두 앱 재생성·warm-up 없음·50회 요청이며 별도 지연 합격 기준은 없다. 현재 확인한 것은 정합성 통과와 응답 지연의 기준값이다.
자원·Hikari 표본은 실행당 4회뿐이다. 관측 pending이 0이어도 잠금·커넥션 대기 부재나 병목 원인을 결론내리지 않는다.

## 매진 반복과 집중·분산 비교

focus-04도 동일 JAR로 성공 20/예상 거절 30/예상 외 0, DB 예약·인원·서로 다른 회원 수 20을 확인했다.
성공 평균/p95는 1,733.06/2,232.11ms, 거절은 2,467.85/2,561.06ms였다. 요청 시작 범위는 5ms였다.
준비·HTTP·DB 검증·수집·정리 종료 코드가 모두 0이고 오류 파일은 비어 있었다. 정합성은 반복 확인했지만 지연은 focus-03보다 커져 안정적이라고 결론내리지 않는다.

집중·분산 성능 비교는 두 경우 모두 성공 50건이 되도록 조건을 맞췄다. single-01·spread-01에서 첫 실행을 완료했다.

| 모드 | 배치 | 기대 결과 |
| --- | --- | --- |
| single | 슬롯/어트랙션 1개, 정원 50 | 요청 50건 모두 성공, DB 예약/인원 50 |
| spread | 서로 다른 어트랙션의 슬롯 5개, 각 정원 10 | 슬롯별 성공 10건, 총 성공·DB 예약/인원 50 |

같은 코드·회원 수·요청 수·총 정원·자원·앱 재생성·warm-up 없음 조건에서 대상 분산만 달리한다.
슬롯과 어트랙션 잠금 경합이 함께 달라지므로 특정 락 하나만의 효과로 확정하지 않는다.
기존 sold-out 모드는 정합성 검증용으로 유지한다. 성공 20·거절 30인 실행과 성공 50인 실행을 직접적인 성능 개선 전후로 묶지 않는다.

| 첫 비교 결과 | single-01 | spread-01 |
| --- | ---: | ---: |
| 요청 / 성공 / 거절 / 예상 외 | 50 / 50 / 0 / 0 | 50 / 50 / 0 / 0 |
| 성공 평균 / p95 / p99 (ms) | 1,381.95 / 1,868.34 / 1,912.54 | 1,275.77 / 1,712.71 / 1,721.33 |
| DB 예약 수 / 서로 다른 회원 수 | 50 / 50 | 50 / 50 |
| 슬롯별 예약 수=reservedCount=정원 | 1개 × 50 | 5개 × 10 |
| 요청 호출 시작 범위 | 5ms | 5ms |

두 실행 모두 동일 JAR이며 티켓 소유 관계·슬롯별 자동 마감·정상 종료를 확인했다. 준비·수집·정리 오류 및 예상 외 응답은 없었다.
분산 실행의 지연이 조금 낮았으나 각 1회·warm-up 없음·짧은 표본이므로 분산 효과나 특정 잠금 병목으로 확정하지 않는다.

다음은 순서를 바꿔 spread-02를 먼저, 결과 확인 후 single-02를 실행해 반복한다. 각 실행은 앱을 재생성하므로 하나씩 순차 실행한다.
현재 코드·자원·50건·warm-up 없음 조건을 유지하고 서버 시각·기존 결과는 바꾸지 않는다. 두 반복 실행은 아직 미실행이다.

## 피크 시나리오 검토 방향

“피크에 2,000명이 예약”은 실제 운영 통계가 아닌 가정으로 다룬다. 하루 이용자 수와 동시에 예약하는 인원은 다르다.
2,000건이 한순간에 몰리는 spike와 1분간 유입되는 부하는 별도 시나리오다. 현재 도구는 50건 비교만 지원하며 2,000 VUs를 구현·실행하지 않았다.
확대 전에 유입 시간, 집중/분산 비율, 정원 소진에 따른 예상 거절, 허용 지연/오류, 종료 후 회복 기준을 정한다.
작은 비교 후 단계적으로 확대하고 부하 발생기와 서버 한계를 구분한다. 모든 예약의 성공이 아니라 정합성·정상 업무 거절·서버 오류·지연·회복을 함께 평가한다.
