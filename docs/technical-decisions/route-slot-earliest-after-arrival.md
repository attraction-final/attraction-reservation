# 슬롯은 "도착 후 가장 이른 슬롯"으로 고정해 탐색 공간 줄이기

> 분류: 기술적 도전 · 관련 이슈: KAN-164 · 기준 코드: `dev` `RouteSearcher#findEarliestAvailableSlot`, `CandidateSelector`

| 항목 | 내용 |
| --- | --- |
| 문제 | 방문 순서마다 어느 슬롯을 탈지까지 고르면 순서 하나당 최대 `40⁵ ≈ 1억` 가지다 |
| 결정 | 순서가 정해지면 각 어트랙션에서 도착 시각 이후 가장 이른 슬롯을 고른다 |
| 근거 | 일찍 타면 일찍 끝나고, 일찍 도착해서 손해 보는 일은 없다. 늦은 슬롯을 고를 이유가 없다 |
| 효과 | 탐색 대상이 `순열 × 40⁵`에서 `순열`로 줄어든다 |

## 1. 문제

방문 순서뿐 아니라 각 어트랙션에서 **몇 시 슬롯을 탈지**도 골라야 한다. 슬롯 조합까지 전부 탐색하면 순서 하나당 최대 `40⁵ ≈ 1억` 가지가 된다.

## 2. 결정

순서가 정해지면, 각 어트랙션에서는 **도착 시각 이후에 시작하는 가장 이른 슬롯**을 고른다 (`findEarliestAvailableSlot`). 슬롯은 후보 선정 단계(`CandidateSelector`)에서 시작 시각순으로 정렬해 둔다.

## 3. 근거

- 같은 어트랙션의 슬롯은 탑승 시간이 같다(`AttractionSlot.endsAt = startsAt + attraction.durationMinutes`). 그래서 일찍 시작하면 일찍 끝난다.
- 일찍 끝나면 다음 어트랙션에 일찍 도착한다. 일찍 도착해서 탈 수 없는 슬롯은 없다(기다리면 된다). 그래서 **더 늦은 슬롯을 골라서 얻는 이득이 없다.**
- 덕분에 탐색 대상은 "방문 순서"뿐이고, 슬롯 선택은 순서마다 정렬된 목록을 앞에서부터 한 번 훑는 것으로 끝난다.

## 4. 그리디와 무엇이 다른가

[완전 탐색 문서](route-search-dfs-backtracking.md)의 그리디는 "**어느 어트랙션을** 먼저 갈지"를 탐욕적으로 고르는 것이라 틀린다. 이 결정은 순서가 정해진 뒤 "**그 어트랙션의 어느 슬롯을** 탈지"만 탐욕적으로 고르는 것이라 손해가 없다.

## 5. 한계

- 슬롯마다 탑승 시간이 다른 어트랙션이 생기면 "일찍 시작 = 일찍 끝남"이 깨지므로 다시 검토해야 한다.
