# 외부 AI가 느리거나 죽어도 서비스는 그대로: Q&A 장애 격리

> 분류: 성능 · 장애 격리 · 관련 이슈: KAN-116, KAN-119 · 기준 코드: `dev` `AttractionQuestionService`, `JevAttractionQuestionClassifier`, `application.yaml` (`spring.ai.typesafe`)

| 항목 | 내용 |
| --- | --- |
| 문제 | 외부 AI가 느리거나 죽거나, 키 없이 배포될 수 있다. 이때 서버 전체나 다른 API까지 함께 느려지면 안 된다 |
| 결정 | 키가 없어도 서버는 뜬다. 타임아웃 2초 · 재시도 1번 · 전체 5초 안에 503으로 끝낸다. 트랜잭션 밖에서 호출한다 |
| 근거 | 실패 원인이 무엇이든 사용자가 할 일은 "잠시 후 다시 시도"로 같다. DB 커넥션을 쥐고 기다리지 않는다 |

## 1. 문제

외부 AI가 느리거나 죽거나, 키가 빠진 채 배포될 수 있다. 이때 서버 전체가 뜨지 않거나, 요청 스레드와 DB 커넥션이 응답을 기다리며 묶이면 Q&A와 무관한 예약 · 결제까지 함께 느려진다.

## 2. 결정

| 상황 | 처리 |
| --- | --- |
| API 키 미설정 | 스타터가 클라이언트 빈을 만들지 않는다. `ObjectProvider`로 받아 **서버는 정상 기동**하고 Q&A만 503 (시나리오 14) |
| 응답 지연 | 요청당 타임아웃 2초 (`timeout: 2s`) |
| 429 · 500 · 529 · 타임아웃 · 연결 실패 | 1번 재시도 (`max-retries: 1`), 재시도 포함 전체 5초 (`total-timeout: 5s`). `Retry-After`가 남은 시간보다 길면 기다리지 않고 503 |
| 400 · 401 · 422 | 재시도하지 않고 503 |
| 해석할 수 없는 응답 | 추측하지 않고 503 |

- 질문 처리(`AttractionQuestionService#answer`)에는 `@Transactional`을 붙이지 않았다. **Jev 응답을 기다리는 동안 DB 커넥션을 잡고 있지 않는다.**
- 실패 응답은 503 하나로 통일하고, 원인은 로그의 `exceptionType`으로 구분한다.

## 3. 근거

- 실패 원인이 무엇이든 사용자가 할 수 있는 일은 "잠시 후 다시 시도"로 같다.
- 잘못된 값으로 숫자를 답하는 것보다 답하지 않는 편이 낫다.
- 커넥션 풀은 예약 · 결제와 함께 쓴다. 외부 호출이 최대 5초 걸려도 커넥션을 쥐고 있지 않으므로 다른 API에 영향이 없다.
- 검증 (`JevClientHttpTest`, 실제 HTTP 서버로 Jev 응답을 흉내 냄)

| 테스트 | 확인 내용 |
| --- | --- |
| `noApiKey` | API 키가 없어도 앱은 뜨고 Q&A만 503 |
| `appliesSettings` | `application.yaml`의 모델과 시간 제한이 클라이언트에 적용된다 |
| `classify_errorStatus` | 오류 응답은 503, 일시적인 오류만 한 번 재시도, 예외 종류를 로그로 남김 |
| `classify_timeout` | 응답이 늦어도 재시도를 포함해 5초 안에 503 |
| `classify_connectionRefused` | 연결할 수 없으면 503 |

## 4. 한계

- 연속 실패 시 호출 자체를 잠시 끊는 서킷 브레이커는 두지 않았다. 장애가 길어지면 요청마다 최대 5초를 기다린다.
