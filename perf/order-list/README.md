# 주문 목록 부하 테스트 — 준비와 측정 기록

## 목적과 현재 상태

- 담당: 경식 / 주문·회원·인증.
- 기준 코드: dev `10759c4` (2026-10-29 확인). 이후 dev 변경은 자동 혼합하지 않고 별도 버전으로 기록한다.
- 작업 브랜치: `perf/order-list-baseline`. 기존 회원 탈퇴 브랜치는 변경하지 않았다.
- 현재는 개인 로컬 환경의 실행 준비·정확성 검증·예비 측정이다. 운영 성능이나 개선 효과가 검증된 상태가 아니다.
- 업무 코드, 인덱스, 인증 정책은 아직 변경하지 않았다.

## 환경

- 앱: 호스트 Java 17, `127.0.0.1:18086`, 힙 256~512MiB, Hikari 최대 연결 10개.
- MySQL: 전용 Compose, `127.0.0.1:13316`, DB `attraction_perf`. 기존/공용 DB를 사용하지 않는다.
- Redis: 전용 Compose, `127.0.0.1:16396`. 이미지 digest는 compose.yaml에 고정했다.
- k6: Docker 이미지 digest를 run.py에 고정하고 실제 버전을 실행마다 저장한다.
- 실제 환경변수를 상속하지 않는 앱 실행기를 사용한다. PortOne 주소는 로컬 비수신 포트이며 실제 결제를 호출하지 않는다.
- 웹훅·보상·환불·주문 취소 스케줄러는 이 조회 실험에서 끈다. 티켓 만료 스케줄러는 최초 실행 후 24시간 간격이고 대상 데이터가 없다. 배포 환경과 차이가 있으므로 결과에 명시한다.
- 신규 개인 DB 스키마 생성에만 Hibernate update를 사용한다. 팀 DB의 배포/마이그레이션 방법을 변경하는 설정이 아니다.
- 앱·DB·부하 발생기가 같은 Mac의 자원을 공유한다. 외부 서버 용량으로 일반화할 수 없다.

## 데이터와 시나리오

- 합성 회원 20명, 회원별 주문 1,000건, 전체 20,000건.
- 정상 회원가입·CSRF·로그인 API를 사용한다. 로그인은 측정 요청 전에 수행하며 토큰은 출력하지 않는다.
- 주문 목록 조회만을 위한 합성 COMPLETED 주문이다. 주문 항목·결제·티켓이 없어 구매 처리의 검증 자료로 쓸 수 없다.
- 이 분포는 초기 재현 fixture이며 실제 서비스의 주문 분포나 목표 트래픽을 대표한다고 가정하지 않는다.
- 동일 생성 시각도 포함해 ID 보조 정렬을 검증한다.
- 페이지 크기 10, 첫 페이지·중간 페이지·마지막 페이지를 순환한다.
- VU마다 다른 회원을 사용한다. 현재 fixture는 최대 20 VU까지만 지원한다. 계정 중복으로 2,000명을 흉내 내지 않는다.
- 각 요청 사이에 1초 대기한다. 일정한 VU 수의 닫힌 모델이므로 실제 달성 요청률을 함께 보고한다.
- 각 응답의 HTTP 200, success, 전체/페이지 건수, DB에서 독립 조회한 주문 ID와 순서, 금액·상태를 비교한다.
- 시작 전 미인증 요청이 401인지 확인한다. 이 요청은 목록 처리 시간 지표에 포함하지 않는다. 전체 HTTP 요청 수에는 1건 포함된다.
- 토큰 만료를 피하도록 초기 측정 길이는 30/60/90초로 제한한다. 장시간/2,000 VU 시나리오는 인증 모델·데이터·발생기 자원을 별도로 설계한다.
- 현재 자동 합격 기준은 데이터 정확성이다. 지연·오류율 목표는 팀 요구와 기준 측정 뒤 근거를 정해 추가한다.

## 실행

모든 명령은 이 별도 저장소 루트에서 실행한다. 실제 PG/소셜 인증, 공용 데이터 변경은 포함하지 않는다.

```sh
docker compose -f perf/order-list/compose.yaml up -d --wait
bash gradlew bootJar --console=plain
python3 perf/order-list/start-app.py
python3 perf/order-list/prepare.py --seed
python3 perf/order-list/run.py local-smoke-03
python3 perf/order-list/run.py local-calibration-02 --mode load --vus 10 --duration 60s
```

- seed는 신규 DB에 한 번만 실행한다. 주문이 있으면 거부한다. 기존 결과를 지우거나 DB를 자동 초기화하지 않는다.
- run.py는 시작 전에 테스트 계정으로 로그인해 토큰과 DB 기준 예상 결과를 갱신한다.
- 실행 ID는 매번 다르게 지정한다. 같은 이름으로 덮어쓰지 않는다.
- `.local/`에는 토큰과 앱 로그가 있다. Git 제외 대상이며 공유하지 않는다.
- 결과는 `results/<실행 ID>/`에 저장한다. 원본 결과는 Git 제외 대상이다. 공유할 결과는 내용 확인 후 별도 첨부한다.

## 결과 파일과 의미

| 파일 | 용도 |
|---|---|
| metadata.json | 코드·k6·Docker 버전, 부하 조건, 시작·종료 시각, 한계 |
| fixture.json | 회원별 주문 수와 검증 페이지의 예상 ID. 토큰 없음 |
| summary.json | k6 최종 지표. 목록 지연은 order_list_duration 사용 |
| metrics.json | 시간대별 k6 원본 지표 |
| terminal.txt | 터미널 출력 |
| dashboard.html | 충분히 긴 실행에서 생성되는 HTML 그래프. 짧은 smoke는 생성 안 될 수 있음 |
| db-before.txt | 실제 데이터 수, 테이블과 기존 인덱스 |
| plans-before.txt | 조회 계획의 보조 재현. 실제 SQL은 digest와 대조해야 함 |
| sql-digests-before/after.txt | 누적 SQL 통계의 앞뒤 스냅샷. 차이를 계산해 사용하며 누적값을 해당 실행의 값으로 오해하지 않음 |
| resource-samples.jsonl | DB·Redis 컨테이너와 앱 프로세스 CPU/RSS 샘플. JVM heap/GC·DB 연결 대기를 모두 수집한 것은 아님 |

EXPLAIN ANALYZE는 실제 쿼리를 실행해 캐시에 영향을 줄 수 있다. 현재는 준비 검증용이며 정식 전후 비교는 같은 워밍업·계획 수집 순서와 최소 3회 반복 조건을 먼저 고정한다. 데이터·SQL 계획·앱 상태가 달라진 실행을 그대로 비교하지 않는다.

## 캡처 지침

지금은 준비 검증 기록을 보존한다. 개선 전후 비교의 최종 캡처는 양쪽 조건이 고정된 뒤 남긴다.

1. 실행 조건: metadata의 코드, 데이터 수, VU·대기·시간, 환경 차이가 보이게 기록.
2. 결과: HTML/터미널의 P95·평균·요청 수·오류·응답 검증 결과를 실행 ID와 함께 캡처.
3. 원인: 같은 시간대 서버/DB 지표, 실제 SQL과 조회 계획. 단순 filesort 존재만으로 병목이라고 결론 내리지 않는다.
4. 변경: PR에서 실제 코드/인덱스 변경과 선택 이유 기록.
5. 재측정: 같은 축·조건으로 전후 비교. 실패/무개선 실행도 보존.

스크린샷만 보관하지 않고 스크립트·원본 수치·환경 기록을 함께 남긴다. 토큰·쿠키·실제 개인정보는 캡처하지 않는다.

## 오늘/내일/모레

- 오늘: 개인 환경 확인, 스크립트 정확성, 예비 측정, 목표/데이터 분포/모니터링 확정. 저녁에 실제 진척으로 범위 재평가.

- 모레: 같은 조건 재측정, 결과 비교, 한계·후속 과제·PR 정리.
- 모니터링/배포 담당 재서님에게 테스트 대상 서버 및 관측 지표를 확인한다. 답을 기다리는 동안 로컬 준비를 진행한다.
- 캐싱은 팀 필수 항목의 담당/대상을 확인한다. 개인 주문·회원 데이터 캐싱을 성급히 도입하지 않는다.

## 기록상 주의

- local-smoke-01: 응답 검증 50/50 통과, SQL 통계 파일 저장 실패. 오류와 결과 보존.
- local-smoke-02: 기록 권한 수정 후 다시 실행. 결과 폴더 참조.
- 예비 실행 간 지연 차이는 개선 효과로 쓰지 않는다. 업무 코드 변경도 없고 워밍업/표본이 다르다.
- 설치 준비, 응답 정확성 통과, 성능 기준 충족, 최적화 완료는 서로 다른 상태로 기록한다.

## 테스트 데이터 확장

기존 테스트 데이터를 유지하면서 총 회원 100명,
회원별 주문 1,000건으로 확장한다.

```bash
python3 perf/order-list/prepare.py --extend --users 100 --orders-per-user 1000
```

이미 주문이 1,000건인 대상 회원은 추가하지 않는다.
기존 회원의 주문 수가 0건 또는 지정한 건수와 다르면 중단한다.
여러 단계로 데이터를 추가하므로 전체 작업이 하나의 트랜잭션은 아니다.
실패하면 저장된 상태를 확인한 뒤 재실행 여부를 판단한다.

## 주문 목록 복합 인덱스 실험

- 적용 SQL: `index-order-list.sql`
- 적용 대상: 개인 테스트 DB `attraction_perf`
- 인덱스: `(user_id, created_at DESC, id DESC)`
- 공유 DB에 자동 적용하지 않는다.
- 이미 적용된 DB에는 같은 생성문을 다시 실행하지 않는다.

회원 조건과 최신순 정렬에 맞춘 인덱스의 효과를 확인한다.
실행 계획에서 인덱스 사용 여부, 별도 정렬, 실제 읽은 행 수를 비교한다.

API 비교 조건은 회원 100명·주문 100,000건,
100 VU·60초·응답 후 1초 대기로 유지한다.
첫·중간·마지막 페이지를 순환 조회하고 응답 정확성도 검증한다.

각 조건에서 반복 측정 결과를 모두 보관한다.
준비 실행은 비교 측정과 구분한다.
측정일·준비 절차·로컬 자원 상태의 차이를 기록하고,
응답 시간 차이를 인덱스만의 효과로 단정하지 않는다.

결과 파일은 `results/`에 저장되며 Git 추적에서 제외된다.
공유할 결과 요약과 원본 백업은 별도로 보관한다.
