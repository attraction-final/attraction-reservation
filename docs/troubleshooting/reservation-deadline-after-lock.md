# 예약 잠금 대기 후 마감 시각 검증 트러블슈팅

> **KAN-105 · 잠금 대기 전의 시각으로 마감 검사를 통과하는 문제 개선**
>
> 실제 MySQL에서 예약 요청을 회원 잠금에 대기시킨 뒤 기준 시각을 마감 이후로 변경하여, 마감이 지난 예약이 저장되는 문제를 재현했다.
> 회원·슬롯·어트랙션 잠금 확보 후 시각을 한 번 취득하도록 변경했다.
> 잠금 대기·마감 경계값 5개 case와 관련 회귀 테스트를 포함한 55개 Test Suite, 397개 테스트의 통과를 확인했다.

## 1. 문제와 업무 기준

예약 생성은 회원, 슬롯, 어트랙션의 행 잠금을 순서대로 얻는다. 수정 전에는 이 잠금들을 얻기 전에 `KstTime.now()`로 기준 시각을 구했다.

잠금을 기다리는 동안 마감이 지나도 처음 구한 시각으로 검증하므로, 실제 처리가 재개된 시점에는 마감된 슬롯에 예약이 생성될 수 있었다.

읽기 전용 원본 `sources/비즈니스 규칙.md`에서 확인한 기준:

- **BR-RSV-02:** 현재 시각 ≤ 슬롯 시작 − 30분인 경우에만 예약할 수 있다.
- **BR-COM-01:** KST 서버 시각을 기준으로 마감 등을 판단한다.
- **9장 결정 사항:** 마감 정각도 허용한다.

서버 요청 접수 시각을 별도로 인정하는 예외 정책은 확인하지 못했다. 이번 변경은 필요한 잠금을 확보한 후의 시각으로 판단하는 방향이며, 마감 정각 허용 조건은 유지했다. 원본 참고 문서는 변경하지 않았다.

## 2. 수정 전 실행 순서

[ReservationService.java](../../src/main/java/com/example/attractionreservation/domain/reservation/service/ReservationService.java)의 `createReservation()`은 다음 순서로 실행됐다.

```text
now와 today 계산
→ 회원 잠금 조회·활성 상태 검사
→ 티켓 소유자·상태·방문일 검사
→ 슬롯 잠금 조회
→ 어트랙션 잠금 조회
→ 최초 now를 사용한 마감 검사
→ 중복·시간 충돌 검사
→ 정원 확보와 예약 저장
```

예를 들어 슬롯 시작이 14:00이면 마감은 13:30이다.

```text
13:29:59  now 취득
          회원 행 잠금 대기
13:30:01  회원 잠금 획득 후 예약 처리 재개
          13:29:59를 기준으로 마감 검사 통과
          예약 저장 및 정원 사용
```

행 잠금은 동시 변경을 보호하지만, 잠금 전에 구한 시각을 자동으로 갱신하지 않는다.

## 3. 재현 테스트 환경과 제어 방법

[ReservationDeadlineConcurrencyIntegrationTest.java](../../src/test/java/com/example/attractionreservation/domain/reservation/service/ReservationDeadlineConcurrencyIntegrationTest.java)를 추가했다.

- `@DataJpaTest`, `@ActiveProfiles("test")`
- Testcontainers MySQL `mysql:9.6`
- `ddl-auto=create-drop`, Hikari 최대 커넥션 4개
- 기본 테스트 트랜잭션은 `NOT_SUPPORTED`
- fixture 준비·최종 DB 조회는 별도 `TransactionTemplate` 사용
- 실제 예약 Service와 회원·슬롯·어트랙션 잠금 조회 사용
- UserService 생성에 필요한 PasswordEncoder·RefreshTokenRepository만 mock 처리

fixture는 2026-11-06 방문일의 IN_USE 종일권과 14:00 슬롯을 사용한다. 슬롯 정원은 5명이며 최초 예약 인원은 0명이다.

### 실행 순서 제어

1. 별도 트랜잭션이 대상 회원 행에 `PESSIMISTIC_WRITE` 잠금을 얻는다.
2. 예약 작업 스레드에서 `KstTime.now()`를 13:29:59로 제어하고 예약을 요청한다.
3. 회원 조회 시작 신호를 받은 뒤, 요청이 500ms 동안 완료되지 않는지 확인한다.
4. 기준 시각을 13:30:01로 변경한다.
5. 선행 트랜잭션을 commit하여 잠금을 해제한다.
6. 요청 결과와 별도 트랜잭션에서 조회한 예약·정원을 비교한다.

`AtomicReference<LocalDateTime>`로 반환 시각을 변경한다. static mock은 예약 작업 스레드 안에서만 사용하고, `now()` 외의 KST 변환 메서드는 실제 동작을 유지한다.

Spy는 해당 잠금 조회에 도달했다는 신호만 전달한다. 조회 결과를 임의로 바꾸지 않고 실제 Service·Repository 처리를 실행한다.

500ms 확인은 후행 요청이 완료되지 않았음을 검증하는 방식이다. MySQL 잠금 대기 테이블을 직접 조회한 것은 아니다. 기준 시각을 제어하므로 실제 마감까지 수십 분을 기다리지 않는다.

## 4. 실제 재현 결과

최초 실패 XML 시작 시각은 **2026-11-04 17:19:15 KST**였다.

```text
성공 응답: 기대 없음 / 실제 RESERVED 응답
마감 초과 예외: 기대 발생 / 실제 없음
예약 저장 건수: 기대 0 / 실제 1
슬롯 예약 인원: 기대 0 / 실제 1
슬롯 잔여 정원: 기대 5 / 실제 4
```

테스트 1개 안의 검증 5개가 실패했고, 실행 오류는 없었다. 환경 초기화 문제가 아니라 실제 예약 저장과 정원 변경을 확인하여 문제를 재현했다.

마감 검사의 `deadLine.isBefore(now)` 조건 자체는 정각 허용 정책에 맞았다. 비교에 사용하는 now가 잠금 대기 전의 값이라는 점이 원인이었다.

과거 실패 XML은 이후 실행으로 덮어써졌으므로, 이 결과는 당시 읽어 확인한 리포트를 기록한 것이다.

## 5. 해결: 필요한 잠금 확보 후 기준 시각 취득

기존 시각 계산과 티켓 방문일 검사 블록을 어트랙션 잠금 조회 다음으로 이동했다.

```text
회원 잠금 조회·활성 상태 검사
→ 티켓 소유자·상태 검사
→ 슬롯 잠금 조회
→ 어트랙션 잠금 조회
→ KstTime.now()를 한 번 호출하고 today 계산
→ 티켓 방문일 검사
→ 슬롯 날짜·시간·운영 상태·마감 검사
→ 중복·시간 충돌 검사
→ 정원 확보와 예약 저장
```

같은 now에서 today를 계산하므로 티켓 방문일과 예약 마감이 하나의 기준 시각을 사용한다.

```java
LocalDateTime now = KstTime.now();
LocalDate today = now.toLocalDate();
```

기존 마감 비교는 유지했다.

```java
if (deadLine.isBefore(now)) {
    throw new BusinessException(ErrorCode.RESERVATION_DEADLINE_PASSED);
}
```

- 마감 이전: 허용
- 마감 정각: 허용
- 마감 이후: 거부

회원 → 슬롯 → 어트랙션의 기존 잠금 순서는 바꾸지 않았다. 새로운 잠금이나 DB 컬럼도 추가하지 않았다.

회원 잠금은 `UserService.findByUserId()`가 호출하는 `UserRepository.findByIdForUpdate()`에 이미 선언되어 있다. 호출 이름이 일반 조회처럼 보여도 실제로는 비관적 잠금 조회이며, 예약 생성 트랜잭션이 끝날 때까지 유지된다.

## 6. 추가 검증: 잠금별 대기와 경계값

잠금 확보를 일부만 마친 시점에 now를 구하면 후속 잠금 대기 시간이 다시 누락될 수 있다. 이를 확인하기 위해 회원·슬롯·어트랙션을 각각 선행 트랜잭션이 잠그는 경우를 검증했다.

### ① 회원 잠금 대기 중 마감 초과

- 13:29:59에 예약 요청을 시작하고 회원 잠금에서 대기한다.
- 13:30:01에 잠금을 해제한다.
- `RESERVATION_DEADLINE_PASSED`, 예약 0건, 정원 변경 없음을 확인한다.

### ② 슬롯 잠금 대기 중 마감 초과

- 회원 잠금은 얻고 슬롯 잠금에서 대기한다.
- 13:30:01에 슬롯 잠금을 해제한다.
- 동일한 마감 초과 예외와 예약·정원 미변경을 확인한다.

### ③ 어트랙션 잠금 대기 중 마감 초과

- 회원·슬롯 잠금은 얻고 어트랙션 잠금에서 대기한다.
- 13:30:01에 어트랙션 잠금을 해제한다.
- 동일한 마감 초과 예외와 예약·정원 미변경을 확인한다.

### ④ 회원 잠금 해제 후 마감 이전

- 잠금을 해제할 때 반환하는 시각은 13:29:59다.
- RESERVED 응답, 예약 1건 저장, 예약 인원 0→1, 잔여 정원 5→4를 확인한다.

### ⑤ 회원 잠금 해제 후 마감 정각

- 잠금을 해제할 때 반환하는 시각은 13:30:00이다.
- 마감 이전과 동일하게 예약 성공과 정원 1자리 사용을 확인한다.

최종 테스트 메서드는 4개이며, 경계값 parameterized test의 2개 case를 포함해 총 5개다.

## 8. 검증 범위와 한계

- 실제 MySQL 행 잠금과 예약 생성 Service 트랜잭션을 사용했다.
- 마감 이후 거부 시 DB에 예약이 없고 정원 변경도 없는지 확인했다.
- HTTP Controller, 인증·권한, 요청 접수 시각 수집은 이 테스트에 포함하지 않았다.
- 자정을 넘기는 날짜 변경 경합은 별도 통합 테스트로 재현하지 않았다. 날짜 검사 위치 변경과 기존 회귀 테스트 통과를 확인한 범위다.
- 기준 시각은 필요한 세 잠금을 확보한 후의 한 시점이며, 최종 commit 시각까지 매번 다시 검사하는 구조는 아니다.
- 다른 업무 경로 전체의 잠금 순서, deadlock·timeout·부하에 따른 처리량을 검증한 것은 아니다.

## 9. 배운 점

시간 검증의 비교식뿐 아니라 기준 시각을 취득하는 위치도 비즈니스 규칙에 영향을 준다. 잠금이 필요한 업무에서는 잠금 대기 전에 읽은 시각이 실제 판단 시점보다 오래될 수 있다.

이번에는 시간 판단에 필요한 잠금을 확보한 뒤 시각을 한 번 취득하고 날짜·마감에 함께 사용하여, 마감 정각 정책을 유지하면서 잠금 대기에 따른 잘못된 예약 승인을 방지했다.
