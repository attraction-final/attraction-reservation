# 주문 생성·취소 — 부하 확대와 DB 연결 풀 비교

## 결론

공통 상품과 회원별 분산 상품에서 10·50·100 VU 반복 부하를 수행했다.
탐색 실행 6회 모두 주문 생성·취소 응답과 실행 후 DB 검증을 통과했다.

공통 상품 100 VU 진단에서 DB 연결 획득 대기와 MySQL 행 잠금 대기가 관측됐다.
이를 근거로 최대 DB 연결 수를 10개에서 20개로 늘리는 후보를 비교했다.

설정별 본 측정 3회에서 전체 흐름 P95의 실행별 중앙값은
213.70ms → 204.00ms로 4.54% 감소했다.
그러나 실행 간 변동이 크고 P99 중앙값은 28.17% 증가했다.

안정적인 개선 근거가 부족하다고 판단해 20개 설정은 채택하지 않았다.
최종 개인 설정은 10개로 복구했고 복구 후 정확성 검사도 통과했다.
운영 설정과 주문 서비스 코드는 변경하지 않았다.

## 실험 질문

1. 상품 하나에 주문이 몰려도 주문·결제 상태와 재고가 일치하는가?
2. 같은 회원 수에서 상품을 분산하면 지연 양상이 달라지는가?
3. 지연 구간에서 DB 연결 대기와 행 잠금 대기가 관측되는가?
4. 연결 풀 확대가 정확성을 유지하면서 지연을 개선하는가?

상품 분산은 경합 가능성을 살펴보기 위한 시나리오 비교다.
분산 시나리오의 결과를 서버 코드 개선 효과로 해석하지 않는다.

100 VU는 이 흐름을 반복하는 가상 사용자 100명이다.
서버에서 정확히 100건을 동시에 처리했다는 의미는 아니다.
2,000건 동시 요청이나 운영 서비스 전체 수용 능력 검증이 아니다.

## 정확성 검사

기본 검사에서 공통 상품과 분산 상품을 각각 확인했다.

- 생성: HTTP 201, 주문·결제 PENDING, 재고 10000 → 9999
- 취소: HTTP 200, 주문·결제 CANCELLED, 재고 9999 → 10000
- 재취소: HTTP 409, 재고 10000 유지

k6 소규모 검사:

| 조건 | 생성·취소 각각 | 응답 검사 |
|---|---:|---:|
| 공통 상품 1 VU × 3회 | 3건 | 33개 통과 |
| 분산 상품 2 VU × 3회 | 6건 | 66개 통과 |

각 부하 실행에서 다음을 대조했다.

- 생성 시도·성공·취소 시도·성공·완료·반복 건수 일치
- 흐름당 응답 검사 11개 통과
- HTTP 실패와 중단 반복 0건
- 실행 전후 새 주문·항목·결제 건수와 완료 흐름 수 일치
- 주문 소유자와 회원별 배정 상품 일치
- 금액·가격 10000원, 항목 1개, 수량 1개, 방문일 일치
- 새 주문·결제 모두 CANCELLED
- 사용 상품 재고 10000·ON_SALE 복구, 미취소 주문 0건

검증 실패 시 기록을 보존하고 중단한다.
주문을 자동 삭제하거나 재고를 임의 초기화하지 않는다.

재고가 충분한 조건의 반복 생성·취소 검사다.
재고 부족 시 초과 판매와 동일 주문의 동시 취소 경쟁을
이번 부하에서 새로 검증한 것으로 주장하지 않는다.
이전 검증은 ../order-write/README.md에서 구분해 확인한다.

최종 개선 전후 비교에 사용하는 기준 측정과 구분한다.
전체 흐름 시간 단위는 ms다.

| 상품 | VU | 완료 | 평균 | P95 | P99 |
|---|---:|---:|---:|---:|---:|
| 공통 | 10 | 550 | 93.05 | 149.10 | 274.04 |
| 분산 | 10 | 570 | 62.99 | 75.00 | 89.00 |
| 공통 | 50 | 2786 | 81.67 | 298.25 | 1236.15 |
| 분산 | 50 | 2850 | 55.72 | 119.55 | 283.02 |
| 공통 | 100 | 5725 | 57.54 | 161.40 | 755.52 |

모두 응답·DB 검증을 통과했다.

그러나 VU 증가에 따라 지연이 일관되게 증가하지 않았다.
이 결과만으로 처리 한계나 잠금 경합의 인과 효과를 확정하지 않았다.

## 진단 근거

공통 상품 100 VU에서 로그인 준비 후 JFR 기록을 시작하고
부하 종료 직후 중지했다. 진단 실행은 성능 비교에서 제외했다.

생성·취소 각각 5443건, 응답 검사 59873개와 DB 검증을 통과했다.

MySQL 서버 전체 카운터 증가량:

- 행 잠금 대기 발생: 8114회
- 누적 행 잠금 대기 시간: 141695ms

| JFR 기록 | 이벤트 수 | 평균 | 최대 | 합계 |
|---|---:|---:|---:|---:|
| Hikari 연결 획득 중 대기 | 3876 | 87.54ms | 649.36ms | 339320.09ms |
| MySQL 소켓 읽기 대기 | 4441 | 30.21ms | 371.03ms | 134145.72ms |
| GC | 36 | 1.78ms | 7.09ms | 64.13ms |

연결 대기 스택에서 인증 필터와 주문 생성·취소 호출 경로가 확인됐다.
인증 필터는 현재 회원 상태·권한 조회에도 DB 연결을 사용한다.
스택에 나타난 사실만으로 해당 기능이 잘못됐다고 판단하지 않는다.

이벤트 수는 요청 수가 아니며 기록 설정의 영향을 받는다.
여러 스레드의 대기 합계는 전체 실행 시간을 넘을 수 있다.
MySQL 카운터는 같은 서버 전체의 값이다.
소켓 읽기 대기에는 SQL 실행·잠금·통신의 영향이 섞여 있다.
특정 SQL의 잠금이 전체 지연의 원인이라고 확정하지 않는다.

## 비교 방법

DB 연결 획득 대기를 줄일 수 있는지 확인하기 위해
최대 DB 연결 수 10 → 20개를 후보로 선정했다.
연결 증가로 같은 상품의 잠금 경쟁이 늘 가능성도 고려했다.

- 설정별 앱 재시작
- 공통 상품 100 VU·60초 예열 1회 후 본 측정 3회
- 양쪽 모두 caffeinate -i 사용
- 본 측정 JFR 미사용
- 소스 커밋·JAR 해시·부하 스크립트 동일
- 앱 설정 차이는 최대 DB 연결 수만 존재

주지표는 전체 흐름 P95의 실행별 중앙값이다.
평균·P99·완료 건수와 정확성도 함께 검토했다.
측정 후 임의의 최소 개선율을 만들어 판정하지 않았다.

전체 흐름 시간 단위는 ms다.

| 연결 풀 | 회차 | 완료 | 평균 | P95 | P99 |
|---|---:|---:|---:|---:|---:|
| 10 | 1 | 5730 | 55.23 | 198.00 | 506.42 |
| 10 | 2 | 5546 | 89.47 | 322.75 | 2549.20 |
| 10 | 3 | 5794 | 44.01 | 213.70 | 513.14 |
| 20 | 1 | 5777 | 46.56 | 139.00 | 831.48 |
| 20 | 2 | 5797 | 43.89 | 204.00 | 463.08 |
| 20 | 3 | 5656 | 66.56 | 352.00 | 657.70 |

| 실행별 지표 중앙값 | 10개 | 20개 | 변화 |
|---|---:|---:|---:|
| 전체 흐름 P95 | 213.70ms | 204.00ms | -4.54% |
| 전체 흐름 평균 | 55.23ms | 46.56ms | -15.69% |
| 전체 흐름 P99 | 513.14ms | 657.70ms | +28.17% |

변화율은 반올림 전 원본 수치로 계산했다.
실행별 P95 중앙값을 전체 요청을 합친 P95로 표현하지 않는다.

본 측정 6회에서 생성·취소 각각 총 34300건,
응답 검사 총 377300개를 통과했다.
HTTP 실패·중단은 모두 0건이며 DB 검증도 통과했다.

## 미채택 판단과 복구

P95는 소폭 감소했지만 실행별 값이 겹치고 P99 중앙값은 증가했다.
완료 흐름 증가도 작아 안정적인 개선 근거가 부족하다고 판단했다.
따라서 연결 풀 20개는 채택하지 않고 10개로 복구했다.

이는 모든 환경에서 풀 확대가 나쁘다는 결론이 아니다.
이번 상품·부하·공유 Mac 조건에서 채택을 뒷받침하지 못했다는 판단이다.

복구 후 앱을 재시작하고 공통 상품 2 VU 검사를 수행했다.
생성·취소 각각 6건, 응답 검사 66개와 DB 검증을 통과했다.

## 해석과 한계

- 생성·취소 HTTP 시간은 response.timings.duration이다.
  연결 수립 등 호출 전체 시간을 모두 포함하지 않는다.
- 전체 흐름은 생성 직전부터 취소 응답 검사까지의 실제 경과 시간이다.
  마지막 1초 대기는 제외한다.
- 응답이 느려지면 다음 반복도 늦어지는 부하 모델이다.
  고정된 요청 도착률을 유지하는 실험이 아니다.
- 진행 중 반복이 종료 유예 시간에 완료될 수 있다.
  완료 건수를 단순히 60으로 나눠 정확한 서버 TPS로 주장하지 않는다.
- 같은 Mac의 앱·DB·부하 도구와 다른 프로세스가 자원을 공유했다.
  호스트 자원 사용량을 별도로 수집·통제하지 않았다.
- 10개 뒤 20개를 순차 실행했고 DB 이력도 누적됐다.
  실행 순서·시간·캐시 상태의 영향을 완전히 제거하지 못했다.
- 변경 후 JFR을 수집하지 않아 연결 대기 감소량은 주장하지 않는다.
- 장시간 안정성·운영 환경·최대 수용량 검증은 이번 범위 밖이다.

## 실행 방법

전용 DB와 앱을 준비한 후 회원·상품을 준비한다.
아래 명령은 저장소 최상위 경로에서 실행한다.

    python3 perf/order-write-capacity/prepare-users.py --users 100

    docker compose -f perf/order-list/compose.yaml exec -T mysql \
    mysql --default-character-set=utf8mb4 \
    -uperf -pperf-local-only attraction_order_write_capacity_perf \
    < perf/order-write-capacity/prepare-products.sql

소규모 검사는 회원당 3회, 반복 부하는 60초다.
기존 결과 폴더가 있으면 다른 실행 이름을 사용한다.

    caffeinate -i python3 perf/order-write-capacity/run-load.py \
    order-shared-smoke-example \
    --mode smoke --distribution shared --vus 2

    caffeinate -i python3 perf/order-write-capacity/run-load.py \
    order-shared-load-example \
    --mode load --distribution shared --vus 100

분산 조건은 --distribution split으로 지정한다.
JFR은 Java 17의 JAVA_HOME 설정 후 --jfr을 추가한다.
진단 실행은 성능 전후 비교에서 제외한다.

동일한 전용 DB에 다른 주문 테스트를 동시에 실행하지 않는다.
실행 후 DB 대조가 끝나기 전에 다른 부하를 시작하지 않는다.
