# 주문 자동 취소 정확성 및 인덱스 비교 실험

## 1. 목적과 결론

30분 이상 지난 결제 대기 주문을 자동 취소하는 기존 기능의 정확성과 처리 비용을 확인했다.

완료 주문 10만 건이 쌓인 환경에서 자동 취소 대상 조회가 전체 주문을 스캔하는 것을 확인하고, `(status, created_at, id)` 복합 인덱스를 적용했다.

확인 결과:

- 만료 주문 조회의 전체 스캔과 별도 정렬이 제거됐다.
- 취소 대상이 없는 경우에도 인덱스로 대상 없음이 확인됐다.
- 인덱스 적용 전후 모든 정상 측정에서 주문·결제 취소와 재고 복구가 일치했다.
- 전체 취소 처리 시간 합계의 중앙값은 2,978ms에서 2,880ms로 약 3.3% 감소했다.
- 실행 편차와 측정값의 범위가 겹쳐 전체 취소 처리의 뚜렷한 성능 개선으로 판단하지 않았다.

서비스 코드와 스케줄러 구현은 변경하지 않았다. 인덱스는 개인 실험 DB에만 적용했다.

## 2. 기존 기능

자동 취소 작업은 다음 조건으로 주문을 조회한다.

- 주문 상태가 `PENDING`
- 생성 시각이 현재 시각보다 30분 이상 이전
- `created_at ASC, id ASC` 순서
- 한 번에 최대 100건

주문자 정보도 함께 조회하며, 조회된 주문은 각각 별도 트랜잭션으로 취소 처리한다.

처리 로그:

```text
event=ORDER_AUTO_CANCEL_PROCESSED
count=...
failedCount=...
skippedCount=...
durationMs=...
result=...
```

`durationMs`는 해당 작업 호출의 조회와 취소 처리 시간을 나타낸다. 다음 작업까지의 대기 시간은 포함하지 않는다.

## 3. 실험 환경

| JVM 메모리 | `-Xms256m -Xmx512m` |
| DB | 개인 MySQL의 `attraction_auto_cancel_perf` |

| MySQL 접속 | `127.0.0.1:13316` |
| Redis 접속 | `127.0.0.1:16396` |
| 앱 포트 | `127.0.0.1:18088` |

| 첫 작업 대기 설정 | 10초 |

별도 API 부하 발생기를 사용하는 실험이 아니라, 실제 스케줄러를 실행한 백그라운드 작업 비교 실험이다.

측정 중 기존 개인 테스트 앱은 종료했다. MySQL과 Redis는 같은 로컬 Docker 환경을 사용했다.

`source-commit.txt`는 기록 당시 체크아웃된 소스 커밋이다. JAR 해시를 별도로 수집하지 않았으므로 실행 바이너리를 식별하는 자료와는 구분한다.

## 4. 데이터 구성

기존 실험 DB의 테이블 구조를 전용 DB에 복사한 뒤 테스트 데이터를 준비했다. 원본 DB의 기존 대기 주문 4건은 유지했다.

### 기본 동작 검사

| 조건 | 준비 건수 | 예상 결과 |
|---|---:|---|
| 35분·45분·60분 지난 대기 주문 | 3 | 주문·결제 취소 |
| 생성 직후 대기 주문 | 1 | 대기 유지 |
| 결제 완료 주문 | 1 | 완료 유지 |
| 이미 취소된 주문 | 1 | 취소 유지, 재고 중복 복구 없음 |

첫 실행에서 만료 주문 3건만 취소됐고 재고는 95개에서 98개로 복구됐다.

이후 시간이 지나 생성 직후 주문도 만료됐다. 본 측정 전에 해당 주문 1건을 별도로 자동 취소해 재고 99개를 확인했다. 이 준비 작업은 성능 비교에 포함하지 않았다.

### 반복 측정 시작 상태

| 항목 | 값 |
|---|---:|
| 전체 주문 | 100,306건 |
| 완료 주문 | 100,001건 |
| 기존 취소 주문 | 5건 |
| 측정용 만료 대기 주문 | 300건 |
| 전체 주문 항목 | 306건 |
| 전체 결제 | 306건 |
| 측정용 상품 시작 재고 | 700개 |
| 측정용 주문별 수량 | 1개 |

배경 데이터인 완료 주문 10만 건은 기존 합성 데이터를 복사했다. 이 배경 주문에는 주문 항목·결제를 복사하지 않았으며, 실제 구매 이력 전체를 재현한 데이터는 아니다.

측정용 주문 300건에는 주문 항목과 결제를 각각 생성했다. 같은 회원과 같은 전용 상품을 사용하며, 생성 시각은 모두 60분 이상 이전으로 설정했다.

## 5. 인덱스 변경

기존 주문 인덱스:

- `PRIMARY (id)`
- `idx_orders_user_created_id (user_id, created_at DESC, id DESC)`

추가 인덱스:

```sql
CREATE INDEX idx_orders_status_created_id
ON attraction_auto_cancel_perf.orders (
    status,
    created_at,
    id
);
```

상태 조건으로 범위를 좁히고, 생성 시각과 ID 순서로 오래된 주문을 조회하려는 목적이다.

기존 인덱스는 유지했다. 신규 인덱스의 저장 공간 및 주문 생성·상태 변경 시 유지 비용은 별도로 측정하지 않았다.

## 6. 실행 계획 결과

조회 조건과 정렬 순서는 기존 저장소 조회에 맞췄으며, `EXPLAIN ANALYZE`로 실행 계획을 확인했다.

### 만료 주문 300건 중 100건 조회

| 항목 | 적용 전 | 적용 후 |
|---|---|---|
| 전체 주문 수 | 100,306건 | 100,306건 |
| 만료 주문 수 | 300건 | 300건 |
| 주문 접근 방식 | 전체 스캔 | 신규 인덱스 범위 스캔 |
| 주문 접근 단계의 실제 반환 행 수 | 100,306건 | 100건 |
| 별도 정렬 | 있음 | 없음 |
| 단일 조회 관측 시간 | 15.3ms | 0.305ms |

실제 반환 행 수는 실행 계획의 해당 노드에 표시된 값이다. 물리 디스크 읽기 횟수나 전체 내부 접근 횟수를 뜻하지 않는다.

위 시간은 각각 단일 실행 관측값이다. 반복 측정으로 확정한 조회 개선율로 표현하지 않는다.

### 취소 대상이 없는 경우

| 항목 | 적용 전 | 적용 후 |
|---|---:|---:|
| 전체 주문 수 | 100,006건 | 100,306건 |
| 취소 대상 | 0건 | 0건 |
| 주문 접근 방식 | 전체 스캔 | 신규 인덱스 범위 스캔 |
| 별도 정렬 단계 | 있음 | 없음 |
| 단일 조회 관측 시간 | 15.6ms | 0.00954ms |

적용 전후 데이터 건수와 상태 구성이 다르므로 정확한 시간 개선율 비교로 사용하지 않는다.

적용 전 정렬 단계도 입력이 0건이므로 주문 10만 건을 정렬했다고 해석하지 않는다. 핵심은 대상이 없어도 발생하던 전체 스캔을 피한 점이다.

## 7. 자동 취소 반복 측정 결과

매 실행 전에 같은 시작 DB를 복원했다. 적용 후 측정은 복원 후 신규 인덱스를 다시 생성했다.

별도 앱 예열 없이 앱을 재시작했으며, 한 실행에서 100건씩 세 차례 처리했다.

### 인덱스 적용 전

| 결과 폴더 | 첫 100건 | 다음 100건 | 마지막 100건 | 합계 |
|---|---:|---:|---:|---:|
| `auto-cancel-before-02` | 1,170ms | 887ms | 796ms | 2,853ms |
| `auto-cancel-before-03` | 1,288ms | 868ms | 2,003ms | 4,159ms |
| `auto-cancel-before-04` | 1,145ms | 946ms | 887ms | 2,978ms |

`auto-cancel-before-01`은 중간 종료한 실행으로 비교에서 제외했다.

### 인덱스 적용 후

| 결과 폴더 | 첫 100건 | 다음 100건 | 마지막 100건 | 합계 |
|---|---:|---:|---:|---:|
| `auto-cancel-after-01` | 1,089ms | 1,090ms | 869ms | 3,048ms |
| `auto-cancel-after-02` | 1,113ms | 984ms | 783ms | 2,880ms |
| `auto-cancel-after-03` | 1,376ms | 728ms | 605ms | 2,709ms |

### 해석

세 실행의 처리 시간 합계 중앙값:

- 적용 전: 2,978ms
- 적용 후: 2,880ms
- 감소량: 98ms, 약 3.3%

이는 실행 사이의 대기 시간을 제외한 작업 시간 합계다. 300건 전체가 취소될 때까지의 경과 시간이나 API 응답 시간과는 다르다.

조회 실행 계획은 개선됐지만 전체 취소 처리 시간의 변화는 작았고 실행 편차가 있었다. 전체 처리의 뚜렷한 개선이나 인덱스만의 인과 효과를 확정하지 않았다.

## 8. 실행 후 정확성 검증

인덱스 적용 전후 정상 측정 6회 모두 다음 조건을 확인했다.

- 처리 로그의 성공 건수 합계 300건
- 실패 및 건너뜀 0건
- 전용 주문 300건 모두 `CANCELLED`
- 연결된 결제 300건 모두 `CANCELLED`
- 전용 주문 총수량 300개
- 전용 상품 재고 700개 → 1,000개
- 상품 상태 `ON_SALE`
- 남은 대기 주문 0건
- 전체 주문 100,306건 유지
- 전체 주문 항목·결제 각각 306건 유지

추가 스케줄 실행의 `count=0` 로그는 처리할 대상이 없음을 의미한다. 위 처리 시간 합계에는 포함하지 않았다.

## 9. 실행 및 복원 방법

명령은 저장소 루트에서 실행한다.

### 준비 조건

- 개인 MySQL·Redis 컨테이너 실행
- Java 17
- 측정할 코드로 빌드한 실행 JAR
- 전용 DB 및 테스트 데이터 준비
- 다른 개인 테스트 앱 종료
- 18088·18089 포트 미사용

```bash
export JAVA_HOME=$(/usr/libexec/java_home -v 17)
export PATH="$JAVA_HOME/bin:$PATH"

bash gradlew bootJar --console=plain
```

초기 DB 생성, 스키마 복사, 완료 주문 10만 건 복사는 수동으로 수행했다. 이 폴더의 SQL만으로 빈 DB에서 모든 시작 데이터를 구성하는 것은 아니다.

`prepare-smoke.sql`은 초기 기본 동작 데이터용이다. `prepare-load.sql`은 기본 검사와 정리 및 배경 데이터 구성이 끝난 100,006건 상태를 전제로 한다. 준비 조건이 다르면 중단된다. MySQL의 `--force` 옵션은 사용하지 않는다.

### 반복 측정 시작 상태 복원

전용 앱을 종료한 뒤 실행한다. 아래 복원은 전용 DB 테이블과 데이터를 백업 내용으로 되돌린다.

```bash
docker compose -f perf/order-list/compose.yaml exec -T mysql \
mysql -uperf -pperf-local-only attraction_auto_cancel_perf \
< "/Users/t2025-m0237/Documents/Codex/perf-backups/order-auto-cancel-start-20261105.sql"
```

해당 백업은 개인 환경에 별도 보관하며 Git에 포함하지 않는다. 다른 환경에서는 동일한 시작 데이터를 별도로 준비해야 한다.

복원 후 확인 조건:

- 대기 주문 300건
- 전용 상품 재고 700개
- 전체 주문 100,306건
- 전체 항목·결제 각각 306건

### 적용 후 측정의 추가 단계

시작 백업에는 신규 인덱스가 없다. 적용 후 측정은 매번 복원 다음에 실행한다.

```bash
docker compose -f perf/order-list/compose.yaml exec -T mysql \
mysql -uperf -pperf-local-only attraction_auto_cancel_perf \
< perf/order-auto-cancel/index-order-auto-cancel.sql
```

### 앱 실행과 결과 보관

```bash
python3 perf/order-auto-cancel/start-app.py
```

시작 스크립트는 `.local/app.log`를 덮어쓴다. 이전 실행 로그를 보관한 뒤 다시 실행한다.

```bash
tail -n +1 -f perf/order-auto-cancel/.local/app.log \
| grep --line-buffered 'event=ORDER_AUTO_CANCEL'
```

`count=100`인 성공 로그 세 줄을 확인한다. Control + C는 로그 보기만 종료하므로 앱은 별도로 종료한다.

```bash
perf_auto_pid=$(cat perf/order-auto-cancel/.local/app.pid)
kill "$perf_auto_pid"
```

재실행 전에 앱 로그, 사용 설정, 소스 커밋, 적용 인덱스 및 DB 검증 결과를 실행별 결과 폴더에 보관한다.

## 10. 파일과 보관 정책

| 파일 | 역할 |
|---|---|
| `application-perf.yaml` | 전용 DB·포트·스케줄 설정 |
| `start-app.py` | Java 17 확인 및 전용 앱 실행 |
| `prepare-smoke.sql` | 기본 동작 검사 데이터 준비 |
| `prepare-load.sql` | 만료 주문 300건 준비 |
| `index-order-auto-cancel.sql` | 실험용 복합 인덱스 적용 |
| `.local/` | 앱 로그·PID·로컬 준비 자료 |
| `results/` | 실행 조건·로그·실행 계획·DB 검증 결과 |

`.local/`, `results/`, `__pycache__/`는 Git에서 제외한다.

설정에 있는 인증·결제 관련 값은 로컬 테스트 전용 값이다. 실제 비밀값으로 대체해 커밋하지 않는다.

원본 결과와 DB 시작 상태는 개인 백업 폴더에 별도 보관한다.

## 11. 범위와 한계

- 개인 DB의 합성 데이터 실험이며 공용·배포 DB에는 적용하지 않았다.
- 앱과 Docker가 같은 Mac의 자원을 공유한다.
- DB 복원과 앱 재시작은 수행했지만 MySQL 버퍼와 운영체제 캐시까지 초기화하지 않았다.
- 적용 전 측정 후 적용 후 측정을 수행했으며 실행 순서를 교차하지 않았다.
- 앱 시작 직후의 초기화·예열 영향이 포함될 수 있다.
- 단일 회원·단일 상품의 만료 주문을 순차 처리했다.
- 여러 서버에서 스케줄러가 동시에 실행되는 상황은 검증하지 않았다.
- 결제 승인·환불과 자동 취소의 경합, 실패 복구, 대규모 적체는 이번 반복 측정 범위에 포함하지 않았다.
- 운영 환경의 처리 용량이나 최대 처리량을 증명하지 않는다.
- 인덱스의 저장 공간과 쓰기 유지 비용은 별도 검증이 필요하다.
