# 주문 생성·취소 정확성 검증 및 부하 테스트

## 목적과 결론

주문 생성·취소의 동시 요청 정확성과 반복 요청의 응답 시간을 확인한다.

- 재고 5개에 주문 요청 10건을 보내 5건 성공·5건 재고 부족 거절을 확인했다.
- 동일 주문의 취소 요청 10건에서 1건 성공·9건 취소 불가 거절을 확인했다.
- 10 VU 반복 측정에서 응답 내용과 DB 상태·재고의 일치를 확인했다.
- 같은 상품에 대한 행 잠금 대기를 관측했다.
- 취소 처리 순서 변경을 시험했으나 성능 개선을 확인하지 못해 기존 순서로 복구했다.

이 실험은 개인 테스트 환경의 결과이며 배포 서버의 최대 처리 능력을 의미하지 않는다.

## 실행 환경

- 개인 Mac에서 Spring Boot 실행
- Docker에서 MySQL·Redis·k6 실행
- 개인 DB: `attraction_perf`
- API: `127.0.0.1:18086`
- 관리 포트: `127.0.0.1:18087`
- Java 17, JVM 힙 초기 256MB·최대 512MB
- DB 커넥션 풀 최대 크기 10개
- Docker Compose와 공통 도구는 `perf/order-list` 사용

앱·DB·부하 발생기가 같은 Mac의 자원을 공유한다.

## 사전 조건

1. `perf/order-list/README.md`에 따라 개인 테스트 환경을 준비한다.
2. 기존 테스트 회원 `perf0000@example.test`가 LOCAL·ACTIVE 상태로 존재해야 한다.
3. 해당 회원의 비밀번호가 공통 준비 도구의 테스트 비밀번호와 일치해야 한다.
4. 현재 앱 코드에 맞는 DB 스키마가 필요하다. 특히 `ticket_products.version` 컬럼을 확인한다.
5. DB 구조를 변경하기 전에는 기존 앱을 중지하고 DB를 백업한다.
6. 실제 서비스의 DB·결제 서버·인증 비밀값을 사용하지 않는다.

실험에서는 기존 개인 DB에 `version BIGINT NOT NULL DEFAULT 0` 컬럼을 추가한 뒤 현재 앱을 빌드했다. 이미 컬럼이 존재하는 환경에서 같은 ALTER 문을 반복 실행하지 않는다.

스키마 자동 갱신을 사용하는 환경이므로 앱 시작에 따른 스키마 변경 가능성도 확인한다.

## 파일 구성

| 파일 | 역할 |
|---|---|
| `prepare.sql` | 전용 회원 10명과 기본 검사 상품 준비 |
| `check-order.py` | 생성·취소·재취소 거절 및 DB 상태 확인 |
| `prepare-race.sql` | 재고 5개인 동시 주문 전용 상품 준비 |
| `check-race.py` | 서로 다른 회원 10명의 동시 주문 검사 |
| `check-cancel-race.py` | 같은 주문에 대한 동시 취소 검사 |
| `prepare-load.sql` | 반복 부하용 상품 준비 |
| `prepare-load.py` | 로그인 및 실행 전 DB 기준 저장 |
| `order-write.js` | k6 주문 생성·취소 시나리오 |
| `run-write.py` | 준비·측정·자료 수집·DB 검증 실행 |
| `verify-load.py` | k6 결과와 실행 후 DB 상태 대조 |

`.local/`과 `results/`는 Git에서 제외한다. 토큰·비밀번호를 출력하거나 저장소에 추가하지 않는다.

## 기본 동작 검사

명령은 저장소 루트에서 실행한다.

```bash
docker compose -f perf/order-list/compose.yaml exec -T mysql \
mysql -uperf -pperf-local-only attraction_perf \
< perf/order-write/prepare.sql

python3 perf/order-write/check-order.py order-write-smoke-01
```

확인 항목:

- 주문 생성: HTTP 201, 재고 100 → 99
- 주문 취소: HTTP 200, 주문·결제 CANCELLED, 재고 100 복구
- 재취소: HTTP 409, 재고 100 유지
- 주문자·금액·방문일·주문 항목·결제 데이터 일치

검사 결과 폴더가 이미 있으면 새로운 실행 ID를 사용한다. 기존 결과를 덮어쓰지 않는다.

## 동시 주문·취소 검사

다음 순서는 아직 사용하지 않은 동시 주문 전용 상품을 기준으로 한다.

```bash
docker compose -f perf/order-list/compose.yaml exec -T mysql \
mysql -uperf -pperf-local-only attraction_perf \
< perf/order-write/prepare-race.sql

python3 perf/order-write/check-race.py order-write-race-01

python3 perf/order-write/check-cancel-race.py \
order-write-cancel-race-01 \
--source-run order-write-race-01
```

관측 결과:

| 검사 | 성공 | 정상 업무 거절 | 최종 재고 |
|---|---:|---:|---:|
| 재고 5개에 동시 주문 10건 | 5건 | 5건 | 0개 |
| 같은 주문에 동시 취소 10건 | 1건 | 9건 | 1개 |

취소 대상 주문·결제는 CANCELLED가 됐고, 나머지 주문 4건은 유지됐다.

전용 상품은 `PERF_ORDER_WRITE_RACE_01`로 고정돼 있다. 실행 ID만 바꿔도 이미 사용한 상품으로는 동시 주문 검사를 다시 수행할 수 없다. 재고를 강제로 초기화하거나 기존 주문을 삭제하지 말고, 반복 검사가 필요하면 상품과 검사 도구를 함께 분리한다.

## 반복 부하 테스트

전용 상품을 준비한다.

```bash
docker compose -f perf/order-list/compose.yaml exec -T mysql \
mysql -uperf -pperf-local-only attraction_perf \
< perf/order-write/prepare-load.sql
```

측정 조건:

- 서로 다른 전용 회원 10명
- 같은 상품에 수량 1개 주문
- 상품 가격 10,000원, 시작 재고 10,000개
- 주문 생성 → 본인 주문 취소 → 1초 대기
- 10 VU, 실행별 60초
- 진행 중 작업의 종료 대기 최대 30초
- 준비 실행 후 본 측정 3회

아래는 실행 형식이다. `실행앱커밋`은 실제 빌드·기동한 코드의 커밋 해시로 바꾼다.

```bash
python3 perf/order-write/run-write.py order-write-warmup-새번호 \
--phase warmup --vus 10 --app-code 실행앱커밋

python3 perf/order-write/run-write.py order-write-baseline-새번호 \
--phase baseline --vus 10 --app-code 실행앱커밋
```

- 실행기는 VU 1~10을 지원한다.
- 각 실행에서 로그인과 실행 전 기준 데이터를 준비한다.
- `--app-code`는 실행자가 지정한 기록이며 바이너리에서 자동 검증한 값은 아니다.
- 기존 결과 폴더는 재사용하지 않는다.
- 준비 실행은 성능 비교에서 제외한다.
- 취소된 주문 이력은 삭제하지 않으므로 실행마다 데이터가 누적된다.
- 시작 재고가 예상과 다르거나 미취소 주문이 남아 있으면 원인을 확인한다.
- 다른 DB 작업이나 부하 테스트를 동시에 실행하지 않는다.

## 실행 후 검증

`run-write.py`는 k6 종료 후 `verify-load.py`를 자동 실행한다.

확인 항목:

- 생성 시도·생성 성공·취소 시도·취소 성공·완료 흐름 수 일치
- 응답 검증 실패 및 HTTP 실패 없음
- 신규 주문·주문 항목·결제 수 일치
- 주문자·금액·수량·방문일 일치
- 주문·결제 CANCELLED
- 최종 재고 10,000개, 상품 상태 ON_SALE

검증은 다음 부하 실행 전에 완료해야 한다. 검증 도구가 실행 전 주문 ID 이후의 데이터를 확인하므로, 다른 실행이 추가된 뒤 과거 결과를 재검증하면 범위에 새 데이터가 포함될 수 있다.

## 잠금 진단

별도 진단 실행 전후 MySQL 전체 누적값의 증가분:

- 잠금 대기 횟수: 1,070회
- 누적 잠금 대기 시간: 22,573ms

이는 여러 요청의 대기를 합산한 값이다. 특정 상품의 대기 시간이나 API 응답 시간과 동일하지 않다.

추가 실행 중 `performance_schema.data_lock_waits`와 `data_locks`를 조회해 `ticket_products`의 PRIMARY 키 14번에 대한 행 잠금 대기를 관측했다.

해당 표본은 특정 시점의 대기 대상을 보여주며 전체 대기 횟수나 시간의 분포를 의미하지 않는다.

## 처리 순서 변경 실험

실험 커밋: `5588098`

- 변경 전: 결제 잠금 → 주문 취소 → 재고 복구 → 결제 취소
- 변경 후: 결제 잠금 → 주문 취소 → 결제 취소 → 재고 복구

상품 잠금을 획득한 뒤 수행하는 작업을 줄이면 대기가 감소할 수 있다는 가설을 검증했다. 관련 테스트와 재고 복구 후 강제 오류에 대한 DB 롤백 테스트를 수행했다.

변경 후 측정:

|---|---:|---:|---:|---:|---:|---:|
| 01 | 560회 | 45.65ms | 65.19ms | 33.31ms | 52.09ms | 98.05ms |

| 03 | 570회 | 36.97ms | 57.37ms | 29.59ms | 49.86ms | 91.55ms |

세 실행 모두 응답 및 DB 검증을 통과했고 HTTP 실패는 없었다. 최종 재고는 매번 10,000개였다.

실행별 지표 세 값의 중앙값 비교:

| 항목 | 변경 전 | 변경 후 |
|---|---:|---:|
| 취소 평균 | 29.38ms | 30.17ms |

| 전체 흐름 P95 | 83.00ms | 98.05ms |
| 상품 잠금 조회 평균 | 19.21ms | 21.05ms |

이는 전체 요청을 합쳐 계산한 지표가 아니다. 상품 잠금 조회 시간에는 잠금 대기 외 SQL 처리 시간도 포함된다.

성능 개선을 확인하지 못해 `17f762f`에서 기존 처리 순서로 복구했다. 복구 후 관련 테스트와 실제 API의 기본 동작 검사를 다시 수행해 통과했다.

앱 재시작과 환경 편차가 있어 변경만을 성능 차이의 원인으로 확정하지 않는다.

## 보관 자료와 한계

반복 부하 실행의 결과 폴더에 다음 자료를 보관한다.

- HTML 보고서와 측정값 JSON
- 실행 조건 및 앱 코드 수동 기록
- 디스크의 JAR 해시
- 검증 기준 데이터와 실행 도구 사본
- SQL 누적 통계 전후 자료
- 자원 사용 표본
- DB 검증 결과

기본 동작·동시성 검사는 결과 JSON을 보관한다. 실행 결과와 인증 파일은 Git에 포함하지 않는다.

이번 실험은 모든 사용자가 같은 상품을 주문하고 취소하는 제한된 시나리오다. 외부 결제 승인·환불·자동 취소 부하는 포함하지 않았다.

1초 대기가 있는 조건이므로 최대 처리량 측정이 아니며, 배포 환경의 성능이나 2,000명 수용 여부를 판단할 수 없다.
