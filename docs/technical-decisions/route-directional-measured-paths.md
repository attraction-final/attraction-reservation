# 어트랙션 간 이동은 방향별 실측 구간만 사용하기

> 분류: 데이터 정합성 · 관련 이슈: KAN-136, KAN-139, KAN-161 · 기준 코드: `dev` `TravelTimeTable`, `AttractionPath`

| 항목 | 내용 |
| --- | --- |
| 문제 | A→B와 B→A의 실측 시간이 다르다. 데이터가 없는 구간을 어떻게 다룰지도 정해야 한다 |
| 결정 | 출발 → 도착 방향마다 실측값을 저장하고, 없거나 막힌 구간은 그 순서를 쓰지 않는다 |
| 근거 | 역방향 값이나 추정값으로 채우면 추천 결과에 근거 없는 값이 섞인다 |
| 한계 | 데이터가 빠지면 추천할 수 있는 순서가 줄어든다 |

## 1. 문제

어트랙션끼리의 이동 시간을 어떻게 구할지, 그리고 데이터가 없는 구간을 어떻게 다룰지 정해야 한다.

## 2. 선택지

| 방식 | 문제점 |
| --- | --- |
| 모든 구간을 하버사인으로 추정 | 우회 계수가 구간마다 1.34 ~ 1.98로 크게 다르다. 하나의 계수로는 구간별 차이를 반영하지 못한다 |
| 대칭 가정 (A→B = B→A, 데이터 절반) | 실측했을 때 방향마다 값이 실제로 달랐다 |
| 없는 구간을 역방향 값·추정값으로 대체 | 추천 결과에 근거 없는 값이 섞인다 |
| **방향별 실측 + 없으면 그 순서 무효** | 데이터가 빠지면 추천 가능한 순서가 줄어든다 |

## 3. 결정

- `attraction_paths`에 **출발 → 도착 방향마다 한 행씩** 저장한다 (10개 어트랙션 × 9방향 = 90건, 네이버 지도 도보 길찾기 측정값).
- 탐색은 `from → to` 방향의 활성 구간만 찾는다. 없거나 비활성이면 **그 방문 순서를 쓰지 않는다.** 역방향 값이나 추정값으로 채우지 않는다.
- `is_active = false`: 공사 등으로 막힌 구간. 계산에서 뺀다.
- `is_estimated = true`: 실측이 아닌 근사값. 응답에 추정 여부를 표시한다.

## 4. 근거

- 방향별로 다른 실측값을 가진 **방향 그래프(비대칭)** 로 모델링해야 실제 이동 시간을 반영할 수 있다.
  - `RouteSearcherTest#search_MeasuredPath_ChoosesShorterDirection`: A→B 30분, B→A 5분이면 B → A 순서를 고른다.
  - `RouteRecommendationMeasuredDataIntegrationTest`: 배포용 실측 데이터(Flyway V13)로 추천하면 콜럼버스 대탐험 → 범퍼카 실측 9분을 그대로 쓴다. 역방향 값(12분)을 썼다면 13:12 슬롯을 놓친다.
- "모르는 값은 만들지 않는다"는 원칙으로, 추천 결과의 모든 이동 시간이 실측값이거나 추정 표시가 붙은 값이 되게 했다.
- 구간이 막혀도 전체 추천이 실패하지 않는다. 그 구간을 지나는 순서만 빠지고, 탐색이 다른 순서나 부분 경로를 찾는다.

## 5. 한계

- 어트랙션이 하나 늘면 구간을 양방향으로 다시 측정해 넣어야 한다 (n개면 `n × (n − 1)`건).
