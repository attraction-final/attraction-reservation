# 내 정보 조회 부하 테스트 및 DB 연결 풀 비교

## 목적

`GET /api/users/me`의 응답 정확성과 부하 증가에 따른 응답 시간을 확인한다. 지연 원인을 진단하고 DB 연결 풀 설정을 변경해 반복 측정한다.

실제 HTTP 부하는 k6가 발생시킨다. Python은 테스트 데이터·로그인 토큰 준비, k6 실행, 결과 저장을 담당한다.

## 환경과 조건

- 개인 Mac: 메모리 16GiB, 논리 CPU 10개
- Docker 할당: CPU 10개, 메모리 약 7.75GiB
- Spring Boot: 호스트의 `127.0.0.1:18086`
- MySQL·Redis·k6: Docker 실행
- 최종 연결 풀 비교: Java 17.0.19, JVM 힙 초기 256MB·최대 512MB
- 앱 코드 기준: `49b39a1`로 수동 기록
- 비교 중 같은 JAR 사용. 실행 바이너리의 커밋을 자동 검증한 값은 아님
- 기존 주문 목록 테스트의 개인 환경과 실행 도구를 사용

앱·DB·부하 발생기가 같은 Mac의 자원을 공유한다.

## 데이터와 요청 방식

- 기본 측정: 합성 회원 100명
- 단계별 부하: 기존 100명과 추가 1,900명으로 구성한 회원 2,000명
- VU마다 서로 다른 회원 계정 사용
- 각 회원이 본인의 정보를 반복 조회
- 로그인은 측정 전에 수행
- 본 측정은 60초이며 응답 후 1초 대기
- 일정한 VU 수를 유지하는 닫힌 부하 모델

추가 회원 준비 SQL은 기존 테스트 계정의 비밀번호 해시를 재사용한다. 회원가입이나 비밀번호 암호화 성능을 측정하는 데이터가 아니다.

## 응답 검증

실행 전에 미인증 조회가 401로 거절되는지 확인한다.

정상 조회마다 다음 7개 항목을 검증한다.

- HTTP 200
- 업무 성공 여부
- 본인 회원 ID
- 이메일
- 닉네임
- 권한과 상태
- 응답 필드 구성

응답 시간은 `user_me_duration`을 사용한다. 공통 HTTP 지표에는 사전 미인증 확인 요청도 포함된다.

## 실행 준비

저장소 루트에서 실행한다. 개인 환경의 최초 구성·앱 실행·기본 회원과 주문 데이터 준비는 `../order-list/README.md`를 따른다.

Java 17, Python 3, Docker Desktop이 필요하다.

추가 회원 준비는 개인 `attraction_perf` DB에서 수행한다. `prepare-load-users.sql`을 실행한 뒤 활성 테스트 회원이 2,000명인지 확인한다.

기본 100명 측정에는 `run-user.py`, 100·300·500·1,000·2,000 VU 단계별 측정에는 `run-load.py`를 사용한다.

## 실행 예시

### 기본 100 VU 측정

```bash
python3 perf/user-me/run-user.py user-me-baseline-new-01
```

### 단계별 부하 측정

```bash
python3 perf/user-me/run-load.py user-me-step-new-300-01 --vus 300
```

계정 준비와 로그인 토큰 갱신은 실행기가 수행한다. 기존 결과를 덮어쓰지 않도록 실행 ID를 매번 다르게 지정한다.

### 연결 풀 비교 절차

1. `../order-list/application-perf.yaml`에서 비교할 연결 풀 최대 크기를 설정한다.
2. 개인 테스트 앱을 종료하고 같은 JAR로 다시 실행한다.
3. 1,000 VU로 60초 준비 실행을 한 번 수행한다.
4. 2,000 VU로 60초 본 측정을 세 번 수행한다.
5. 다른 연결 풀 설정에서도 같은 준비·측정 절차를 수행한다.

준비 실행은 비교 결과에서 제외한다. 설정 변경은 개인 테스트 환경에만 적용한다.

새 비교에서는 Java 버전, JAR 해시, 연결 풀 설정, 데이터 수와 실행 순서를 함께 기록한다. 현재 실행기의 메타데이터는 실제 연결 풀 설정을 자동 탐지하지 않는다.

## 중단 기준

단계별 부하 실행에서는 30초 이후 누적 지표를 기준으로 다음 조건을 평가한다.

- P95가 2,000ms 이상
- HTTP 실패율이 5% 이상

조건을 위반하면 실행을 중단한다. 이는 로컬 탐색용 기준이며 운영 서비스의 성능 목표가 아니다.

별도로 HTTP 실패와 응답 검증 실패는 0을 통과 기준으로 사용한다. 짧은 구간의 지표를 평가하는 이동 구간 방식은 아니다.

## 진단과 최종 비교 결과

2,000 VU 진단의 JFR에서 HTTP 처리 스레드가 HikariCP 연결 획득을 기다리는 기록을 확인했다. 이에 연결 풀 최대 크기 10개와 20개를 비교했다.

저장 공간 부족과 Docker 장애가 발생한 실행은 경위를 기록하고 최종 비교에서 제외했다. 환경 복구 후 연결 풀 20개를 측정하고, 10개로 되돌려 재확인했다.

| 비교 조건 | 본 측정 결과 폴더 |
|---|---|
| 연결 풀 10개 | `user-me-pool10-recheck-01`, `02`, `03` |
| 연결 풀 20개 | `user-me-pool20-baseline-01`, `02`, `03` |

아래 수치는 각 조건의 세 실행에서 얻은 지표의 중앙값이다.

| 지표 | 연결 풀 10개 | 연결 풀 20개 | 감소율 |
|---|---:|---:|---:|
| 실행별 평균 응답 시간의 중앙값 | 999.42ms | 444.98ms | 55.5% |
| 실행별 P95의 중앙값 | 1,198.56ms | 594.81ms | 50.4% |
| 실행별 P99의 중앙값 | 1,285.10ms | 686.76ms | 46.6% |

최종 여섯 실행은 모두 HTTP 실패·응답 검증 실패·중단된 반복 없이 완료됐다.

전체 요청을 합쳐 계산한 평균이나 백분위수가 아니다. 감소율은 반올림 전 원본 값으로 계산했다.

## 판단과 한계

연결 획득 대기 진단과 설정 복원 후 재측정 결과는 연결 풀 설정이 응답 시간에 영향을 줬다는 근거다. 다만 다음 한계가 있다.

- 측정 순서를 무작위로 배치하지 않았다.
- 캐시와 백그라운드 작업을 완전히 통제하지 못했다.
- 연결 풀 20개 적용 후 대기 시간 감소를 JFR로 직접 재측정하지 않았다.
- 연결 수 증가에 따른 DB 자원 사용 비용을 함께 고려해야 한다.
- 연결 풀 20개가 모든 환경에서 최적이라는 의미는 아니다.
- 최대 처리량이나 운영 환경에서의 2,000명 수용 능력을 입증한 결과가 아니다.
- 앱 조회 코드와 캐시는 변경하지 않았다.

개인 설정은 재확인을 위해 연결 풀 10개로 복원했다. 공유 환경 적용은 별도 검토한다.

## 결과 파일과 보관

결과는 `results/<실행 ID>/`에 저장한다.

- `metadata.json`: 실행 조건·도구 커밋·시작과 종료 시각·종료 코드
- `summary.json`: 최종 측정 지표
- `metrics.json`: 시간대별 원본 지표
- `dashboard.html`: HTML 보고서
- `terminal.txt`: 실행 출력
- `fixture.json`: 합성 회원 검증 기준
- `sql-digests-before.txt`, `sql-digests-after.txt`: 누적 SQL 통계
- `resource-samples.jsonl`: 앱·컨테이너 자원 표본

SQL 통계는 전후 차이로 해석한다. 자원 표본은 연속적인 전체 시스템 기록이 아니다. 단계별 실행 종료 직후 k6 컨테이너가 삭제되면 마지막 자원 수집이 실패할 수 있다.

`.local/`, `results/`, `__pycache__/`는 Git에서 제외한다. 토큰과 원본 측정 결과는 커밋하지 않는다.

원본 자료와 JFR은 별도 백업으로 보관한다. 실패한 실행도 정상 실행과 구분해 보관한다.
