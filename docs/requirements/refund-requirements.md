# 기능 요구사항 명세서

## 1. 기본 정보
- **기능명:** 환불 (전체 환불 / 부분 환불)
- **작성 목적:** 환불 기능의 API 계약, 검증 규칙, 오류 응답, 처리·재시도 정책을 코드를 보지 않고 이 문서만으로 확인할 수 있게 정리한다.
- **관련 화면 / 메뉴:** 없음 (API만 제공)

## 2. 기능 개요
- **기능 설명:** 결제 완료된 주문을 전체 또는 티켓 단위로 환불한다. 환불 요청을 먼저 기록하고 PG(결제사) 결제를 취소하며, 취소에 실패하면 자동으로 재시도한다.
- **개발 목적 / 해결하려는 문제:** 사용자는 결제한 주문을 전체 또는 일부 환불할 수 있어야 한다. PG 취소가 실패하거나 처리 중 서버가 종료돼도 환불 요청이 사라지지 않아야 하고, 같은 티켓이 두 번 환불되면 안 된다.
- **사용자 및 실행 조건:**
  - 결제 완료(또는 부분 환불) 상태인 본인 결제만 환불할 수 있다. 관리자는 소유자·기한과 관계없이 환불할 수 있다(REQ-003).
  - 미사용(`UNUSED`) 티켓만 환불할 수 있다.
  - 탈퇴한 회원의 결제는 환불할 수 없다.
- **기능 범위:**
  - 전체 환불 API, 부분 환불 API, 관리자 전체·부분 환불 API
  - 환불 요청 기록(환불·환불 상품), 환불 가능 수량 확인, 티켓 환불 처리
  - PG 부분 취소, 실패 시 자동 재시도, 재시도 한도 초과 시 수동 확인 대상으로 분리
  - 환불 완료 시 결제·주문 상태 변경
  - 환불 완료 시 이번 환불의 상품별 수량만큼 재고 복구 (5-2)
  - PG 취소 웹훅으로 환불 상태를 PG와 맞추는 처리 (KAN-55, 5-3)
- **제외 범위:**
  - 환불 내역 조회 API

## 3. 기존 기능 및 시스템 활용
- **재사용할 기존 기능:**
  - PG 결제 취소 기능 (금액 불일치 보상 취소에서 쓰던 것)
  - 결제 비관적 락 조회 (결제 승인·사용자 취소에서 쓰던 것)
  - 공통 응답 형식과 공통 예외 처리
- **재사용 방식:**
  - PG 결제 취소는 **확장**했다. 기존 호출 방식(결제·사유·금액)은 그대로 두고, "PG 취소 가능 금액"을 함께 보낼 수 있는 방식을 추가했다. 기존 보상 취소는 동작이 바뀌지 않는다.
  - 재시도 구조(점유 → PG 호출 → 결과 기록, 백오프, 멈춘 처리 회수, 스케줄러)는 기존 보상 취소와 같은 방식을 따른다.
- **기존 기능의 유지 조건:** 기존 테스트가 모두 통과해야 한다. 결제 승인·보상 취소 동작은 바뀌지 않는다. 결제 웹훅은 결제 완료·환불된 결제일 때만 PG 취소 금액 확인으로 바뀐다(5-3).
- **추가 구현이 필요한 부분:** 환불 상태 관리, 환불 가능 수량 계산, 환불 전용 처리기와 스케줄러, 결제·주문의 환불 상태 변경
- **사전 확인 사항 (확인됨):** PortOne이 "PG 취소 가능 금액"이 맞지 않을 때 돌려주는 오류의 형식. PortOne server-sdk 0.24.0의 `CancellableAmountConsistencyBrokenError` 기준 `type`은 `CANCELLABLE_AMOUNT_CONSISTENCY_BROKEN`이다.

## 4. 상세 요구사항

### 공통
- **사용자 식별:** JWT 액세스 토큰. 토큰이 없거나 유효하지 않으면 401이다.
- **결제 식별:** 경로의 `pgId` (결제 생성 시 발급되는 결제 식별자)
- **응답 형식:** 모든 응답은 `{ success, message, data }` 형식이다. 실패 응답의 `data`는 없거나, 입력값 검증 실패일 때 필드별 오류다.
- **환불 금액:** 환불 상품마다 `주문 당시 가격 × 환불 수량`을 더한 값이다. 환불 수량은 요청한 티켓을 주문 상품별로 센 값이다.
- **티켓:** 환불을 기록할 때 대상 티켓을 바로 `REFUNDED`로 바꾼다. 이후 PG 취소가 `FAILED`·`DEAD`가 돼도 티켓은 되돌리지 않는다.
- **응답의 `status`:** 저장 직후 PG 취소를 한 번 시도한 뒤의 환불 상태다. 응답까지 최대 약 48초 걸릴 수 있다. PG 취소가 실패해도 오류 응답이 아니라 200과 미완료 `status`로 응답한다.

  | status | 의미 |
  |---|---|
  | `COMPLETED` | PG 취소까지 끝남 |
  | `FAILED` | 즉시 시도가 실패함. 자동으로 재시도된다 |
  | `REQUESTED` | 같은 결제의 다른 환불이 처리 중·확정 대기 중이거나, 실패해 재시도를 기다리고 있어 대기 중. 그 환불이 확정된 뒤 자동으로 처리된다 (5-2 "점유") |
  | `PG_PENDING` | PG가 취소를 접수했지만 아직 확정되지 않음(또는 응답을 해석하지 못함). 취소를 다시 보내지 않고 PG 조회로 자동 확정된다 (5-2 "확정 대기 확인") |
  | `PROCESSING` | PG 취소 중이거나, PG 취소 후 결과와 확정 대기 기록에 모두 실패함. 5분 뒤 다시 점유될 때 PG 조회로 확정된다 (5-2) |
  | `DEAD` | 재시도하지 않는 실패. PG 내역을 수동으로 확인해야 한다 (5-2) |

- **환불 가능 결제 상태:** 결제 완료(`PAID`), 부분 환불(`PARTIALLY_REFUNDED`)
- **환불 기한:** 입장일 전날 23:59:59(KST)까지. 한 주문의 티켓은 모두 주문의 입장일로 발급되므로 주문 단위로 판단한다. 관리자 환불에는 적용하지 않는다.
- **환불 가능 수량:** `주문 수량 − 이 상품의 기존 환불 수량 합계`. 티켓 상태와 환불 수량이 어긋나지 않도록 기록 전에 다시 확인한다(5-1).

### REQ-001. 전체 환불
- **설명:** 결제의 남은 미사용 티켓 전부를 환불한다.
- **실행 조건:** `POST /api/payments/{pgId}/refunds`
- **입력값:**
  ```json
  { "reason": "단순 변심" }
  ```
  | 필드 | 규칙 |
  |---|---|
  | `reason` | 필수, 공백 불가, 200자 이하 |
- **처리 규칙:**
  - 주문의 미사용(`UNUSED`) 티켓 전부를 환불한다.
  - 사용했거나(`IN_USE`·`USED`) 만료됐거나(`EXPIRED`) 이미 환불된 티켓은 건너뛴다.
  - 환불할 미사용 티켓이 하나도 없으면 거부한다.
- **결과 / 출력값:**
  ```json
  {
    "success": true,
    "message": "환불 요청에 성공했습니다.",
    "data": { "refundId": 1, "refundAmount": 40000, "status": "COMPLETED" }
  }
  ```
- **예외 및 오류 처리:**

  | 상태 | 메시지 | 상황 |
  |---|---|---|
  | 400 | 입력값을 확인해주세요 | `reason`이 없거나 공백이거나 200자 초과 (`data`에 필드별 오류) |
  | 400 | 요청 본문 형식이 올바르지 않습니다. | JSON 형식 오류 |
  | 400 | 환불 수량이 올바르지 않습니다. | 환불할 미사용 티켓이 하나도 없음 |
  | 401 | 인증이 필요합니다. | 토큰이 없음 (만료·위조 토큰은 인증 공통 응답을 따른다) |
  | 404 | 결제 내역을 찾을 수 없습니다. | 결제가 없거나 본인 결제가 아님 (존재 여부를 숨기기 위해 같은 응답) |
  | 409 | 탈퇴한 회원의 결제는 환불을 요청할 수 없습니다. | 결제 소유자가 탈퇴 상태 (`REFUND_USER_WITHDRAW`) |
  | 409 | 환불할 수 없는 결제 상태입니다. | 결제가 결제 대기·결제 실패·결제 취소·전체 환불 상태 |
  | 409 | 입장일 전날까지만 환불할 수 있습니다. | 요청 시각(KST)이 입장일 당일 이후 |
  | 409 | 다른 요청에 의해 데이터가 변경되었습니다. 다시 시도해주세요. | 같은 회원·결제의 다른 요청 처리를 3초 넘게 기다림 |

### REQ-002. 부분 환불
- **설명:** 선택한 티켓을 환불한다.
- **실행 조건:** `POST /api/payments/{pgId}/refunds/partial`
- **입력값:**
  ```json
  {
    "ticketIds": [1001, 1002, 1005],
    "reason": "단순 변심"
  }
  ```
  | 필드 | 규칙 |
  |---|---|
  | `ticketIds` | 필수, 1개 이상, 원소는 null 불가. 해당 결제의 주문 티켓이어야 한다. 같은 티켓을 두 번 넣을 수 없다 |
  | `reason` | 필수, 공백 불가, 200자 이하 |
- **처리 규칙:** 요청한 티켓을 주문 상품별로 세어 환불 수량으로 삼는다. 상품마다 환불 수량이 남은 환불 가능 수량 이하인지, 티켓이 모두 미사용인지 확인하고, 모두 통과하면 하나의 환불로 기록한다. 하나라도 실패하면 아무것도 기록하지 않는다.
- **결과 / 출력값:** REQ-001과 같은 형식이다. `message`는 "부분 환불 요청에 성공했습니다."이다.
- **예외 및 오류 처리:**

  | 상태 | 메시지 | 상황 |
  |---|---|---|
  | 400 | 입력값을 확인해주세요 | `ticketIds`가 없거나 비어 있음, null 원소, `reason` 오류 (`data`에 필드별 오류) |
  | 400 | 요청 본문 형식이 올바르지 않습니다. | JSON 형식 오류 |
  | 400 | 같은 티켓을 중복해서 환불할 수 없습니다. | 같은 티켓 ID가 두 번 이상 (`REFUND_DUPLICATE_TICKET`) |
  | 400 | 해당 주문의 티켓이 아닙니다. | 없는 티켓이거나 결제의 주문 티켓이 아님 (`REFUND_INVALID_TICKET`) |
  | 400 | 환불 수량이 올바르지 않습니다. | 남은 환불 가능 수량 초과 |
  | 401 | 인증이 필요합니다. | 토큰이 없음 (만료·위조 토큰은 인증 공통 응답을 따른다) |
  | 404 | 결제 내역을 찾을 수 없습니다. | 결제가 없거나 본인 결제가 아님 |
  | 409 | 미사용 티켓만 환불할 수 있습니다. | 사용·만료·이미 환불된 티켓 포함 (`TICKET_NOT_REFUNDABLE`). 환불 가능 수량 검사를 통과한 뒤 확인하므로, 남은 수량이 있는 상품의 환불된 티켓을 다시 요청하면 이 응답이다 |
  | 409 | 탈퇴한 회원의 결제는 환불을 요청할 수 없습니다. | 결제 소유자가 탈퇴 상태 |
  | 409 | 환불할 수 없는 결제 상태입니다. | 결제가 결제 대기·결제 실패·결제 취소·전체 환불 상태 |
  | 409 | 입장일 전날까지만 환불할 수 있습니다. | 요청 시각(KST)이 입장일 당일 이후 |
  | 409 | 다른 요청에 의해 데이터가 변경되었습니다. 다시 시도해주세요. | 같은 회원·결제의 다른 요청 처리를 3초 넘게 기다림 |

### REQ-003. 관리자 환불
- **설명:** 관리자가 회원 결제를 전체 또는 티켓 단위로 환불한다.
- **실행 조건:** `ADMIN` 권한
  - 전체 환불: `POST /api/admin/payments/{pgId}/refunds` (본문은 REQ-001과 같음)
  - 부분 환불: `POST /api/admin/payments/{pgId}/refunds/partial` (본문은 REQ-002와 같음)
- **처리 규칙:**
  - 결제 소유자를 확인하지 않는다.
  - 환불 기한(입장일 전날)을 확인하지 않는다.
  - 탈퇴 회원 차단, 결제 상태, 미사용 티켓, 환불 가능 수량 검사는 회원 환불과 같다.
  - 처리 흐름(5-1의 잠금 순서, 5-2의 PG 취소)은 회원 환불과 같다.
- **결과 / 출력값:** 회원 환불과 같다. 요청 뒤 `REFUND_ADMIN_FULL_REQUESTED`·`REFUND_ADMIN_PARTIAL_REQUESTED` 로그에 관리자 `userId`를 남긴다.
- **예외 및 오류 처리:** 회원 환불의 오류에서 본인 결제 아님(404)과 기한 초과(409)를 뺀 것과 같다. `ADMIN`이 아니면 403 "접근 권한이 없습니다."이다.

## 5. 처리 흐름

### 5-1. 환불 요청 기록 (하나의 트랜잭션)
1. 사용자가 전체 환불 또는 부분 환불을 요청한다. (부분 환불은 이 단계에서 티켓 목록이 비었는지, 같은 티켓이 중복됐는지 먼저 검증한다.)
2. 결제 소유자의 회원 행을 비관적 락으로 잠근다. 잠글 대상을 찾으려고 결제의 소유자 ID만 먼저 조회한다(잠금 없음).
   - 결제가 없으면 404
   - 회원 탈퇴와 같은 행을 잠가, 환불 요청과 탈퇴가 동시에 진행되지 않게 한다([refund-withdrawal-concurrency.md](../troubleshooting/refund-withdrawal-concurrency.md)).
3. 결제를 비관적 락으로 조회한다. 같은 결제에 대한 다른 환불 요청은 앞의 락이 풀릴 때까지 기다린다(최대 3초).
4. 본인 결제인지 확인한다. (관리자 환불은 건너뜀)
   - 본인 결제가 아니면 404
5. 결제 소유자가 탈퇴 상태면 409.
6. 결제가 결제 완료 또는 부분 환불 상태인지 확인한다.
   - 아니면 409
   - 요청 시각(KST)이 주문 입장일 당일 이후면 409 (관리자 환불은 건너뜀)
7. 환불할 티켓을 비관적 락으로 조회한다.
   - 부분 환불: 요청한 티켓. 없거나 결제의 주문 티켓이 아니면 400
   - 전체 환불: 주문의 미사용 티켓 전부. 하나도 없으면 400
8. 티켓을 주문 상품별로 세어 환불 상품을 만들고, 상품마다 남은 환불 가능 수량 이하인지 확인한다.
   - `남은 환불 가능 수량 = 주문 수량 − 이 상품의 기존 환불 수량 합계`
   - 기존 환불 수량에는 **모든 상태**의 환불을 포함한다. 진행 중(`REQUESTED`·`PROCESSING`), 재시도 대기(`FAILED`)는 아직 PG 취소될 수 있고, `DEAD`는 PG에서 취소됐는지 알 수 없으므로 수동으로 확인하기 전까지 포함한다.
   - 초과하면 400
9. 티켓을 `REFUNDED`로 바꾼다. 미사용 티켓이 아니면 409.
10. 환불을 `REQUESTED` 상태로 기록하고 커밋한다. 이때 회원·결제·티켓 락이 풀린다.
11. 같은 요청 안에서 PG 취소를 한 번 시도하고(5-2), 시도 후 환불 상태를 응답한다.

- 격리 수준은 READ COMMITTED다. 소유자 ID를 먼저 조회한 뒤 잠금을 기다리므로, 기다리는 동안 다른 요청이 커밋한 환불 수량을 읽어야 하기 때문이다.

### 5-2. 환불 PG 취소 처리 (트랜잭션 밖에서 PG 호출)
- **처리 시점:** 요청 직후 즉시 1회 시도한다. 실패했거나 시도하지 못한 환불은 스케줄러가 30초 간격으로 최대 20건씩 처리한다.
- **처리 대상:** `REQUESTED` 환불, 재시도 시각이 지난 `FAILED` 환불, `PROCESSING`으로 5분 넘게 멈춘 환불
- **확인 대상:** 다음 확인 시각이 지난 `PG_PENDING` 환불. 취소를 다시 보내지 않고 PG 결제 조회로만 확정한다(아래 "확정 대기 확인"). 스케줄러는 처리 대상 다음에 확인 대상을 30초마다 최대 5건씩 처리한다. 확인마다 PG를 조회하므로, PG 장애로 `PG_PENDING`이 쌓여도 환불 처리가 밀리지 않게 처리 대상(20건)과 따로 제한한다(`payment.refund.scheduler.pg-check-batch-size`).
- **점유 (짧은 트랜잭션):**
  1. 결제 → 환불 순서로 잠근다.
  2. 다시 확인해 처리 대상이 아니면 건너뛴다. 즉시 시도와 스케줄러, 여러 서버가 동시에 같은 환불을 처리하려 해도 한 곳만 처리한다.
  3. **같은 결제의 다른 환불이 이 환불의 점유를 막으면 건너뛴다.** 같은 결제의 환불은 PG 취소가 확정될 때까지 한 번에 하나씩 처리한다. 앞선 취소가 확정되기 전에 다음 부분 취소를 보내면 PG 취소 가능 금액이 어긋날 수 있기 때문이다.
     - 다른 환불이 `PROCESSING`이거나 `PG_PENDING`이면 항상 막힌다.
     - 다른 환불이 `FAILED`이면(KAN-132): PG에 취소가 반영됐는지 모를 수 있으므로, 이 환불이 `REQUESTED`면 막히고, 이 환불이 `FAILED`면 id가 더 작은 `FAILED`에만 막힌다(먼저 실패한 것부터 재시도). 재시도 시각 전인 `FAILED`도 막는다.
     - 처리 중 멈춘 `PROCESSING`을 다시 점유할 때는 `FAILED`에 막히지 않는다. 이미 PG로 나갔을 수 있는 환불을 먼저 확정해야 하기 때문이다.
     - 건너뛴 환불은 상태가 그대로라 앞선 환불이 끝난 뒤 스케줄러가 처리한다. 이런 환불은 처리 대상 조회에서부터 같은 규칙으로 빼서, 배치 앞쪽을 차지해 다른 결제의 환불이 밀리지 않게 한다.
  4. `PROCESSING`으로 바꾸고 시도 횟수를 1 늘린다.
  5. PG 취소 가능 금액을 계산한다: `결제 금액 − 완료(COMPLETED)된 환불 금액 합계`. PG에 실제 반영된 환불만 뺀다.
- **재시도 전 확인:** 시도 횟수가 2 이상이면 취소를 보내기 전에 PG 결제를 조회한다. 이전 시도가 취소를 보낸 뒤 결과를 기록하지 못했을 수 있기 때문이다(서버 종료, 결과 기록 실패, 통신 실패).
  - 금액이 같은 접수된(`REQUESTED`) 취소 내역이 있으면 취소를 보내지 않고 그 내역으로 `PG_PENDING`이 된다. 접수된 취소 금액이 PG 취소 가능 금액에서 바로 빠지는지 알 수 없어, PG 취소 가능 금액만으로는 같은 취소를 다시 보내는 것을 막을 수 없다.
  - `PG 취소 누적 금액 − 완료 환불 합계 = 이번 환불 금액`이면 이미 반영된 것이므로 취소를 보내지 않고 성공으로 기록한다.
  - PG에 결제가 없으면 반영된 취소가 없으므로 취소를 보낸다.
  - 조회에 실패하면 결과를 모른 채 취소를 다시 보내지 않도록 실패로 기록한다.
- **PG 부분 취소:** 환불 금액, 환불 사유, PG 취소 가능 금액을 보낸다. PG는 취소 가능 금액이 자신이 가진 값과 다르면 거절하므로, 같은 취소가 두 번 처리되는 것을 막는다.
  - 통신 실패는 같은 요청 키로 다시 보낸다. 첫 시도를 포함해 최대 3회(재시도 2회)이고, 1회당 연결 5초 + 응답 10초다.
  - 다시 보낸 요청에 PG가 "같은 키의 앞선 요청 처리 중"(409 `IDEMPOTENCY_OUTSTANDING_REQUEST`)으로 응답하면 1초(`portone.cancel-outstanding-retry-delay`, 연속이면 2초) 기다려 같은 키로 다시 보낸다. 횟수는 통신 재시도와 함께 3회로 센다. 이 응답을 한 번이라도 받았는데 끝내 결과를 확인하지 못하면 실패가 아니라 `PG_PENDING`이 된다. 앞선 요청이 PG에 도달했기 때문이다.
  - PG가 "이미 취소된 결제"라고 응답하면 성공으로 보지 않는다. 부분 취소에서 이 응답은 다른 경로로 전체 취소됐다는 뜻이라 이번 환불이 반영됐다고 볼 수 없다. 재시도하지 않고 `DEAD`로 보낸다. 전체 취소(보상 취소)에서는 기존과 같이 성공으로 본다.
    - 이때 PG는 전체 취소 상태지만 결제는 `PAID` 또는 `PARTIALLY_REFUNDED`, 주문은 `COMPLETED` 또는 `PARTIALLY_REFUNDED`로 남는다. 남은 수량으로 다시 환불을 요청할 수 있고, 그 환불도 같은 응답을 받아 바로 `DEAD`가 된다. 결제·주문 상태는 수동으로 맞춰야 한다 (10장 "`DEAD` 확인 수단").
  - **취소 응답 상태로 결과를 정한다.** PG는 200이어도 취소가 끝나지 않았을 수 있다.

    | 취소 응답 | 처리 |
    |---|---|
    | 200 + `SUCCEEDED` | 성공 |
    | 200 + `REQUESTED`, 본문 없음·해석 불가·모르는 상태, 처리 중 응답 뒤 결과 미확인 | `PG_PENDING` (취소 내역 ID가 있으면 저장). 취소를 다시 보내지 않는다 |
    | 200 + `FAILED`, 4xx·5xx, 통신 실패 | 실패 |

- **결과 기록은 점유한 처리만 한다.** 점유할 때의 시도 횟수와 지금 시도 횟수가 다르면(멈춘 처리로 보고 다른 처리가 다시 점유함) 이전 처리의 늦은 결과는 기록하지 않고 건너뛴다.
- **성공 (짧은 트랜잭션):** 결제 → 환불 순서로 잠근 뒤, 환불을 `COMPLETED`로 바꾸고 결제·주문 상태를 함께 바꾼다.
  - 모든 주문 상품의 완료된 환불 수량이 주문 수량과 같아지면 → 결제·주문 `REFUNDED`
  - 그렇지 않으면 → 결제·주문 `PARTIALLY_REFUNDED`
  - 아직 재시도 중인 다른 환불이 있으면 `PARTIALLY_REFUNDED`로 남는다.
  - 같은 트랜잭션에서 **이번 환불의 상품별 수량만큼 재고를 복구한다.** 환불은 `COMPLETED`가 한 번만 되므로 이중 복구되지 않는다.
    - 재고가 0이어서 `OUT_OF_STOCK`(품절)이 된 상품은 복구되면 `ON_SALE`로 되돌린다. 관리자가 중지한 `STOPPED` 상품은 재고가 0이어도 상태를 유지한다.
    - 환불 요청 저장(`REQUESTED`)·`FAILED`·`DEAD`·`PG_PENDING`에서는 복구하지 않는다. PG 취소가 확정(`COMPLETED`)된 환불만 복구한다.
    - 확정 대기 확인(`SUCCEEDED`)과 웹훅 동기화(5-3)로 `COMPLETED`가 되는 경우도 같은 방식으로 복구한다.
- **실패:**
  - `FAILED`로 바꾸고 1분, 2분, 4분, 8분 뒤에 재시도한다.
  - 5번째 시도도 실패하면 `DEAD`가 되고 오류 로그를 남긴다. 이후 자동으로 처리하지 않으므로 PG 내역을 확인해 수동으로 처리한다.
  - 실패 사유는 최대 500자까지 기록한다.
  - PG가 "PG 취소 가능 금액이 맞지 않는다"(`CANCELLABLE_AMOUNT_CONSISTENCY_BROKEN`)고 거절하면 앞선 요청이 이미 처리됐을 수 있으므로 재시도하지 않고 시도 횟수와 관계없이 바로 `DEAD`로 보낸다.
- **PG 취소는 성공했는데 결과 기록에 실패한 경우:** 실패로 기록하지 않는다. 실패로 기록하면 재시도하면서 취소를 다시 보내기 때문이다. 오류 로그를 남기고 `PG_PENDING`으로 기록해 조회로 완료되게 한다. 그것도 실패하면 `PROCESSING`으로 남고, 5분이 지나 다시 점유될 때 재시도 전 확인이 PG 취소 누적 금액으로 성공을 확인해 `COMPLETED`가 된다. 그 전에 PG 취소 웹훅이 오면 PG 기준으로 `COMPLETED`가 된다(5-3).
- **확정 대기(`PG_PENDING`) 확인:** 점유하지 않고 PG 결제를 조회해 판단한다. 결과 기록은 환불을 잠그고 같은 확인 대기 주기(시작 시각)인지 다시 확인한 뒤 반영한다.
  - 취소 내역 ID가 있으면 조회 응답의 같은 ID 취소 내역 상태로 판단한다: `SUCCEEDED` → `COMPLETED`(결제·주문 상태 함께 변경), `FAILED` → `FAILED`(백오프 후 취소 재시도. 시도 횟수가 이미 5회면 바로 `DEAD`), 그 밖 → 다음 확인 예약.
  - ID가 없으면(응답을 해석하지 못함) 금액이 같은 접수된 취소가 없고 `PG 취소 누적 금액 − 완료 환불 합계 = 이번 환불 금액`일 때만 `COMPLETED`로 본다. 실패는 확인할 수 없으므로 기한까지 기다린다. 같은 결제의 환불은 한 번에 하나씩 처리하므로 금액으로 판단할 수 있다.
  - 조회 실패나 PG에 결제 없음은 실패로 보내지 않고 다음 확인을 예약한다.
  - 다음 확인 간격은 `PG_PENDING`이 된 뒤 지난 시간(최소 1분, 최대 30분)이라 대략 두 배씩 늘어난다. 24시간 안에 확정되지 않으면 `DEAD`가 되고 오류 로그를 남긴다. PG에서 취소 반영 여부를 먼저 확인한 뒤 수동 처리한다.

### 5-3. PG 취소 웹훅으로 환불 상태 맞추기
- **목적:** PG에서는 취소됐지만 결과 기록에 실패했거나 응답이 타임아웃 나 `PROCESSING`·`FAILED`·`DEAD`로 남은 환불을 PG 기준으로 완료한다.
- **처리 시점:** 기존 웹훅 처리(Inbox 저장 → 스케줄러)를 그대로 쓴다. 결제가 `PAID`·`PARTIALLY_REFUNDED`·`REFUNDED`이면 웹훅 종류와 관계없이 이 처리로 넘어간다.
- **확정 대기 환불 먼저 (웹훅 본문은 쓰지 않음):** PG를 다시 조회한 뒤, 이 결제에 `PG_PENDING` 환불이 있으면 그 응답으로 5-2 "확정 대기 확인"과 같이 먼저 판단한다. 웹훅이 스케줄러보다 확정을 앞당긴다.
  - 완료 → `COMPLETED`로 기록하고 웹훅 `PROCESSED`
  - 아직 확정 안 됨 → 바꾸지 않고 웹훅 `PROCESSED`(스케줄러가 이어서 확인). PG 취소 누적 금액에 접수만 된 취소가 포함되는지 알 수 없으므로 금액으로 판단하지 않는다
  - 실패 → `FAILED`로 기록한 뒤 아래 금액 판단을 이어서 한다
- **판단:** PG 조회 결과의 취소된 누적 금액(`amount.cancelled`)으로, 결제 → 환불 순서로 잠근 뒤 `차이 = PG 취소 금액 − 완료(COMPLETED) 환불 합계`를 계산한다.

  | 차이 | 처리 | 웹훅 상태 |
  |---|---|---|
  | 0 | 이미 맞음. 아무것도 바꾸지 않는다 | `PROCESSED` |
  | > 0, 금액이 정확히 같은 `PROCESSING`·`FAILED`·`DEAD` 환불이 1건 | 그 환불을 `COMPLETED`로 바꾸고 결제·주문 상태를 함께 바꾸며 재고도 복구한다(5-2 성공과 같음) | `PROCESSED` |
  | < 0 | PG 조회 이후 같은 결제의 다른 환불이 완료된 경우다(조회 시점 차이). 바꾸지 않고 실패로 기록해 다시 조회한다 | `FAILED` (백오프 후 재시도, 한도 초과 시 `DEAD`) |
  | 그 밖 (후보 없음·2건 이상) | 바꾸지 않고 오류 로그를 남긴다. 우리 시스템 밖의 취소(PortOne 콘솔 등)도 여기에 해당한다 | **`DEAD`** (수동 확인) |

  - `REQUESTED`는 아직 PG에 보낸 적이 없으므로 후보가 아니다. `PG_PENDING`은 취소 내역으로 판단하므로 금액 판단의 후보가 아니다.
  - PG 조회 실패·락 충돌은 웹훅 실패로 기록되어 재시도된다.
- **동시 처리:** PG 취소 응답을 기다리는 사이 웹훅이 먼저 완료하면, 이후 결과 기록은 "다른 처리가 먼저 기록함"으로 건너뛴다. 실패 기록도 같은 이유로 건너뛴다.
- **알려진 한계:**
  - 우리 시스템 밖의 취소 금액이 우연히 미완료 환불 1건과 같으면 그 환불이 완료로 처리될 수 있다.
  - 금액이 같은 미완료 환불이 2건 이상이면 맞추지 않는다. 예: 환불 A가 응답 타임아웃으로 `FAILED`지만 PG에는 반영됐고, 이어 같은 결제의 환불 B가 PG 취소 가능 금액 불일치로 `DEAD`가 됐는데 A와 B의 금액이 같은 경우. 잘못 완료하지 않고 수동 확인으로 남긴다.
- **기존 결제 웹훅 동작 변경:** 이미 `PAID`인 결제의 웹훅도 PG를 한 번 조회한다. 차이가 0이면 결과는 이전과 같다(`PROCESSED`).
  - PG 장애 중에는 이전에 바로 끝나던 결제 완료 웹훅도 실패로 기록되어 재시도되고, 장애가 길면 `DEAD`가 된다. 외부 취소를 감지하려면 PG 조회가 필요해 감수한다.

## 6. 제약사항 및 주의사항
- **기존 동작 중 유지해야 할 부분:** 결제 승인, 금액 불일치 보상 취소의 동작. 결제 웹훅은 결제 완료 전 결제의 처리를 유지한다(결제 완료·환불된 결제는 5-3).
- **변경하면 안 되는 부분:** PG 결제 취소의 기존 호출 방식(결제·사유·금액). 보상 취소가 그대로 사용한다.
- **권한 / 보안 조건:**
  - 회원 환불은 로그인 사용자(JWT) 본인 결제만 환불할 수 있다. 다른 사용자의 결제는 결제가 없는 것과 같은 404로 응답한다.
  - 관리자 환불은 `ADMIN` 권한만 호출할 수 있다(`/api/admin/**`).
- **성능 및 데이터 제약:**
  - 즉시 시도를 요청 안에서 기다리므로 PG 응답이 느리면 응답도 최대 약 48초 걸린다.
  - 같은 회원·결제의 환불 요청은 회원·결제 락 때문에 순서대로 처리되고, 3초 넘게 기다리면 409로 끝난다.
- **기술적 제약:**
  - 트랜잭션 안에서 PG를 호출하지 않는다.
  - 잠금 순서: 환불 요청 기록은 회원 → 결제 → 티켓, PG 취소 처리(점유·결과 기록·웹훅 동기화)는 결제 → 환불 순서다.
  - 다른 처리가 커밋한 최신 상태를 읽어야 하는 곳은 READ COMMITTED로 실행한다. MySQL 기본 격리 수준에서는 락을 기다린 뒤에도 기다리기 전의 데이터를 읽어, 같은 결제의 환불이 동시에 PG로 나가는 문제를 MySQL 테스트로 확인했다.
    - 대상: 환불 요청 기록 4개 경로(회원·관리자 전체·부분), 점유(`claim`), 결제·주문 상태를 함께 바꾸는 완료 기록(`recordComplete`, `recordPgCancelled`, `syncWithPgCancelledAmount`)
    - 환불 행만 잠그는 기록(`recordPgPending`, `recordFailure`, `recordDead`, `recordPgCancelFailed`, `reschedulePgCheck`)은 기본 격리 수준이다.
  - 처리 중 멈춘 환불을 다시 점유하는 기준(5분)은 PG 취소 최대 소요 시간(약 48초, 대기 설정 상한 10초면 약 75초)보다 길어야 한다.
  - 스케줄러 스레드 풀(3개)은 웹훅·보상 취소·환불·주문 만료 자동 취소·티켓 만료·슬롯 생성 스케줄러가 함께 쓴다. ECS에서는 API 인스턴스(`api` 프로필)가 환불 스케줄러를 끄고 worker에서만 실행한다. 요청 직후 즉시 시도는 API 인스턴스에서 실행된다.
  - 테이블은 Flyway `V1__init.sql`이 만든다(11장).

## 9. 환불 상태 전이
| 상태 | 의미 | 전이 가능 상태 |
|---|---|---|
| `REQUESTED` | 환불 기록됨, PG 취소 대기 | `PROCESSING` |
| `PROCESSING` | PG 취소 중 | `COMPLETED`, `PG_PENDING`, `FAILED`, `DEAD`, `PROCESSING` |
| `PG_PENDING` | PG가 취소를 접수했지만 확정 안 됨(또는 응답 해석 불가), 조회로 확정 대기 | `COMPLETED`, `FAILED`, `PG_PENDING`, `DEAD` |
| `FAILED` | PG 취소 실패, 재시도 대기 | `PROCESSING`, `COMPLETED`(PG 기준, 5-3) |
| `COMPLETED` | PG 취소 완료 | 없음 |
| `DEAD` | 재시도 한도 초과 또는 재시도하면 안 되는 실패, 수동 확인 필요 | `COMPLETED`(PG 기준, 5-3) |

- `PROCESSING → PROCESSING`은 5분 넘게 멈춘 처리를 다시 점유하는 경우다.
- `DEAD`는 `FAILED`가 아니라 재시도 중(`PROCESSING`)에 5번째로 실패할 때 정해진다. PG가 "이미 취소된 결제" 또는 "PG 취소 가능 금액 불일치"로 거절하면 시도 횟수와 관계없이 `PROCESSING`에서 바로 `DEAD`가 된다.
- `PG_PENDING`에서 조회로 취소 실패를 확인했을 때 시도 횟수가 이미 5회면 `FAILED`를 거치지 않고 바로 `DEAD`가 된다.
- `FAILED`·`DEAD` → `COMPLETED`는 PG 재조회로 취소 반영을 확인한 경우(5-3)에만 쓴다. PG 취소 성공 응답으로 완료하는 경로(5-2)는 `PROCESSING`에서만 가능하다.
- `PG_PENDING`에서는 취소를 다시 보내지 않는다. `PG_PENDING → PG_PENDING`은 다음 확인을 예약하는 경우, `PG_PENDING → DEAD`는 확인 기한(24시간)이 지난 경우다.
- 허용되지 않은 전이는 409 "유효하지 않은 환불 상태 전이입니다."로 막는다(내부 처리용).

### 결제·주문 상태와의 관계
| 결제·주문 상태 | 환불 요청 | 환불 완료 시 |
|---|---|---|
| 결제 완료 | 가능 | 부분 환불 또는 전체 환불 |
| 부분 환불 | 가능 | 부분 환불 또는 전체 환불 |
| 전체 환불 | 불가 (409) | — |
| 결제 대기·결제 실패·결제 취소 | 불가 (409) | — |

## 10. 미해결 사항
| 항목 | 현재 상태 | 영향 |
|---|---|---|
| PG 취소 가능 금액 불일치 오류 구분 | 해결. server-sdk로 `type` 값을 확인하고 바로 `DEAD`로 보낸다 | 실제 PortOne 응답으로는 아직 확인하지 않았다 (아래 "실제 PortOne 연동") |
| 실제 PortOne 연동 | 가짜 PG로만 테스트 | 취소 가능 금액 필드가 실제로 받아들여지는지 확인 필요 |
| 재고 복구 | 해결. 환불이 `COMPLETED`가 될 때 이번 환불의 수량만 복구한다 (5-2) | 관리자 상품 수정은 비관적 락과 version 비교로 차감을 덮어쓰지 않는다 |
| `DEAD` 확인 수단 | 오류 로그만 남음 | 알림·조회 수단과 수동 환불 절차 필요 |
| PG 취소 웹훅 반영 | 해결 (KAN-55, 5-3) | 우리 시스템 밖의 취소는 자동으로 맞추지 않고 웹훅 `DEAD`로 수동 확인한다. 금액이 우연히 같은 미완료 환불이 있으면 잘못 완료될 수 있다 |

## 11. 데이터
테이블은 Flyway `V1__init.sql`이 만든다. 스키마 변경 방법은 [migration.md](../database/migration.md). 시각 컬럼은 `DATETIME(6)`으로 소수 초까지 저장한다(재시도 시각 비교가 어긋나지 않게).

**`refunds` (환불, 환불 1건 = PG 취소 요청 1건)**
| 컬럼 | 설명 |
|---|---|
| `id` | PK |
| `payment_id` | 환불할 결제 (필수) |
| `refund_amount` | 환불 금액 (필수) |
| `status` | 환불 상태 (9장, 필수) |
| `reason` | 환불 사유, 200자 (필수). PG 취소 사유로도 보낸다 |
| `requested_at` | 요청 시각 (필수) |
| `completed_at` | PG 취소 완료 시각 |
| `attempt_count` | PG 취소 시도 횟수 (필수) |
